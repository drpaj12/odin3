Stage 2 also builds processes (2D Task 21; EL-33 to EL-35, EL-41 T9/T10): each `always` block is one `$proc` node (or none when it has no output), made whole by the process generator (`pg.h`) following Yosys's `ProcessGenerator`: the sorted lvalue bits are the outputs, each with a `$0` temporary net and, per chunk (a run of consecutive bits of one variable), a root hold action `t0 = c` and a sync action `c <- t0`; blocking assignments update `rv` so later reads see the value, non-blocking ones do not (`q <= q + 1` and `r2 <= r1` read the register); an assignment removes the earlier actions of its bits and appends one action per run of consecutive temporary bits, the leftmost part of a concatenation first; `O` pins are the nets some action assigns and `I` pins every other net read, constants on their shared nets, both in net-ID order, so the node's `BODY` is IR-19's canonical layout (cases, switches and actions numbered breadth first). A design read from a file (JSON, for one) can carry forged attributes that match, so `raise` is only as sound as its input: run `cone_check` in the same session, on the same design, immediately before `raise`. An outside reader added to an internal net after the proof is refused (the net becomes a boundary net, so the hash or the binding check fails). The cell has one `DERIVED` provenance record whose parents are the provenance of every replaced node, so `odin3_prov_sources` of the cell is the union of their sources (nodes without provenance add none; none at all gives the cell provenance 0). The cell has no name and no copied attributes; the module's `odin3:cone_*` result attributes stay, and a second `raise` finds the group gone and fails. Errors also: group empty in every module, usage. Info line per module: `raise: module 'M': group 'K=V': N nodes replaced by one TYPE`. `-const PORT=V` (v1.0.5, spec K-6) must match the `cone_check` run, spelling included (it is part of `odin3:cone_cell`). In the run phase only, each constant bit of the new cell is connected to the net of a live `$_CONST0_`/`$_CONST1_` node outside the group (lowest node ID), else of one `raise` creates, so a refused module gets no new node; a constant driver inside the group is never reused, since its node is deleted. |

**Processes** (2D EL-33, as amended in 2D spec v4.2, "mode P"). Each pass declares whether it may
run on a design that still has processes (`$proc` nodes, `docs/IR.md` IR-19): the
`odin3_pass_def.processes` flag (`ODIN3_PASS_PROCESSES_OK` or `_REFUSE`), and for a plugin pass
the `odin3_plugin_pass.processes` slot (NULL is `REFUSE`). Before a `REFUSE` pass runs, the pass
manager fails it when some module has a process, naming the first such module in creation order:
`pass '<name>': module '<m>' has processes; run proc first` (`ODIN3_ERR_INVALID_ARG`; nothing
runs, no pass run is opened). The `OK` passes are `read_blif`, `read_techlib`, `read_project`,
`dump_project`, `dump_locs`, `preprocess`, `check`, `stats`, `compact`, `hierarchy`, `write_verilog_ast`,
`write_rtlil` (2D) and `proc` (2E, which lowers them); `read_verilog` (2C/2D) and the eight opt
passes of 2F (`opt`, `opt_expr`, `opt_merge`, `opt_muxtree`, `opt_reduce`, `opt_share`, `opt_dff`,
`opt_clean`) are `OK` (registered by 2F Task 4; all eight are real). Every other pass is `REFUSE`: here `write_blif`, `write_json`,
`write_verilog`, `write_dot` and `sim`; later `flatten`, `lower` and `abc`. An `OK` pass treats a
`$proc` node as opaque (no constant propagation or CSE through it; its `O` pins drive unknown
values, its `I` pins read); `opt_muxtree` and `opt_clean` skip a module that still has processes.
The writers `odin3_blif_write`, `odin3_json_write`, `odin3_verilog_write` and `odin3_dot_write`
also refuse such a design themselves, for callers that bypass the pass manager: `module '<m>' has
processes; run proc first`, before the path is opened.
