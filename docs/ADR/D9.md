# D9: Provenance on every IR object

Status: Accepted
Date: 2026-10-08

## Context
The aim is source-line to VPR-block tracing without Odin III loaded (spec §2 rationale).
Provenance also supports "Agentic construction" and RE reporting (spec §1, §8).

## Decision
Every IR object carries provenance: pointers in-process, plus stable string IDs that survive
serialization and appear in emitted names.

## Consequences
Positive:
- A VPR block can be traced to its source line from the emitted netlist alone.
Negative:
- Cost on every node, pin, and net (spec §5.3: `struct odin3_prov` with `loc`, `ast`,
  `origin`, `hier_path`) against the 2M-node, < 2 GB target (spec §5.1).
- Provenance names are long; VPR runtime impact is unmeasured (spec §13 #6).
- Passes must maintain the forward AST to IR index incrementally (spec §5.3).
Forces on later phases:
- Phase 1: provenance in the core IR; the string-ID scheme and `--name-style` flag.
- Phase 2+: front ends carry source locations into the AST (spec §4.1); the slang adapter
  copies them verbatim (spec §4.2); AST is never
  discarded (spec §4.5). Netlist readers give structural-only provenance until `raise`
  (spec §4.4).
- Emitted names follow `hier/path/cellname@file:line` (spec §5.3).
- Resolved 2026-10-08 (`docs/IR.md` IR-12, PHASE1 #3/#9): no pointers — every object holds a
  provenance ID into a hash-consed lineage DAG, and everything is reached by ID or hash.
