# D14: Provenance is one two-way granularity DAG over the whole CAD flow

Status: Accepted (Peter 2026-10-25)
Date: 2026-10-25

## Context
Peter, 2026-10-25, on how provenance should work:

> "Provenance should suggest where it comes from, so an if in an always has both (this is a
> hieararchy) each lower granularity keeps the ideas it's from (yes this loses detail, but it
> suggests) also, if a logic optimization blends 2 constructs or clusters 2 constructs this should
> be labelled as a joining of two ideas"

> "Is a second file good (is it because the Blifs names can't be long - didn't we have a hashing
> method to get this)?"

The answer agreed with him: extend the existing `--name-style hash` name map, not a new file kind.

> "are you thinking about provenance this way now (HDL is hierarchy of granularity) that should be
> captured in all places as the CAD refines it (some times in flattening and bit level) but also
> coarsening in optimization, LUTs, Clusters"

> "I think AST and Netlist are both part of provenance"

What exists today (details with file:line in `docs/V1.2.0.md`, "Current state"):

- A provenance record (`src/ir/prov.h:120`) holds kind, run, op, source locations, an AST node ID,
  a module-relative `hier` string of named scopes only, and parent records. SOURCE records are flat:
  the record of a statement does not point at the record of the `if` or `always` that holds it.
  The nesting exists only in the AST, reachable through the record's `ast` field while the AST store
  of the read run is held (`docs/IR.md` IR-12; `docs/specs/2026-10-09-2A-ast-design.md` AST-15).
- The AST store is freed at the end of the read unless `--keep-ast` or a `wants_ast` pass keeps it
  (`src/frontends/verilog/elab1.c:527`, `src/ir/design.c:253`). Writers and consumers normally run
  with no AST. The public ABI does not return the `ast` field at all (`odin3_source`,
  `include/odin3/odin3.h:790`).
- A record does not say whether the step that made it refined, rewrote or coarsened; both can only
  be guessed from the pass name and the parent count, and the code does not follow that guess
  (`proc` muxes have many parents and refine; `src/passes/proc/proc_emit.c:581`).
- The name an object gets in output, and every consumer, uses only the first SOURCE leaf of the
  backward walk (`src/backends/common/hdl_loc.c:507`, `src/backends/prov_name.c:9`). The hash name
  map is a flat list of nets (`src/backends/blif/writer.c:548`) with one location each.
- Joins (opt merge, CSE, ABC regions) exist as DERIVED records with several parents
  (`src/passes/opt/merge.c:866`, `src/passes/abc/prov.h:66`) but nothing says that two distinct
  HDL constructs were blended, and nothing exists after Odin III (pack, place).
- The consumers pay for this: Loki rebuilds the construct of a final cell by a span-subset join
  and guesses instance paths (`loki/labels.py:41`, `loki/labels.py:83`), the timing attribution
  needs a second provenance BLIF and a positional join (`tools/flow/timing_attr.py:119`), and
  Norns finds that one `always` line holds 1739 of the 2506 blocks of `sha`
  (`scripts/build_words.py:4`).

## Decision
1. Provenance is one two-way DAG over the whole flow. Its levels, coarse to fine, are: module,
   block (process, continuous assign, generate), branch (if or case arm), statement, expression,
   word, gate, LUT, BLE, CLB, placed site. The instance is a separate axis (the flatten path),
   not a rung of this ladder: an `INSTANCE` is a sibling of the processes in its parent module, not
   their ancestor. There is no `design` rung (no record or AST node sits there) and no `bit` rung
   (`lower` makes one record per word cell, shared by its gates). The upper levels are AST nodes;
   the lower levels are netlist objects. Both are provenance (Peter's last quote), in one DAG:
   SOURCE records link into the AST level, DERIVED records link netlist levels to each other.
2. Every step declares its class: the pass says, for each operation it starts, whether the
   operation refines (1 to N), rewrites (1 to 1), coarsens (N to 1), or only adds context (flatten
   adds the instance), and between which levels. The class is held in a design-global side table:
   a default per (run, op) and an override per derived record ID where one operation derives
   records of two classes; flatten also declares which trailing parents are context. The record
   layout and its hash-consing identity do not change. A DERIVED
   record that has no class is a `check` failure in Debug. A pass that only
   rewires adds no record, as today (IR-12).
3. Lower-granularity objects inherit the full chain of what they came from: the chain of an object
   runs through its constructs (statement, branch, block, module). The chain loses detail on
   purpose; it suggests.
4. A coarsen step whose inputs come from two or more distinct constructs is labelled a join of
   those constructs, with the pass, the operation and the constructs. "Distinct" is decided at the
   nearest statement-or-coarser construct, so two expressions of one statement are not a join.
   An operation the pass declares as bulk (ABC's over-budget single record) is labelled a lossy
   join.
5. The AST level is exported as part of provenance and kept as part of the design, so a netlist
   object can be walked to its constructs and source text without the original run's in-memory AST
   store. The recommended form is a design-held construct table (the AST nodes that records
   reference, with their ancestors, each with kind, span, parent), built when elaboration ends and
   kept whatever `--keep-ast` says. The alternative is the construct-kind subset of the AST;
   the full AST is a third, dearer option (`docs/V1.2.0.md`, "The AST layer"). The table mode is a
   read-time option; export may request a subset of what was kept, and running out of budget is an
   error, not a silent downgrade.
6. Export goes through the existing hash name map, not a new file kind: BLIF, JSON and Verilog
   keep their hash names, and the map (`<file>.names`, or `--name-map`) gains records, chains,
   joins and the construct table, in a new map version that is opt-in (`--prov-map`, which
   requires `--name-style hash` and is an error otherwise). `names --lookup` and the Python API
   return the record. Steps after Odin III (BLE, CLB, site) are appended to the same schema by a
   tool that reads VPR's `.net` and `.place`; VPR is unchanged.
7. The version 2 map **is read back into the IR** (Peter 2026-10-25, against the first
   recommendation). `read_blif`, `read_json` and `read_verilog -netlist` with a version 2
   `--name-map` restore the pass runs, the records with their classes, the construct table and the
   post-Odin lines (marked stale once a later pass runs); the `ast` of a restored SOURCE record is
   remapped to its construct row (there is no AST store), record identity keeps its form, `check`
   rules 12 and 13 hold, and write, read, write gives a byte-identical map for the `refs`, `full`
   and `none` modes with no call-site miss. `constructs` mode and call-site misses are canonical
   from the second write on (write 2 = write 3). Netlists are byte-identical only for the reader
   and writer pairs whose idempotence Task 9 proves first (V1.2.0 section 4.5, Task 9).
8. Joins carry why and how critical (Peter 2026-10-25): a multi-label set of clustering classes with
   shares (the five Norns round-4 N17 classes: series-critical, series-noncritical, shared-input,
   orthogonal and filler, defined in V1.2.0 section 3.6; possibly hybrid), the packer's gain terms and the pass objective where recorded,
   and criticality data (pack-time, post-route slack, near-critical flags with the margin, the
   number of near-critical paths), each marked recorded or inferred (V1.2.0 section 3.6, Task 10).

Spec, schema, plan and agent defaults: `docs/V1.2.0.md`.

## Consequences
Positive:
- "Which `if` arm, in which `always`, in which instance, made this LUT" and "this CLB holds LUTs
  from two statements" become lookups, not heuristics. Loki's labels, the Loki loss audit (L15),
  the Norns packing census (N17), the timing attribution and the Wyrd view share one source.
- The timing attribution can drop its second provenance BLIF and positional join (a measured
  report-only check in V1.2.0 section 6 shows VPR gives identical packing, placement, routing and
  critical path on hash-named BLIFs); Loki can drop its span-subset join and instance-site climb
  for designs that carry the map.
- Existing outputs are unchanged unless the new option is given, so goldens stay as they are.
Negative:
- The default flow gains a construct table in memory (order of 50 bytes per referenced AST node
  with its ancestors; measured in `docs/V1.2.0.md` section 5) and the map file grows (measured
  there). A read-time switch turns the table off.
- Three IR additions, all design-global beside the records: the construct table, the op-class
  table and the `extra` text list of restored post-Odin lines, plus a per-run `restored` flag.
  None adds a field to an IR object or a provenance record or changes hash-consing. They add
  `check` rules 12 and 13, and every pass that starts a provenance operation (33 begin sites: 17
  direct calls and 16 through `odin3_kit_begin_rewrite`) declares its class. This is a design-rule change (D9 amended)
  and needs Peter's review.
- The public ABI goes from 6 to 7. The plugin loader and the Python binding require an exact
  version match (`src/api/plugin.c:30`, `plugins/example_c/example_plugin.c:108`,
  `plugins/python/odin3.py:115`), so every compiled v6 plugin must be rebuilt. There is no
  API or ABI stability promise (`docs/V1.1.0.md:92`); D13 bumped to v6 for an additive change in
  the same way.
- Only outputs written with `--name-style hash` and `--prov-map` carry the chain. `write_blif`
  PLAIN, `write_json` and Verilog with short or provenance names get no chain, and
  `--prov-map` without hash names is an error.
- Records made from netlists (IMPORTED, restored locations) carry no AST chain; their chain stops
  at the record's own location. The map says so. A design read back from a version 2 map regains
  the records and the chain (decisions 7, 8); one read back from a version 1 map has none.
Forces on later work:
- Every new pass that clumps or decomposes must declare its class and levels at each operation.
- The post-Odin tool must keep the atom-name join with the map stable across BLIF name styles.

## Related
- D9 (provenance on every IR object): this record extends it. D9's "stable string IDs that survive
  serialization and appear in emitted names" stays; the IDs gain a chain and a construct table, and
  the emitted name stays the first-leaf name. `docs/IR.md` IR-12 and IR-13 are unchanged in
  fields; a section of IR.md gets the construct table and the op-class table (plan Tasks 2 and 3).
  D9 also says "AST is never discarded (spec 4.5)". That promise was already overtaken by AST-16
  (`docs/specs/2026-10-09-2A-ast-design.md:719`: ASTs are freed at the end of their read pass
  unless kept) and PHASE2 #7, and this record does not restore it. The construct table is the
  supported substitute: the part of the AST that records reference, kept with the design. This is
  the amendment to D9, stated here so Peter sees it.
- D13 (v1.1.0 scope): it added ABI v6 for the SV reader seam; V1.2.0 adds v7 on the same
  footing.
- D1 (granularity: word and bit views): the level vocabulary refines D1's tags upward (AST) and
  downward (LUT to site).
- `docs/specs/2026-10-20-5.4-hdl-locations-design.md` section 13 (H-1 to H-8, the hash name map).
- `docs/V1.1.1.md` (timing attribution) and `docs/V1.0.5.md` (core options for Loki III): the
  consumers.

Revisit if: the construct table or the extended map costs too much on the largest VTR designs
(memory over the design byte budget, read time up by a few percent, or a map over a few times
today's size), or Peter prefers the minimal construct-kind subset or the full AST, or VPR outputs
differ when only BLIF names change (the V1.2.0 check found no difference on three designs).
