# D4: Built-in simulator and equivalence checking

Status: Accepted
Date: 2026-10-08

## Context
The simulator must serve hard-block semantics and RE; equivalence checking is the regression
oracle (spec §2 rationale).

## Decision
Odin III provides both:
- a built-in netlist simulator, and
- equivalence checking: ABC `cec`/`dsec`, and Verilator on emitted Verilog.

Per spec §10: `simulate` is a cycle-based, event-free simulator over the netlist view using
op-registry semantics (hard blocks simulate via their registry function; VCD out); `equiv` runs
ABC `cec` (combinational) / `dsec` (sequential) between any two IRs or BLIFs, plus a Verilator
harness comparing emitted Verilog against source.

## Consequences
Positive:
- Simulation semantics live once, in the op registry (spec §5.2: C function pointer per cell
  type).
- Equivalence gives a regression oracle independent of the simulator.
Negative:
- Two verification mechanisms to maintain; every hard-block cell type needs simulation
  semantics.
Forces on later phases:
- Phase 0: `equiv-check` tool. PHASE0 §A.2 #8 adds a functional `multiply` hard-block model to
  `equiv-check`; memories wait for Phase 4. #7: latch init 2/3 treated as 0 with a notice,
  `--strict-init` refuses.
- Phase 1: simulator; exit test "sim matches ABC on goldens" (spec §12).
- Phase 2: micros equivalent to Parmys. Spec §11 round-trip and fuzz tests use `equiv`.

resolved by the registry function, or maintaining both becomes a cost the project cannot carry.
