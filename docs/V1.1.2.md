## 1. Current state (file:line, v1.1.1 main `0b90fff9`)

### 1.1 What a record holds

- A record has `kind` (SOURCE, IMPORTED, DERIVED), `run`, `op`, `locs`, `ast`, `hier`, `parents`
  (`src/ir/prov.h:120`). Records are immutable and hash-consed; SOURCE and IMPORTED identity is
  every field except `op`, DERIVED identity includes `run` and `op` (`src/ir/prov.h:80-86`,
  `docs/IR.md` IR-12, IR-13). Record IDs grow in creation order, so every parent is older than its
  child (`src/ir/prov.h:23-26`).
- The elaborator makes SOURCE records per AST node: wire to its declarator, cell to the expression
  that made it, `$proc` to its `ALWAYS`, each action, case and switch to its statement
  (`docs/specs/2026-10-11-2D-elaboration-design.md` section 10, EL-45; code
  `src/frontends/elab/elab2_wires.c:94` `prov_for`, `src/frontends/elab/pg.c:474` `pg_stmt_prov`,
  `src/frontends/elab/pg_always.c:648`). The record stores the node's own span, the node's ID in
  the elaborated store (`ast`) and `hier`.
- **SOURCE records are flat.** The record of `q <= d` inside `if (en)` inside `always` carries the
  span and `ast` of the assignment only; no parent edge reaches the record of the `if` or of the
  `always` (`src/frontends/elab/pg.c:479-480` makes each record from one node and one scope; SOURCE
  has no parents, `src/ir/prov.h:120-129`). The nesting lives only in the AST, reachable through
  `ast` and `odin3_ast_parent_index_build` (parent by span containment, `src/ast/ast.h:428`).
- `hier` holds the specialization name and **named** generate and block scopes only: an unnamed
  scope is skipped (`src/frontends/elab/elab2_wires.c:81`, `rec->name != 0`). So an unnamed `if` or
  `case` is not a level in `hier`; and `hier` is module-relative until `flatten` adds the instance
  path (`docs/IR.md` IR-12, `src/passes/flatten/prov.c:33-62`, `odin3_flatten_derive` at `:65`).
- Restored locations (`read_verilog -netlist`, `read_json`) make a SOURCE record with `ast` 0
  (`src/frontends/hdl_restore.c:42-43`); BLIF readers make IMPORTED records (structural only).

### 1.4 When the AST store is dropped (for the chain source)

`odin3_elab_run` calls `odin3_elab_stage2`, then `hand_over_elab`, which drops the elaborated store
unless the keep level keeps it (`src/frontends/verilog/elab1.c:554-555`, `:519-529`;

sets ELABORATED; the only pass with `wants_ast` is `write_verilog_ast`
(`src/passes/builtin.c:812-816`, `src/passes/manager.c:193-197`). The Python `Design` never sets

### 1.5 The exact gaps

1. **An unnamed `if` or `case` is not a level.** No SOURCE record points at its parent
   (1.1); `hier` skips unnamed scopes (`elab2_wires.c:81`); a `proc` mux points at the switch and
   case records but not at the `always` (`docs/specs/2026-10-11-2E-proc-design.md:898-906`).
2. **Only the first SOURCE leaf is printed.** Names, the map entry and the timing join use
   `locs[0]` of one leaf (`prov_name.c:9-27`); the others exist only via `--src-attr` (BLIF PLAIN),
   JSON `hdl`, Verilog `src`, capped at 8.
3. **Joins are not labelled.** Merge, CSE and ABC regions make multi-parent DERIVED records
   (1.2) but nothing says that distinct HDL constructs were blended, which pass blended them, or
   which constructs.
4. **ABC bulk fallback.** Over budget, one record covers the whole run and every new LUT carries
   it (`src/passes/abc/prov.h:66-75`): a LUT then has every cell of the run as an ancestor.
   Norns sees this as "its budget makes whole runs share one record"
   (`scripts/build_words.py:18`).
5. **No records after Odin III.** BLE, CLB and site are not in the IR or the BLIF; V1.1.1's
   attribution works at atom level only.
6. **Records and the AST layer are not exported.** Neither the chain, nor `hier` of a record, nor
   the run and op, nor the AST, reaches a file or the Python API; the AST is gone by write time.
7. **Netlist-derived records have no AST** (`hdl_restore.c:42-43`, IMPORTED).

## 2. Level vocabulary

One ordered list, coarse to fine. A level is the granularity of an object or a construct. The
names are exact and appear in the schema.

| Level | Kind of thing | Source of the node |
|---|---|---|
| `design` | the project | the run's design record |
| `module` | a module specialization | AST `MODULE` |
| `instance` | an instance of a module (flatten path) | AST `INSTANCE`, `INSTANTIATION`, `GATE_DECL`; flatten's instance record |
| `block` | a process, continuous assign or generate construct | AST `ALWAYS`, `INITIAL`, `CONT_ASSIGN`, `NET_ASSIGN`, `GENERATE`, `GEN_FOR`, `GEN_IF`, `GEN_CASE`, `GEN_BLOCK`, `FUNCTION_DECL`, `TASK_DECL` (the call site is a second location, EL-45) |
| `branch` | an if or case arm | AST `CASE_ITEM`; for `IF`, two synthesized arms `IF_THEN` and `IF_ELSE` with the span of the arm statement (the arm is not an AST node of its own); the `IF` and `CASE` nodes are the switch, `branch`'s parent |
| `stmt` | a statement or declaration | AST `BLOCKING_ASSIGN`, `NONBLOCKING_ASSIGN`, `FOR`, `WHILE`, `REPEAT`, `TASK_CALL`, `PROC_CONT_ASSIGN`, `DECLARATOR`, `PORT_DECL`, named `SEQ_BLOCK` (an unnamed `SEQ_BLOCK` is transparent) |
| `expr` | an expression that made a cell | AST `BINARY`, `UNARY`, `TERNARY`, `SELECT`, `CONCAT`, `CALL` (only those a record references) |
| `word` | a word-level cell | IR node, granularity `word` (IR-9) |
| `bit` | a single bit of a word, a flip-flop bit | IR net or bit slice of a word cell |
| `gate` | a bit-level cell (`$_AND_`, ...) | IR node, granularity `bit` |
| `lut` | a `$lut` cell | IR node of type `$lut` |
| `ble` | a basic logic element | VPR `.net` (Task 7) |
| `clb` | a cluster | VPR `.net` (Task 7) |
| `site` | a placed grid location and subtile | VPR `.place` (Task 7) |

Hard and black-box cells keep their IR-9 tag `hard` or `blackbox` as the level word at the
netlist rank of `word`, with the cell type in the record. The first seven levels are the AST
layer; `word` to `lut` are IR objects; the last three are appended after Odin III.

**Construct and construct chain.** A *construct* is an entry of the construct table (section 4):
an AST node of a level from `module` to `expr`, with its kind, level, span, name and parent
construct. The *construct chain* of a SOURCE record is its construct, then its parent, up to the
`module`. The chain of a netlist object is the union of the chains of its SOURCE leaves, kept as a
DAG (a LUT that blends two statements has two chains that meet at the `block` or `module`).

**Distinct construct (definition).** Two constructs `a` and `b` are *distinct* when neither is the
other or an ancestor of the other in the construct tree. A set of constructs is *reduced* by
removing every member that is an ancestor of another member. Two leaves with the same construct
but different instance paths are the same construct on *distinct instances* (flatten, 1.2).

## 3. Records, joins and the export schema

### 3.1 What a step records

At export, every DERIVED record is described by:

- `step`: the pass run (name, arguments, run number from the pass-run table) and the op number;
- `dir` (direction): `origin` (SOURCE or IMPORTED), `refine` (one parent, many pieces share the
  record: `proc`, `lower`, `unmap`), `rewrite` (one parent, 1:1: `opt`, `hardmap`, `lpmmap`,
  `dfflibmap`), `coarsen` (two or more parents of the same role: merge, CSE, `abc` regions, `raise`,
  `submod`), `context` (flatten's second parent is the instance record, which adds the instance
  level above and is not a join);
- `from` and `to` levels: from the pass registry (3.4) and the cell types of the parent and the
  object;
- `join` and `lossy` (3.3).

This needs no field in the IR record. Direction and levels are derived at export from the pass name
(the run table), the parent count and the object kind; the registry in 3.4 is a static table, one
row per pass that makes records. A pass that is missing from the table exports its records with
`dir` `unknown`, and the check in Task 2 fails if a registered pass has no row.

### 3.2 The schema, version 2

The map stays one TAB-separated UTF-8 file with LF lines, the escaping of version 1
(`%09 %0A %5C %25`, `%23` for a leading `#` of the first field,
`src/backends/common/name_map.h:1-12`), and the same name (`<netlist>.names`, or `--name-map`). It
is written only on request (3.5); without the request the file is version 1 and byte-identical to
today. Version 2 begins:

```
# odin3-names 2 hash=sha256 width=10 prov=1 ast=refs
```

`ast=` is `refs`, `constructs`, `full` or `none` (section 4). Every later line starts with a one
letter type, so a reader ignores a type it does not know (a located WARNING, as version 1 does for
a malformed line) and a version 1 reader refuses the file at the header (unknown version).

| Type | Fields (after the type letter) | Meaning |
|---|---|---|
| `O` | `module kind short full hier file line recs` | an object renamed by `hash` (version 1's seven fields, unchanged, plus `recs`: comma list of record IDs `r<n>`, the naming record first) |
| `N` | `module kind name recs` | an object that keeps its name (a port bit, a generator) and has records |
| `R` | `id kind level dir step parents origins cons flags` | one provenance record |
| `C` | `id kind level parent file span name` | one construct of the AST layer |
| `F` | `id path` | a file, once, referenced by `R` and `C` as `f<n>` |
| `T` | `id run pass args info` | a pass run, referenced by `R.step` as `t<n>.<op>` |
| `A` | `atom recs` | post-Odin: an atom (BLIF net name as VPR sees it) with its BLE, CLB and site records (Task 7) |

Fields of `R`:

- `id`: `r<n>`, numbered from 1 by a deterministic traversal (objects in the sorted order of the
  `O` and `N` lines, records breadth first, parents before children), so equal designs give equal
  bytes and the numbers do not depend on IR IDs.
- `kind`: `S` (SOURCE), `I` (IMPORTED), `D` (DERIVED).
- `level`: the level of the object the step made (section 2); for `S`, the level of its construct.
- `dir`: as 3.1.
- `step`: `t<n>.<op>`.
- `parents`: comma list of `r<n>`.
- `origins`: for `S` and `I`, the locations `f<n>:L.C-EL.EC`, `|` separated, at most 8 (the cap of
  `ODIN3_HDL_LOC_MAX`, with `capped` in `flags`), full spans, columns included.
- `cons`: for `S`, the construct `c<n>` (empty when `ast` is 0, or the leaf is restored or
  imported). For a `D` with a join, the reduced set of constructs the step blends (3.3).
- `flags`: comma list from `join`, `join=instance`, `lossy=bulk`, `lossy=cap`, `chain=span`,
  `capped`, `hier=<text>` (the record's `hier` string, escaped; a `D` or `S` with `hier` 0 has none).

Fields of `C`: `id` is `c<n>`; `kind` the AST kind (or `IF_THEN`, `IF_ELSE`); `level` as section 2;
`parent` the parent construct or empty for a `module`; `file` `f<n>`; `span` `L.C-EL.EC`; `name` the
construct's name where it has one (module, instance, block label, declarator).

### 3.3 Joins

A *step join* is a `coarsen` record. Let `fine(p)` be the reduced set of constructs of the SOURCE
leaves below parent record `p` (leaves with no construct count by their `file:line` span, flagged
`chain=span`). For a `coarsen` record `s` with parents `P`, let `J(s)` be the reduced union of
`fine(p)` over `p` in `P`. Then:

- `s` is a **join of distinct constructs** (`flags` has `join`) when `|J(s)| >= 2` and `J(s)` is
  not equal to `fine(p)` of any single parent `p`: the step itself blended constructs; a blend
  inherited from one parent is not a new join. `cons` lists `J(s)`, at most 16 entries, with the
  full count when more.
- `s` is a **join of instances** (`join=instance`) when `J(s)` has one construct but the leaves
  below have two or more instance paths (the same statement of two instances of one module).
- Two bits of one statement, or a statement and its own condition (same `block`, one reduced
  construct), are not a join. Refine, rewrite and context records are never joins.
- **Bulk joins are lossy.** The ABC over-budget record, and any record whose `parents` exceed the
  cap of 16 distinct constructs after reduction, is flagged `lossy=bulk` (the pass that made it
  has already said so: `odin3_abc_coarse_record`, `src/passes/abc/prov.h:73-75`). `cons` then lists
  the first 16 constructs in construct-ID order and the total count is exported as
  `flags` `n=<total>`.

The pack and place records of Task 7 use the same rule: a `clb` record whose BLE records have
distinct constructs is a join labelled by the `pack` step.

### 3.4 The pass registry (levels per step)

One row per pass that makes records: `read_verilog` and the slang reader (origin, levels from
the construct kind), `proc` (`stmt`/`branch` to `word`, refine), `flatten` (context, `instance`),
`lower` (`word` to `gate`, refine), `opt` (`gate`/`word` to the same level: rewrite; merge, CSE,
FF merge: coarsen), `wreduce` (rewrite), `abc` (`gate` to `lut`, coarsen), `hardmap`, `lpmmap`,
`dfflibmap` (rewrite, `word`/`gate` to `hard`), `unmap` (refine, `hard` to `word`), `raise`
(coarsen, `gate` to `word`), `submod` (rewrite), `fsm` (rewrite, state register), `read_blif`
(origin, I), `pack` and `place` (Task 7, coarsen, `lut` to `ble` to `clb`, rewrite to `site`).
It lives in `src/backends/common/prov_levels.c` (Task 2) with a test that walks the pass registry
and fails on a pass that calls `odin3_prov_derive` without a row.

### 3.5 Export options

On `write_blif --vtr`, `write_json` and `write_verilog`, with `--name-style hash`:
`--prov-map [refs|constructs|full]` makes the map version 2 with that AST layer; without it the
map is version 1 as today. `odin3-flow` passes it with `--timing-attr` or a new `--prov`. The
names an output file carries are unchanged (the hash name is a function of the first-leaf full
name only, `docs/specs/2026-10-20-5.4-hdl-locations-design.md` H-2, so BLIF bytes do not change).
`names --map F --lookup SHORT` prints the `O` line, then each of its records and its construct
chain, indented; `--chain SHORT` prints the chain only; `names --check` verifies the version 2
invariants (every `r`, `c`, `f` and `t` reference resolves, parents before children, the hash of
every `O`, no cycle). Python: `Node.provenance()`, `Net.provenance()` returning the record graph
(Task 6), and `odin3.read_name_map(path)`.

## 4. The AST layer: how the chain is obtained

Peter: the AST and the netlist are both provenance. So the AST layer is not a lookup at write time
that may fail; it is held by the design and exported. Three forms, one schema (`C` lines):

- **refs (recommended).** A design-held *construct table*: the AST nodes that any SOURCE record of
  the run references, plus all their ancestors up to the `module`, with kind, level, span, name and
  parent. Built once, when elaboration ends (`odin3_elab_stage2` success), from the elaborated
  store while it is still alive, whatever `--keep-ast` says.
- **constructs (minimal alternative).** The same table restricted to nodes whose kind is a
  construct kind (levels `module` to `stmt`, section 2): no `expr` level; a record that references
  an expression resolves to its nearest construct ancestor.
- **full (dearer alternative).** Every node of the elaborated store (all 68 kinds), parent, span,
  name. For a consumer that wants expression trees; not needed for the chain.

### 4.1 Evidence for choosing a held table over "the AST at write time" (option A)

Option A reads the held AST store when a writer runs. It fails the requirement in four checked
ways: (1) the store is dropped at the end of the read unless `--keep-ast` (1.4), and neither the
Python API, nor `odin3-flow`, nor the CLI default keeps it; (2) the ABI does not expose the
`ast` field, so a Python consumer could not resolve it even if the store were held (1.3); (3) a
design read back from BLIF or JSON never had the store; (4) the construct chain must survive the
file (the map). Making every flow keep the AST costs about 41 bytes per node
(`docs/specs/2026-10-11-2D-elaboration-design.md` section 11, `ODIN3_ELAB_MAX_ELAB_NODES`) plus the
parent index, held for the whole run, to export a subset at the end. Option A stays valid as a
fallback: a writer that finds the elaborated store held may export from it (`ast=full`).

The table is the compact, persisted form of exactly what option A reads, built early.

### 4.2 Option B as originally framed (a construct reference in the record)

Adding a construct index field to `odin3_prov_record` would put the construct in the
hash-consing identity of every SOURCE record and change a struct that IR-12 and the check rule 7
test. Rejected: the record already has `ast`; the table resolves it. The recommended form keeps the
record unchanged.

### 4.3 The IR and ABI change (recommended form), named exactly

All additive; no field of `odin3_prov_record`, `odin3_srcloc`, node, net, wire or pin changes; no
ID, no attribute, no op-registry entry changes; the hash-consing identity is unchanged (`ast`
already is part of a SOURCE record's identity, `docs/IR.md` IR-13).

1. `src/ir/construct.h` and `construct.c` (new): `odin3_construct_table`, a design-global store of
   rows `{ run, ast, level(u8), kind(u8), parent (row index + 1, 0 none), file (strtab ID), line,
   col, end_line, end_col, name (strtab ID) }`, 40 bytes a row, a `u64map` from `(run << 32 | ast)`
   to the row, rows appended parents first. Functions `odin3_construct_snapshot(design, run, ast,
   mode)`, `odin3_construct_find(design, run, ast)`, `odin3_construct_get(design, index)`,
   `odin3_construct_end(design)`, `odin3_construct_bytes_reserved(design)`.
2. `src/ir/ir_internal.h` (the `odin3_design` struct near `asts` at `:124`) gets one pointer
   `construct`; `src/ir/design.c` creates it, frees it, copies it in `odin3_design_copy`
   (`design.c:69`, as `keep_ast` is) and `odin3_design_bytes_reserved` includes it (the shared byte
   budget, `src/passes/budget.h`).
3. `src/frontends/elab/elab2.c:893` `odin3_elab_stage2`: on success, after the IR is built and
   before the caller's `hand_over_elab`, call `odin3_construct_snapshot`. The snapshot marks every
   `ast` that a SOURCE record of the run references (a sweep of the design's records with
   `run == this run`, `src/ir/prov.h` `odin3_prov_end`/`odin3_prov_get`), then adds ancestors from
   `odin3_ast_parent_index_build` (`src/ast/ast.h:428`), skipping transparent kinds, and synthesizes
   `IF_THEN` and `IF_ELSE` arms. Both `read_verilog` and `odin3_ast_elaborate` (`src/api/elab_abi.c:79`,
   the slang shim) reach this function.
4. Public ABI v7 (`ODIN3_ABI_VERSION` 6 to 7, `include/odin3/odin3.h:58`), additive: type
   `odin3_construct`, and `odin3_design_construct_count`, `odin3_design_get_construct`,
   `odin3_obj_get_prov` (object to record ID), `odin3_prov_get_record` (record ID to kind, run, op,
   hier, ast, parents, locations), `odin3_prov_construct_of` (record to construct index, or 0),
   and `odin3_prov_visit_chain(design, obj, visit, user)` visiting the object's chain. `odin3_source`
   and `odin3_prov_visit_sources` stay as they are (Loki's tests that pin them stay valid).
   Exact signatures are in the Task 3 spec for Peter's review.
5. `docs/IR.md`: a new IR-12a states the construct table; IR-12's `ast` row says "resolved in the
   held store, else in the construct table". `docs/DESIGN.md` 5.3 and `docs/ADR/D9.md` get a
   pointer to D14.
6. `check` gets rule 12 (construct table): every row's `parent` index is smaller than its own, its
   `run` is a run of the design, and no row repeats a `(run, ast)` key.

The `constructs` and `full` forms differ only in which rows `odin3_construct_snapshot` keeps
(`mode`), so the choice is a parameter, not a different design. For `full`, a flag
`--prov-ast full` on the read pass would keep the whole store in the table (not recommended as
default).

### 4.4 What the chain cannot give

Records with no `ast` (restored locations, IMPORTED) have no construct; their `cons` is empty and
`flags` carries `chain=span`. Objects of a design read from BLIF have `I` records and no chain at
all; that is stated in the map and not guessed. An unrolled loop's iterations share their body's
records (EL-45), so the construct of an iteration is the loop body, with the loop index only in
`hier` when the scope is named.

## 5. Size

### 5.1 Bounds

- Records are hash-consed, so a record is written once however many objects carry it; `O` and `N`
  lines carry only the record IDs. Records written are the records reachable from the objects
  written (not the whole store).
- Construct rows are written once, only for constructs a written record references (`refs`), their
  ancestors included.
- Joins list at most 16 constructs; the ABC budget bounds DERIVED edges by
  `16 x (old cells + new objects) + 65,536` per run (`docs/IR.md` "Provenance across ABC").
- In memory: the construct table is 40 bytes a row.

### 5.2 Measured counts and estimate

Measured in this lane (release build of main `0b90fff9`, read-only run of `odin3` and the Python
binding on committed designs; throwaway scripts under `/tmp/claude-1000/op-prov`, not committed):

| Design (flow) | Today: map entries / map bytes | IR objects after lower (nodes, nets, wires) | Distinct source-location sets at elaboration | AST nodes (all / construct kinds) |
|---|---|---|---|---|
| `bm_DL_BCD_adder` (`proc; opt; flatten; lower`) | 357 / 87,124 | 129, 159, 6 | 28 | 63 / 19 |
| `bm_if_reset` (same) | 7 / 1,598 | 18, 18, 8 | 37 | 113 / 47 |
| `ch_intrinsics_nolatches` (VTR flow to `abc --lut 6`, default top `memset`) | 159 / 43,494 (BLIF 23,067 B vs 20,518 B with short names) | 173 LUT, 82 FF after `abc` | 82 | not measured (301 source lines) |
| `sha` (VTR design, elaboration only) | not measured (Norns reports 2,506 blocks) | not measured | not measured | 5,439 / 1,893 |

"Distinct source-location sets" is the number of different sorted lists of leaf spans that the
objects' `odin3_prov_visit_sources` gives at that stage; it is a lower bound on the number of
distinct records, and for SOURCE records an estimate of how many AST nodes are referenced. The
record count itself is not exposed by the ABI (1.3), so the estimate for the extended map is built
from the pass structure: `R` = SOURCE records (about the sets above) + one DERIVED per `proc`
process or switch + one per lowered word cell + one per opt class merged + one per `abc` anchor
(about LUTs plus flip-flops).

Row sizes: an `R` line about 100 bytes, a `C` line about 70 (a span, a name, ids), an `O` line
gains about 8 bytes per record ID; a `F` and `T` line are a few per run.

| Design | `R` rows (estimate) | `C` rows (estimate) | Added to the map | Map after |
|---|---|---|---|---|
| `bm_DL_BCD_adder` | about 28 + 14 + 6 = 48, or 4.8 KB | at most 63 (all nodes), 4.4 KB | +12 KB with 357 record references | about 99 KB (+14%) |
| `bm_if_reset` | about 37 + 12 + 10 = 59, or 5.9 KB | at most 113, 7.9 KB | +14 KB | about 15.6 KB (tiny map, large ratio) |
| `ch_intrinsics_nolatches` | about 82 + 68 + 68 + 255 = 473, or 47 KB | about 750 AST nodes (2.5 per source line, from `sha`) of which `refs` about 45%, or 24 KB | +72 KB | about 115 KB (2.6x) |
| `sha`-scale (2,506 blocks) | up to 7,500, or 750 KB | `refs` about 2,500, 175 KB; `full` 5,439, 380 KB | +0.93 MB | about 1.6 MB (map today about 0.7 MB at 280 B per entry) |

For the two ends of the range that matter: in memory the table is 40 bytes a row, so `sha` is
about 100 KB for `refs` and 218 KB for `full`; a 200,000-node design (`mcml`, estimate in
`docs/specs/2026-10-09-2A-ast-design.md:840-843`) is 3.2 MB for `refs` (40% of nodes) against
8 MB for `full`, nothing against the 2 GB target. The estimate method for `refs`: the share
referenced is taken from `bm_if_reset` (37 referenced sets of 113 nodes, one third, 45% with
ancestors). These are estimates; Task 5 replaces them by measurements (`names --check` prints the
counts) and the PR reports them.

## 6. Steps after Odin III

A tool, `tools/flow/prov_post.py` (standard library only, next to `timing_attr.py`, installed by
the same `CMakeLists.txt`, `pyproject.toml` and `plugins/python/entry.py` rows as V1.1.1), command
`odin3-prov-post FLOW_DIR`. It reads:

- the BLIF VPR read (short or hash names) and its map (`<blif>.names`, version 2);
- VPR's packed netlist `.net` (XML; block tree with the primitive, BLE, CLB nesting and the atom
  name of each primitive) and `.place` (block, x, y, subtile).

It appends to the map, in the same file and schema: `R` lines of level `ble` and `clb`
(`dir=coarsen`, `step` `t<n>.0` a new `T` row `pack`, parents = the records of the atoms inside),
`R` lines of level `site` (`dir=rewrite`, parent the CLB, the `.place` coordinates in `flags`),
and `A` lines keyed by atom name. Joins use section 3.3 unchanged: a CLB whose atoms blend
distinct constructs is labelled a join by `pack`. The map is rewritten atomically
(`odin3_atomic_file`-style: temporary file then rename; in Python `os.replace`).

**Atom name join.** VPR names a block after the net its first output drives and an I/O pad after
its port (`docs/V1.1.1.md` Join). With `--name-style hash` those names are the hash names written
in the BLIF; the `O` lines of the map are keyed by the same short names, so the join is exact and
needs no second BLIF. A BLIF written with short names has no map keyed by them, so the tool
refuses it (the V1.1.1 route with two BLIFs stays for that case).

**Are VPR outputs identical when only BLIF names change?** Not assumed. VPR may order or
tie-break by name (packing, placement seeds are not names but net ordering can be). The plan has a
report-only check, as V1.1.1 had: in Task 7 an evidence script runs VPR twice on the same
design, the same seed and the same architecture, once on the short-name BLIF and once on the
hash-name BLIF, and compares the packed block counts, the critical path delay and the wirelength;
differences are reported, not hidden, and decide whether `odin3-flow --prov` uses hash names for
the VPR run or writes a second, VPR-only BLIF. Odin III never runs VPR in this lane; the check is
for the controller's heavy-run when lanes are idle (`work/controller-scripts` rules).

The tool is the only writer of `ble`, `clb` and `site` records; VPR is unchanged.

## 7. Consumers (read-only study; no consumer code in this lane)

### 7.1 Loki (how it labels cells from provenance today)

Loki (`loki/` repo, Python, imports `odin3`) labels final cells by a **span join**:

- A word-level snapshot is taken after `proc; opt; flatten; ...` but before `lower`
  (`loki/snapshot.py:39-62`), one `WordCell` per live word node with `spans=node_spans(node)`, where
  `node_spans` is `node.sources()` (`loki/snapshot.py:20-21`), i.e. `odin3_prov_visit_sources`
  (`plugins/python/odin3.py:650`): file, line, column, end line, end column.
- Final cells (LUTs, flip-flops, gates) get the same `spans` from the final design
  (`loki/extract.py:51`).
- `match_words` (`loki/labels.py:41`) says a word cell W matches a final cell c when `set(W.spans)`
  is a non-empty subset of `set(c.spans)`, sorted by span count then ID. `_cell_label`
  (`loki/labels.py:161`) groups matches with equal (spans, type) (`_groups`, `:75`), sets
  `construct_types` (distinct types joined by `|`), `construct_type` (`_primary`, `:147`),
  `n_construct_cells`, `ambiguous` (identical spans cannot be told apart), and the role.
- The module path cannot come from the record. Flatten keeps the instance path in the record's
  `hier` (`src/passes/flatten/prov.c:33-62`), but the ABI does not return `hier`, and a cell lists
  only the innermost instantiation span. `module_path` (`loki/labels.py:83`) therefore climbs
  from the innermost site to the top through the module hierarchy it recorded before `flatten`
  (`take_instances`, `loki/snapshot.py:65`) and writes `top/*` when a module has several parents
  (the open question in `docs/specs/2026-10-21-l0-dataset-design.md:124-129`).
- The spec (`docs/specs/2026-10-21-l0-dataset-design.md:102-151`) states what the labels rest on:
  `sources()` "is the only provenance the ABI exposes" (`:108-111`); a LUT lists all spans of its
  cone (`:150-151`, section 5.3); a LUT that merges several constructs lists all of them and "a LUT
  is not split".

What D14 changes for Loki, concretely:

1. **The join becomes a walk.** With records and the chain exposed (Task 3 and 6), a final cell's
   construct is read from its record ancestry, not by span-subset matching: the identical-span
   ambiguity (`ambiguous`) disappears because two instances of one module have different `hier`
   and records, and two statements on one line have different `ast` constructs.
2. **`module_path` is exact** from the flatten records' `hier` and the instance chain (the `*`
   guess goes away), including nested instances.
3. **New label columns** become possible from the chain: `block` (always, assign, generate),
   `branch` (the if or case arm), `stmt`, `expr` kind and span, `join_of` (the constructs a LUT
   blends, from section 3.3) and `n_constructs`. `LABEL_COLUMNS` (`loki/schemas.py:21`) is a Loki
   schema change in its own lane; the existing columns keep their meaning.
4. **L15 loss audit** (`work/controller-scripts/ROUND4-PLAN.md`, Loki r5: "construct at file:line
   lost at pass P because merged with Q") needs exactly the registry of 3.4 plus the join label:
   the first `coarsen` record in a construct's descendants that has `join` and names the construct
   in `cons` is "lost at step P" (pass, run, op), "joined with Q" is the other members of `cons`.
   Today this has to be reconstructed from pass-by-pass snapshots of spans; with the map it is a
   lookup per construct, and the snapshots become a check.
5. **From-BLIF designs** (`docs/specs/2026-10-21-from-blif-design.md`) that arrive with a version 2
   map get labels without the Odin III Verilog flow.

Loki's stated facts (`docs/specs/2026-10-21-l0-dataset-design.md` section 5.1, re-checked by
its tests) stay true: `Node.sources()` and `odin3_prov_visit_sources` do not change (Task 3).
Loki keeps its span join as the fallback for designs without a map (BLIF only, no Odin III
provenance) and for the `chain=span` records of 4.4.

### 7.2 Timing attribution (`tools/flow/timing_attr.py`, V1.1.1)

Today the flow writes a second BLIF with `--name-style provenance`
(`tools/flow/odin3_flow.py:403-410`) and the tool pairs it with the short BLIF line by line and
token by token (`build_name_map`, `tools/flow/timing_attr.py:119-143`), reads the name with a regex
(`_PROV`, `:40`, `record_name`, `:146`), and takes one `file:line` per net. Its two core gaps
(`docs/user/timing-attribution.md` "Limits"): line-level spans and no word for generated nets.
With a version 2 map keyed by the BLIF's own names: the second BLIF and the positional join go
(the join is by atom name, `A` and `O` lines); the span is the full `L.C-EL.EC` of the leaf; the
chain gives block, branch and statement for the report ("the `else` arm of the `if (en)` in the
`always` at line 40"); generated nets carry the word of their `DECLARATOR` ancestor when the chain
has one. The JSON `word_via` heuristics become a fallback. `schema_version` of
`attribution.json` stays 1 if only fields are added.

### 7.3 Norns

`scripts/nornlib.py:100-112` parses the provenance name with a regex into module path, leaf, file
and line; `scripts/build_words.py:1-40` reruns the whole Odin III script to read, from the
Python session, "the finer data" the BLIF name lacks (an `always` block is one line, `sha`'s
holds 1739 of its 2506 blocks). With the map the word and the block of every block come from the
file: no rerun. The N17 packing census (`ROUND4-PLAN.md`: "classify every CLB member by
provenance and netlist ... series, shared-input, orthogonal, filler") gets the CLB record of
Task 7: a CLB that is a join of distinct constructs is a census row with the constructs named,
instead of a classification rebuilt from netlist structure.

### 7.4 Wyrd

The view reads `attribution.json` (V1.1.1) and, with this change, the map: a tree of
design, module, block, branch, statement with the delay and the number of blocks each carries,
and the "joined with" list at a LUT or CLB. The tree comes from the `C` lines, the weights from
the `A` and `O` lines. No Wyrd change in this lane.

## 8. Compatibility

- `--name-style short|provenance|hash` unchanged. Without `--prov-map`, `hash` writes the map
  version 1 byte-identical to today; the netlist files are byte-identical in every mode (the hash
  name depends only on the first-leaf full name, H-2).
- `read_blif --name-map` and `read_json --name-map` read version 1 as now; they accept version 2
  and use only the `O` lines (ignoring other types with one WARNING per type). A version 1-only
  build refuses a version 2 file at the header; this is why version 2 is opt-in.
- `names --lookup/--reverse/--check` accept both versions; version 1 output is unchanged.
- Goldens: none changes. The goldens are BLIF, logs and `.prov` produced without the new option
  (`CLAUDE.md` rule 9); the new code runs only on request, the construct table is not written to
  any existing output, and `dump_locs` is untouched. Task 4 adds a test that runs the whole micro
  set before and after and compares every writer output byte for byte.
- ABI version 6 to 7, additive (the precedent is v1.0.3's S1 simulation API, ABI v5, shipped as
  a patch doc). No struct of ABI v6 changes; a v6 plugin loads with the host's check.
- `schema_version`: the map's header version is the schema version (2); each later additive
  field gets a new trailing field, and readers must tolerate unknown trailing fields on `R` and `C`
  lines.
- Memory: the construct table adds 40 bytes per row to every `read_verilog` run, counted in the
  design byte budget (`src/passes/budget.h`). On a design near the budget `odin3_construct_snapshot`
  falls back to `constructs` mode and warns once (agent default V112-8).
