Verilog Synthesis for FPGAs - again\\Built by the DarkFactory and Leads to Yggdrasil~III}

\maketitle

\begin{abstract}
I wrote Odin in 2005 and Odin~II in 2010. Odin~II became the Verilog front end of the VTR FPGA CAD flow, and Yosys with the Parmys plugin has since displaced it. After the ``MAIking software'' moment of December 2025, when AI coding agents began to make real software, I asked the final-frontier question: could a Dark Factory, in which agents turn a human's specification into software, build Odin~III, matching Odin~II's good ideas and plugging into the VTR flow? Odin~III (MIT license) is a C17 framework with one provenance-tracked IR, two-stage elaboration, re-implementations of Yosys~0.55's \code{proc}, \code{opt}, \code{fsm}, \code{wreduce} and \code{flatten}, architecture-driven partial mapping, linked ABC and VPR-ready BLIF, a SystemVerilog front end over the slang library, and a versioned C ABI for plugins and AI tools. Each claim of the paper is a hypothesis with an experiment that confirms it or not. Possibly good: every netlist Odin~III produced for the 15 VTR benchmarks that fit the development laptop routes in VPR, with geomean CLB, channel-width, delay and wirelength ratios against the Parmys flow inside a 1.20 gate, but two designs differ from Parmys in multiplier count and five lose adders, which the gate's equal-or-explained rule does not allow. Confirmed: refinement proofs, functional checks and byte-identical reruns hold; checking against oracles found defects in the Parmys flow; and, when enabled (\code{--prov-ast}, off by default on the command line), provenance records the chain of HDL constructs behind every object. Not confirmed: recording constructs at elaboration costs more than 5\% of read time on two of five large designs (by 1.8 and 2.7\,ms of 34 and 39\,ms), so it is off by default; equivalence on the 14 small VTR designs is only partly proved. The C ABI is stated, not tested. Power is not measured. I state the caveats of this MAIking: a human watched every day, the code has not been deeply read by a human, and testing covers a subset of scenarios. I report the time and token cost, and present the Yggdrasil III ecosystem that this approach made possible.
\end{abstract}

\section{Introduction}
\label{sec:intro}

% Plain-English problem. Each term is defined where it is first used (tag def:<key>), in the order
% of glossary.tex (make_glossary.py); Sec. Background repeats them with the source of the definition.
\emph{The problem in plain English.}
An FPGA is a chip of programmable logic blocks and wires onto which a digital design is loaded~\cite{jamiesonthesis}. % def:fpga
Its storage cell is the flip-flop, which keeps one bit between clock edges, % def:ff
and its logic cell is the LUT (look-up table), a small memory that computes any function of six inputs and, with a flip-flop, forms the basic logic element~\cite{jamiesonthesis}. % def:lut
LUTs and flip-flops are grouped into CLBs (configurable logic blocks), which are placed as one unit~\cite{jamiesonthesis,luuthesis}. % def:clb
A designer describes the circuit in a hardware description language (HDL), here Verilog, % def:hdl
and a tool turns that text into a netlist, the list of gates, LUTs and other cells and the wires between them~\cite{jamiesonthesis}. % def:netlist
The tool that does the first part of this job is the synthesis front end. % def:front
Its first step, elaboration, resolves parameters, generate loops and hierarchy and turns the parsed HDL into a design graph~\cite{jamiesonthesis}. % def:elab
ABC then maps the gates of the netlist onto LUTs~\cite{brayton2010abc}. % def:abc
After that, packing groups the LUTs and flip-flops into CLBs, placement chooses a site on the chip for each CLB, and routing chooses the wires between them~\cite{jamiesonthesis}. % def:prp
The open-source flow that does all of this is VTR (Verilog-to-Routing), and VPR is its packing, placement and routing program~\cite{rose2012vtr,luuthesis}. % def:vtr
A front end that gives VTR good results is not enough for the research I want to do. % why
Synthesis changes the designer's structure: it flattens hierarchy, merges and splits operators, and covers logic with LUTs that no source line names. % why2
The link from each object of the final netlist back to the HDL that produced it is its provenance, % def:prov
and no front end that serves VTR keeps it.

\emph{Why Odin~III.}
Odin~\cite{jamieson2005odin} started from nothing. I used Icarus Verilog~\cite{icarus} as the front end, but Icarus treats Verilog as a simulation language, and building synthesis on a simulator's front end misled me and cost a young engineer a year of work to learn the basics of Verilog synthesis. I wrote Odin~II~\cite{jamieson2011odin2} in my extra time during my post-doc at Imperial College, while my future wife was out of the country, and there I learned to write a proper compiler front end: a Bison and Flex parser, and elaboration into a flattened netlist. Odin~II became the Verilog front end of the VTR flow~\cite{rose2012vtr,luu2014vtr7}, and it mapped multipliers, memories, and adders onto the dedicated blocks that an architecture file describes. VTR has since moved its default front end to Parmys~\cite{parmys}, an extension of Yosys~\cite{wolf2013yosys,yosys} that carries Odin~II's mapping of multipliers, memories and adders onto dedicated blocks, and the VTR documentation marks Odin~II as deprecated~\cite{vtrodindoc}. % def:odin2

Then came what I call the ``MAIking software'' moment of December 2025: AI coding agents~\cite{claudecode} became able to make real software. Yu and Ren's multi-agent self-evolved ABC~\cite{yu2026selfevolvedabc} showed that LLM agents can change the source of a million-line logic synthesis system, rebuild it, check it, and keep the changes that improve its results; VPR-Evolve~\cite{wu2026vprevolve} has since done the same for FPGA place and route, and Ding et al.\ survey high-level synthesis in the agentic era~\cite{ding2026hlsagentic}. Those works build on existing tools, and together they raised the final-frontier question I had to ask. Dan Shapiro describes five levels of AI-assisted programming; at the last, the Dark Factory, the software process is ``a black box that turns specs into software''~\cite{shapiro2026darkfactory}. % def:dark
Could I use a Dark Factory to build Odin~III, a front end that matches Odin~II's good ideas and plugs into the VTR flow where Yosys has displaced Odin~II? This paper describes the answer to that question (YES!), what has been built to answer it, and how it is tested. Odin~III is public at \url{https://github.com/drpaj12/odin3}.

\emph{What counts as a good result.}
A front end is judged on several measures at once, and the dataset I want from it must carry all of them.
The routing channel width is the number of wire tracks per channel that the router needs, written $W$; % def:minw
the wirelength is the total length of wire the routed design uses; % def:wl
the critical path is the slowest path between registers, and its delay is the critical-path delay (CPD); % def:cpd
a near-critical path is one whose delay is within a stated window of the CPD. % def:near
Area is how much chip a design uses: its LUTs, its CLBs and $W$, and a good result keeps it low. % def:area
Speed is how fast the circuit runs: the CPD and the wirelength, and where available the near-critical paths, and a good result keeps it high, on the critical and on the near-critical paths alike. % def:speed
Power is the energy the circuit uses, and a good result keeps it low; this paper does not measure power. % def:power
The reason for the provenance link is the Mimir~III dataset (Fig.~\ref{fig:yggdrasil}): a record that shows \emph{why} each structure was placed where it was, through the HDL construct it came from, for all of these measures at once.

\emph{Claims and experiments.}
Each claim in this paper is a hypothesis, a statement that an experiment can confirm or fail to confirm. % def:hyp
The experiment gives a verdict: USEFUL (confirmed under the stated gate or check), POSSIBLY GOOD (confirmed but narrow or fragile, so stated with the fragility and never as proof alone), INCONCLUSIVE (neither confirmed nor failed), or DISMISSED (failed). Sec.~\ref{sec:results} gives each confirmed hypothesis its experiment. A failed one is a line in the research log (Appendix~A) and the Discussion.

\emph{The innovations in plain English.}
\begin{enumerate}
\item \textbf{A front end that plugs into VTR.} A program that reads Verilog and hands a netlist to VTR, so ABC, packing, placement and routing work as before and the result is about as good as with the Yosys-based front end, comparable and not equal.
\item \textbf{Checking against oracles.} Every stage is compared with a trusted reference tool, an oracle, % def:oracle
and where the two disagree a probe decides which one matches the Verilog, so the reference's own mistakes surface.
\item \textbf{One provenance-tracked IR.} Every object remembers which Verilog text made it, through every pass, in one internal design graph, the IR (intermediate representation), % def:ir
and from v1.2.0 it remembers the whole chain of constructs, including the places where two constructs were blended.
\item \textbf{A versioned C ABI.} A stable interface (the ABI) so a plugin, a separately built program that adds features, and AI tools can drive and read Odin~III without changing it. % def:abi
\end{enumerate}
The way Odin~III was built, with a Dark Factory, is the method and context of the paper and not a tested innovation (Sec.~\ref{sec:method-built}).

\emph{Contributions.} The contributions are the innovations with the hypotheses that confirmed them:
\begin{itemize}
\item the front end and its flow: all 15 designs that fit the laptop route, with average ratios inside a stated bound against Parmys, but two designs differ from Parmys in multiplier count and five lose adders (O1, POSSIBLY GOOD), on a baseline that reproduces VTR's own results (O2, USEFUL; Sec.~\ref{sec:q-qor});
\item checking against oracles: a proof that the lowering pass keeps the design's behaviour, with no unexpected result (O4, USEFUL), a functional check that passes on 12 of 15 designs (O6, USEFUL), identical output on rerun (O7, USEFUL), 144 of 156 VerilogEval references run through the gate flow (O8, USEFUL), and six defects found in the Parmys flow (O9, USEFUL; Secs.~\ref{sec:q-proof} to \ref{sec:parmys-bugs});
\item provenance: the chain of constructs and the joins recorded correctly at every granularity, with every writer's output unchanged (O14, USEFUL); the read back of the exports is only partly shown (O15, INCONCLUSIVE), and a timing attribution that does not change VPR's result (O17, POSSIBLY GOOD, on three designs); the cost of recording constructs at elaboration failed its gate (O16, DISMISSED; Secs.~\ref{sec:q-prov} to \ref{sec:q-timing});
\item an account of the build with a Dark Factory under daily human oversight, with its time and token cost and its limits (Sec.~\ref{sec:method-built});
\item a presentation of Yggdrasil~III, the suite this approach made possible, including a reimplementation of our earlier verilogTown \cite{verilogTown}, now called Midgard, to fit the Norse theme.
\end{itemize}

The approach has limits, and I state them first. It was not a lights-out factory. I watched the agents build and interacted with them daily: I wrote the design specification and goals, ruled on every design rule (architecture decisions, IR invariants, mapping algorithms), and managed the risks of a small machine. Everything ran on one Windows desktop (Intel i7-13700) inside a WSL2 virtual machine with 12 logical processors and 23\, GiB of memory, where an out-of-memory condition or a full host disk kills the virtual machine and every agent in it. Heavy jobs therefore run one at a time under a machine-wide lock in a memory-capped slice, and the largest VTR designs were shipped out to a bigger machine instead of being run. The codebase has not been deeply read by a human. It took 14 calendar days to reach version~1.0 (first commit 2026-10-08, v1.0.0 released 2026-10-21, both days counted) and was tested with a subset of the possible scenarios. Odin~II and Yosys with Parmys are production oracles, so more testing is always possible. We found defects in the Parmys flow (Sec.~\ref{sec:parmys-bugs}), which we will report to those projects in good faith, because we want to contribute to these open-source CAD tools.

The community may object to such a process. It may also ask a harder question: if a guided Dark Factory with oracles can rebuild a tool like this, could a reverse-engineering process let open-source tools rip out the human-years of engineering behind today's EDA tool landscape? (To the companies, I would suggest moving to a cloud service model as soon as possible.) My goal is narrower: to run experiments I couldn't do with Yosys, and with Odin~III I can now, and the ideas I hoped my students could pursue were limited by inflexibilities in the toolflow.

I call this new suite Yggdrasil~III, the world tree (Fig.~\ref{fig:yggdrasil}). Odin~III is the trunk: its steps run from the roots (Verilog and netlists in) to the crown (a netlist for VTR out), and every path passes through its one provenance IR, which is why I see it as the final frontier of the Odin line (at least for me). The oracles (Yosys, Parmys, Odin~II, VTR's stored results, and ABC) stand as a small forest beside the trunk, to compare against. Three deep roots reach three wells (Mimisbrunnr, Urdarbrunnr and Hvergelmir) of outside work: prior work, FPGA CAD and its views, and synthesis sources. In the canopy are Wyrd~III (the experiment runner and GUI); Bifrost~III (the simulation bridge); and Midgard~III, a port of my verilogTown Verilog teaching game~\cite{verilogtown2017}, which Wyrd~III connects to. M\'{\i}mir~III, the circuit knowledge base, hangs there as the fruit: the dataset harvested from the runs, which answers why things are where they are, through provenance. Side branches carry tools and experiments: Loki~III (reverse engineering) continues the netlist-to-RTL work of Faruque et al.~\cite{faruque2025gatebreaker} with an LLM-free L0-L2 flow (provenance datasets, a Bayesian signal-role classifier, clustering and graph-network reconstruction), now measured against the baseline's own metrics; Leman~Russ~III (hardware Trojan detection tools); The Norns~III, the placement experiment of Gharibian et al.~\cite{gharibian2010finding,gharibian2013analyzing}, redone with provenance (Sec.~\ref{sec:provenance-problem}); and Verdandi~III (the Micro through the Macro), a record-and-replay walk of an Odin~III run. All the code is available at \url{https://github.com/drpaj12/YggdrasilIII}.

\subsection{Two open-source models of Verilog synthesis}

\emph{The Odin~II flow.} Odin~II~\cite{jamieson2011odin2} parses Verilog with Bison and Flex into an abstract syntax tree (AST); passes over the AST and the module hierarchy turn it into one flattened netlist of nodes, pins, and nets. It reads the VPR architecture file to decide which multipliers, adders, and memories become dedicated blocks, writes the rest as BLIF for ABC~\cite{brayton2010abc} to map to LUTs, and includes a netlist simulator.

\emph{The Yosys approach.} Yosys~\cite{wolf2013yosys} parses Verilog into an AST, and \code{genrtlil} turns each module into RTLIL, a word-level netlist of wires, cells, processes and memories, with the hierarchy kept. From then on, every step is a pass over RTLIL that never sees the AST: \code{proc}, the \code{opt} family, \code{flatten}, \code{techmap} and \code{abc}. Yosys is the reference open synthesis suite, with a large pass library and SystemVerilog and VHDL through plugins~\cite{yosysslang,ghdl}.

\subsection{VTR and partial mapping}

Both models attach to VTR~\cite{luu2009vpr5,rose2012vtr,luu2014vtr7,murray2020vtr8}: a front end, ABC, then VPR's packing, placement, and routing on an XML-described architecture. Jason Luu's work brought in partial mapping. His architecture description language~\cite{luu2011packing} describes logic blocks with hierarchy, modes, and complex interconnects, and models each dedicated block's primitive, so a front end that reads the same file can map part of a design onto those blocks and leave the rest soft for ABC. VTR~7.0~\cite{luu2014vtr7} and the study of hard adders and carry chains~\cite{luu2014hardadders} carried this to adders, with front-end optimizations that ease the restrictions hardened arithmetic places on logic synthesis. Parmys~\cite{parmys} brings the same partial mapping onto Yosys's word-level netlists, runs inside VTR's pinned Yosys~0.55, and is now VTR's default front end.

\subsection{The provenance problem}
\label{sec:provenance-problem}

Synthesis modifies some of the designer's functional intention. Flattening removes the hierarchy, optimization merges and splits operators, and LUT mapping covers the logic with cells that have no source line names. I call the task of linking each object of the final netlist back to the HDL that produced it the \emph{provenance problem}; it is one of the major pieces of this work going forward. Gharibian et al.\ addressed it in placement: simulated annealing produces a flattened design that loses its HDL hierarchy, so they recovered system-level information from the flat netlist and analyzed its correlation with locality in FPGA placement~\cite{gharibian2010finding,gharibian2013analyzing}, then identified and placed clusters found in the placement data~\cite{gharibian2014identifying}. Our latest paper applies data-mining clustering to such combinatorial optimization algorithms~\cite{jamieson2022datamining}. Goeders and Wilton address the same problem in in-system debug: signals in a high-level synthesis-built circuit must be traced back to their source, and they developed signal-tracing and debug techniques for such circuits on FPGAs~\cite{goeders2014effective,goeders2015dynamic,goeders2017signaltracing}. Each line of work had to recover a link the synthesis tool didn't keep. Odin~III keeps it (Sec.~\ref{sec:arch}), so its analysis flow (provenance coverage, \code{levelize}, graph export; Part~II, Sec.~\ref{sec:re-graph}) can redo the placement-correlation experiment with the link to the HDL measured rather than recovered.

\subsection{Oracles, ASTs and elaboration}

\code{tools/run-oracle.sh} runs an oracle on a design and an architecture and stores its netlist, logs, and commit as a golden; Odin~III's output is compared with the golden for identity after canonical renaming and for functional equivalence. An oracle is trusted because it is the reference, not because it is always right (Sec.~\ref{sec:parmys-bugs}). Odin~II transforms the AST into one flat netlist, while Yosys builds each module separately and flattens later as a pass on the graph; Odin~III takes the RTLIL route with its own split (Sec.~\ref{sec:arch}; Part~II, Sec.~\ref{sec:background-detail}).  We note that an oracle makes the process much simpler than the original creation of Odin and Odin II.  We verified our original work with humans, which was costly.

\subsection{A front end that plugs into VTR}
\label{sec:vtr-link}

\emph{Plain English.} Odin~III reads Verilog, makes a netlist, and hands it to ABC and VPR as before. Plugging into VTR is not the real goal of Odin~III; it is the proof that each step works on real designs, because VTR comes with golden results to compare with. The result is meant to be comparable with the Yosys-based front end, not equal to it.

\emph{Technical.} Odin~III reads a design into one IR and changes it one pass at a time. Figure~\ref{fig:flow} shows the path of a Verilog design through the stages, in the order of the production script:
\emph{One IR, two views.} Each cell type carries a granularity tag (\code{word}, \code{bit}, \code{hard}, \code{blackbox}); the word-level (RTLIL) and bit-level (netlist) views are assertions over that tag, so every reader, writer, checker, and the simulator exist once. Every net is one bit, ports are nodes, constants are cells, and every reference is a typed 32-bit ID into per-module paged storage, never a pointer. Every reader, writer, and transformation is a pass, and in Debug builds the pass manager runs a structural \code{check} before and after each.

\emph{Elaboration in two stages.} A project record names the files, the top, the parameters and, unusually for a front end, the architecture and the mapping rules. A preprocessor and an LALR(1) parser build an AST with source locations. Stage~1 is Verilog-specific: it resolves parameters, \code{generate} and constant functions into an \emph{elaborated AST}. Stage~2 is language-neutral: it binds names, sizes expressions, and builds word-level cells, keeping each \code{always} block as a \code{\$proc} cell. The seam lets a later front end enter at stage~2.

\emph{Word-level passes.} \code{proc} lowers \code{\$proc} cells to multiplexer trees, latches and flip-flops in Yosys~0.55's order, and \code{fsm} recodes state machines where Parmys does. \code{opt} is Yosys's family of rewrites, \code{flatten} inlines instances top-down keeping each object's instance path, and \code{wreduce} narrows widths, which decides the block counts. Every walk that Yosys writes recursively is an explicit worklist here, and every input-driven quantity has a named cap, so a hostile input gives a located error, not a crash.

\emph{Partial mapping.} \code{partial\_map} (script name \code{hardmap}) binds word-level multipliers, adders, and RAMs to the blocks that the architecture lists and leaves the rest soft. Parmys's rule is the default; \code{read\_arch} fills a tech library, and an arch record from a VPR architecture file, and generic blocks match by exact port signature, as in Odin~II.

\emph{Bits, LUTs and BLIF.} \code{lower} turns every remaining word cell into bit cells. \code{abc} runs a linked ABC once per clock domain and returns LUTs as one registry cell, \code{\$lut}, with VTR's own script as the default (other scripts are allow-listed and run in a child process). \code{write\_blif --vtr} writes the top module as BLIF that VPR reads; it refuses, before any byte is written, every construct VPR would reject, and \code{blif-vtr-check} mirrors VPR's BLIF checks so that CI gets VPR's verdicts without VTR. The QoR harness \code{vtr-qor} runs VTR's own scripts, read-only, in legs that separate the causes of a gap. Where Odin~III and Parmys could differ, \code{--vtr-compat} makes Odin~III do what Parmys does and print a WARNING; where Parmys is wrong to the RTL, Odin~III stays correct and declares the difference (Sec.~\ref{sec:parmys-bugs}).

\subsection{Checking against oracles}

\emph{Plain English.} Every stage of Odin~III is checked by a tool that is separate from the code, against a reference. Where Odin~III and the reference differ, a probe decides which one matches the Verilog, so the reference's own mistakes surface, and an unproven result never counts as a pass.

\emph{Technical.} Figure~\ref{fig:flow-verify} marks which technique checks which stage: refinement proofs by SAT (\code{lower-equiv}, \code{opt-equiv}), random module generators checked against Yosys \code{techmap}, Verilator random vectors (\code{fcheck}), golden BLIFs, and the exit-code convention of Sec.~\ref{sec:abi-summary}. Part~II, Sec.~\ref{sec:verify} explains each method.

\subsection{One provenance-tracked IR}

\begin{figure}[t]
\centering
\odinfit{\columnwidth}{\input{IMAGE/fig_prov}}
\caption{The provenance lineage DAG (illustrative run and operation numbers). Two \code{\$add}s from one line of a generate loop get two SOURCE records; lowering each is one operation with one DERIVED record; clumping two gates is one operation with two parents.}
\label{fig:prov}
\end{figure}

\emph{Plain English.} Every object in the netlist remembers which Verilog text made it, and from v1.2.0 it remembers the full chain of constructs, including the places where two constructs were blended. This is Odin~III's answer to the provenance problem (Sec.~\ref{sec:provenance-problem}) and the property the Mimir~III dataset rests on.

\emph{Technical.} Every node, net and wire carries one 32-bit ID into an append-only lineage DAG (Fig.~\ref{fig:prov}). A record is SOURCE (made from the HDL), IMPORTED (read from a netlist) or DERIVED (made by a pass, with its parents), and it holds the pass run and the operation within it, so 100 adders from one line of a generate loop stay distinguishable. A step that blends constructs is labelled a join. The walk runs backward to the source line and forward from \code{file:line}, and the writers can name each object \code{hier/path/name@file:line}, so a VPR block traces to its source line without Odin~III loaded. v1.2.0 adds the construct table (ABI~7) and a version~2 name map, which \code{names --lookup} and \code{names --chain} read and \code{odin3-prov-post} extends after place and route.

\subsection{The ABI: extensions and AI tools}
\label{sec:abi-summary}

\begin{figure}[t]
\centering
\odinfit{\columnwidth}{\input{IMAGE/fig_abi}}
\caption{The C ABI and plugin model. Everything outside the core sees only \code{odin3.h}.}
\label{fig:abi}
\end{figure}

\emph{Plain English.} Other programs (Loki, Wyrd, Norns, Mimir) can drive and read Odin~III through one stable interface, and AI tools attach the same way.

\emph{Technical.} The interface is the contract between compiled code: function names, types, structure layouts, and calling conventions. A plugin built against one version of Odin~III must load against a later build without a recompile, and a C ABI helps: no name mangling, no class layouts, no exceptions across the boundary, and other languages can call it. \code{include/odin3/odin3.h} is the only header a plugin sees (Fig.~\ref{fig:abi}). The ABI version (7 at v1.2.0) exposes an opaque design handle and raw 32-bit IDs; every function returns a status; \code{libodin3.so} exports only what the header declares (a script checks it), and a plugin that asks for another ABI version is refused. Plugins register passes and cell types from an \code{odin3\_plugin\_init} entry point, and Python uses the same header through cffi (Part~II, Sec.~\ref{sec:abi}).

The same boundary is how AI tools attach. Agents built Odin~III by driving its command-line scripts and reading its tools' exit codes, which follow one convention (0 holds, 1 differs, 2 tool error, 3 hard failure, 4 unproven, 77 skipped), so a controller can act on a result without parsing text. Through the Python binding, an agent, or a learned model, can walk the IR and its provenance and add cell types for the structures it recognizes, recording its own decisions as DERIVED provenance records. The analysis flow of v1.0 includes a graph export (Yosys JSON plus versioned Odin~III keys) that networkx and PyTorch Geometric load without Odin~III (Part~II, Sec.~\ref{sec:re}). A tool-calling server for language models would be one more plugin over this ABI; none is built yet. This boundary and the emerging AI experiments that researchers would like to do hinge on this point. No hypothesis tests the ABI itself here; the suite papers use it.

\subsection{Gates, checks and statistics}

Odin~III is a systems paper, and its evidence is gates and checks against oracles, not statistical tests; there is no p-value anywhere. Each experiment states its gate or check with the hypothesis: the QoR gate for quality of results; a proof outcome (ok, expected difference, unexpected difference, unproven) for equivalence; a count of passing designs for functional and determinism checks; byte equality for identical output; a time and memory ratio for cost. Quality ratios are geomeans over designs of Odin~III over Parmys. Where a rule gave no number that decides the question, the verdict is INCONCLUSIVE, and a result is never given a stronger verdict than its numbers.

\textbf{Hypothesis O16.} Recording the construct chain at elaboration (\code{--prov-ast refs}) costs at most 5\% of read time and 10\,MB of memory on large designs. \textbf{Experiment.} Five large designs (\code{LU32PEEng}, \code{LU64PEEng}, \code{arm\_core}, \code{mcml} and \code{mkDelayWorker32B}), seven alternating runs per mode, \code{read\_verilog} time and peak memory. \textbf{Result.} The time ratios are 1.037 (\code{LU32PEEng}), 0.998 (\code{LU64PEEng}), 1.067 (\code{arm\_core}), 1.029 (\code{mcml}) and 1.054 (\code{mkDelayWorker32B}); the memory difference is under 1\,MB on all five. \textbf{Verdict: DISMISSED.} Two designs exceed 5\%, by 0.4 and 1.7 percentage points: the extra read time is 1.8\,ms on \code{mkDelayWorker32B} (33.7 to 35.5\,ms) and 2.7\,ms on \code{arm\_core} (39.1 to 41.8\,ms), against run-to-run standard deviations of 1.2 and 1.5\,ms in the off mode. The margin is small against that noise, but the bound was set in advance and was not tuned. The command-line default therefore became \code{off}; the Python API and \code{odin3-flow --prov} use \code{refs}.

\subsection{Timing attribution to HDL (O17)}
\label{sec:q-timing}

% O17: docs/V1.1.1.md lines 22, 55-66; the Norns III repository, docs/paper/r5-results.tex (999 of 999)
\textbf{Hypothesis.} Joining VPR's timing report to the HDL does not change VPR's result. \textbf{Experiment.} A report-only run with and without the extra report on three designs, and an unmatched-atom check on six. \textbf{Result.} The \code{.net}, \code{.place} and \code{.route} files and the critical-path delay are identical on the three; no atom is unmatched on the six. The companion work on The Norns~III placement experiment~\cite{nornsIII}, which uses the attribution, reports that it agreed with VPR's critical-path delay within 0.5\% in 999 of 999 runs (a different property, not part of this verdict). \textbf{Verdict: POSSIBLY GOOD}, narrow: the identity check covers three designs.

\subsection{Component checks (O11, O12)}

% O11, O12: docs/PHASE3.md measured results (Part II, tab:measured)
\textbf{Hypotheses.} The partial-mapping rules (3C) reproduce Parmys's; the BLIF and in-memory exchanges with the linked ABC (3D-7) give equivalent results. \textbf{Experiments.} Hard-cell and flip-flop counts on 12 big VTR designs; equivalence and LUT ratio on the 29 k6 goldens. \textbf{Result.} Every count difference was explained by reading (fsm recoding, flip-flop-bit merge, the order of \code{wreduce}, \code{opt\_share}) and none came from a mapping rule; every finished design is equivalent, with LUT ratios 0.95 to 1.02 and 1.077 for \code{sha}. \textbf{Verdict: POSSIBLY GOOD} for both, because the explanations are not a test and the unfinished ABC runs are not covered. \section{Discussion and Limits}
\label{sec:discussion}

Self-evolved ABC~\cite{yu2026selfevolvedabc} and VPR-Evolve~\cite{wu2026vprevolve} let agents rewrite tools that already exist, with a benchmark score as the judge, and Ding et al.~\cite{ding2026hlsagentic} ask what agents change for high-level synthesis. Odin~III had no code base to start from, so the specification came first, was reviewed by a human, and the judge checked equivalence against oracles before any quality number counted. Three observations follow. First, an existing tool becomes a specification that can be executed: the oracles made it possible to check work that no human had read, and they found defects in the oracles themselves. Second, human time shifted from writing code to writing specifications, making decisions, and choosing what to test. Third, the limit was the machine, not the agents: memory caps, a lock for heavy jobs, and shipped-out designs shaped the method as much as any design decision.

\emph{What was not confirmed.} Two designs differ from Parmys in multiplier count and five lose adders under the QoR gate (O1). Per-design parity with Parmys was retired by decision, not reached (O3): \code{blob\_merge} has 1.78 times the LUTs. Equivalence on the 14 small VTR designs stops at five designs that are past the size limit of the proof (O5). The round trip of the exports is shown on BLIF only (O15). Recording constructs at elaboration costs more than 5\% on two of five large designs (O16, by 1.8 and 2.7\,ms), so provenance with constructs is opt-in on the command line. Hash names still depend on the directory of the design. The ABI keeps attributes as strings, node IDs are module-local, and there are no bulk readers.

\emph{What was not measured.} The five largest VTR designs; power; near-critical statistics per HDL object; the cost of provenance names in VPR; latches with reset. Future work lists the experiment each would need.

What implications does this work push to our field:
\begin{itemize}
\item{I believe the ``superpower'' as I call the creation of complex software is both liberating and concerning.  For an experienced engineer like myself who has the burden of ``job'' this superpower has allowed me to MAIke again.  For the inexperienced engineer, the question is whether it is a superpower or a crutch that will limit the individual.  This educational question, I will argue, is the crux of our time.}
\item{To the crux, I believe the path forward is developing an engineer's semantic knowledge. What does a builder need to know about synthesis that the agents
could not supply, and how did that knowledge enter the specification?  Many claim this is a critical thinking problem.  I'm not happy with how we define that term; instead, I will say it is developing System Thinking~\cite{cabrera2015systems} through first-principles exercises (humans building and testing the system) and determining the right moments for second-principle design (the Making).  This too is a research question we need answered - when?}
\item{The final frontier. What this means for CAD research, for open-source tools and for the EDA industry?  If anything, I see the possibilities that grow deeply with this ``superpower''.  What experiments I can now run is limited more by my imagination (and time) than by the fact that I have to build the tool.}
\end{itemize}

\section{Future Work}
\label{sec:future}

Five hypotheses are untested. Each is the idea and the experiment it needs, nothing more.

\textbf{U1, the cost of provenance names in VPR.} The names added to the netlist do not change VPR's result or run time. The experiment is the Oprov leg of the QoR harness: the same 15 designs through VPR with the provenance names against without, comparing the four result metrics and the run time.

\textbf{U2, the five largest VTR designs.} Odin~III also stays inside the QoR gate on \code{mcml}, \code{LU32PEEng}, \code{bgm}, \code{LU8PEEng} and \code{LU64PEEng}. The experiment is legs P and O$'$ on a machine with more memory, with the same gate.

\textbf{U3, latches with reset and the \code{\$\_DFFSR\_*} cell types.} They map correctly. The experiment adds them to the micro set and runs the refinement proof and the functional check.

\textbf{U4, the plain-LUT architecture on \code{mkDelayWorker32B}.} It passes through ABC. The experiment is a rerun with a limit longer than the 3,600\,s that stopped it.

\textbf{U5, near-critical paths attributed to HDL objects.} The Mimir~III dataset can say why a structure sits on a critical or near-critical path. The experiment uses the v1.1.1 timing attribution with a window, reports per HDL construct the share of near-critical paths over the 15 designs, and checks that VPR's result is unchanged.

\section{Conclusion}
\label{sec:conclusion}

Odin~III answers the final-frontier question with a qualified yes. A Dark Factory, watched daily by the author of Odin and Odin~II and checked against Yosys, Parmys and Odin~II as oracles, built a Verilog front end that keeps Odin~II's good ideas (the node, pin and net model, the architecture file and partial mapping), follows Yosys's semantics, and plugs into the VTR flow: all 15 VTR designs that fit the development machine route, with geomean results inside the gate against Parmys. It adds what neither predecessor has: provenance from every netlist object back to its HDL, recorded when enabled (off by default on the command line, because of the cost in O16), and a versioned C ABI through which plugins and AI tools extend it, which is stated here and not tested. Of the hypotheses tested, eight are confirmed, four possibly good, one failed (the cost of recording constructs) and three inconclusive; five are untested. No one has read the code deeply, and we've tested it on a subset of scenarios; the oracles make more testing possible. The experiments I could not run with Yosys come next, in Wyrd~III (a GUI and experiment runner) and Loki~III (reverse engineering), which use Odin~III as a package \url{https://github.com/drpaj12/YggdrasilIII}.

\section{Overview of Part II}
\label{sec:overview}

Part~I told the story of Odin~III and reported its first results. Part~II describes the system in
detail: what each stage does and which phase built it, the internal data structures, how the
system is verified, what it offers reverse engineering and graph analysis, how and why it differs
from Yosys and Odin~II, how it was built, and where it stands. It is written for the people who
will use and extend Odin~III after version~1.0.

Three threads drive the design (DESIGN \S1): \emph{forward synthesis}, a Parmys/Odin~II-class
front end with architecture-driven hard-block inference (multipliers, adders and memories);
\emph{reverse engineering}, reading flat netlists and recovering higher-level structure, now
approached from Altera LPM structural Verilog upward (Sec.~\ref{sec:re}); and \emph{agentic
construction}, the project as a case study in building a Yosys-class tool with AI coding
agents~\citeall{claudecode} under human architectural control (Sec.~\ref{sec:method}). The v1.0 scope
(ADR D10 and D11) serves three goals: Verilog designs through the modern VTR flow with results
comparable to Parmys; a platform for netlist analysis that is hard to do in Yosys; and provenance
from the final BLIF, for VTR or Altera, back to the HDL. In practice v1.0 is a tool that works on
VTR architectures, that writes its outputs in BLIF, Verilog and JSON and reads them back with their
HDL locations, and that offers an analysis flow for netlists.

After v1.0 Odin~III is meant to be used as a platform, not changed at its core. The experiments
that motivated it are designed after v1.0 as plugins that read the analysis flow's outputs (ADR
D10): reverse engineering from gate-level netlists (for example a redo of Gate-Breaker on
VerilogEval~\citeall{faruque2025gatebreaker,liu2023verilogeval}), Bayesian hypotheses of control and datapath
raised by known design patterns, levelization, graphlet signatures for hardware trojans, the graph
sandwich coupling, graph neural networks, and a redo of the placement-correlation
experiment~\citeall{gharibian2010finding,gharibian2013analyzing} with provenance from the final
netlist back to the HDL. Provenance, stable IDs, hierarchy and the C ABI are kept intact so that
these can be added as libraries and plugins without changes to the core (Sec.~\ref{sec:re-graph}).

\section{Synthesis Background in Detail}
\label{sec:background-detail}

Section~\ref{sec:background} gave the two models of synthesis, VTR's partial mapping and the
provenance problem. This section adds the detail that the rest of Part~II uses.

\emph{Odin~II's data structures.} Odin~II's AST is made of \code{ast\_node\_t} records, and its
netlist of \code{nnode\_t}, \code{npin\_t} and \code{nnet\_t} records linked by pointers. Its
node/pin/net model, in which nets and nodes are peers, is the one Odin~III keeps.

\emph{Parmys as the oracle.} Parmys runs inside VTR's pinned Yosys~0.55 and is the oracle for
Odin~III's goldens and semantics.

\emph{Other infrastructure.} ABC~\citeall{brayton2010abc} provides logic optimization and
equivalence checking. CIRCT~\citeall{circt} builds hardware IRs on MLIR~\citeall{lattner2021mlir};
Odin III borrows its op registry, pass manager, verifiers and first-class attributes but does not
build on it (ADR D7): the LLVM dependency and SSA semantics fight the node/pin/net model needed
for in-place rewiring and reverse engineering. slang~\citeall{slang} is an MIT-licensed
SystemVerilog compiler that Odin III could use through an adapter after v1.0.

\emph{RTLIL.} RTLIL is the register-transfer-level intermediate language of Yosys. Claire Xenia
Wolf created it with Yosys~\citeall{yosys}. A design is a set of modules. A module holds wires, cells,
processes, memories and connections between signals. A cell has a type, parameters and named
ports. A process holds the decision structure of an \code{always} block. RTLIL has two forms: a
text form that tools read and write, and an in-memory form, the C++ objects that the passes
change. Yosys elaborates in two steps. Its Verilog front end parses the source into an AST and
simplifies that AST. Then \code{genrtlil} turns each module of the AST directly into RTLIL.
The hierarchy is kept: an instance becomes a cell whose type is the name of another module. From
then on, the passes work on RTLIL and never see the AST.

\emph{Oracles.} The oracles and goldens are those of Sec.~\ref{sec:background}. Two tools do the
comparison: \code{netlist-compare} checks whether two netlists are identical after canonical
renaming, and \code{equiv-check} checks whether they compute the same function
(Sec.~\ref{sec:verify}). Where Odin~III proves an oracle wrong, the difference is declared
(Sec.~\ref{sec:parmys}).

\emph{The AST, the symbol table and elaboration.} In Odin~II, as the author sees it, the parser
builds an AST, and a symbol table maps each name to its declaration, per scope. Elaboration is
then a series of passes over the AST. Each pass walks an expression tree depth first. The
passes walk the module hierarchy and its instances breadth first. Together they transform the
AST into one flattened netlist graph. RTLIL does not work this way. \code{genrtlil} builds each
module separately, the hierarchy stays, and flattening is a later pass on the graph. Odin III
takes the RTLIL route with its own split. Elaboration has two stages with a seam between them, an
\emph{elaborated AST} (Sec.~\ref{sec:seam}). Stage~1 resolves what the language fixes at
elaboration time: parameters, generate and constant functions. Stage~2 binds names through the
symbol table and builds word-level cells for each module. The hierarchy stays in the IR.
\code{flatten} is a separate pass over the graph.

\emph{optimization as graph operations.} Most steps of a synthesis flow are operations on a
graph, and the author finds that view the clearest one. The netlist is a graph of cells and nets.
Table~\ref{tab:graph} lists each step with its graph operation. Compiler-style optimizations are
rewrites on a directed acyclic graph (DAG) of cells. Flattening inlines a subgraph in place of
each instance. ABC's logic optimization rewrites an And-Inverter Graph
(AIG)~\citeall{brayton2010abc,mishchenko2006rewriting}, and LUT mapping enumerates cuts of that
DAG and covers it~\citeall{cong1994flowmap}. Partial mapping matches subgraphs, the problem that
VF2~\citeall{cordella2004vf2} solves in general.

\section{Architecture in Detail}
\label{sec:arch-detail}

\begin{figure*}[t]
\centering
\odinfit{\textwidth}{\input{IMAGE/fig_pipeline}}
\caption{The Odin III pipeline. Every step inside the core is a pass registered with the pass manager, which runs
\code{check} before and after each pass in Debug builds. The elaborated AST is the seam between

\code{hardmap}) is Phase~3's fixed binding generalised in Phase~4. BLIF text remains the default exchange with ABC; the in-memory exchange is optional (PHASE3 \#48).}
\label{fig:pipeline}
\end{figure*}

Figure~\ref{fig:pipeline} shows the whole system (DESIGN \S3, \S6), and
Fig.~\ref{fig:flow} (Sec.~\ref{sec:arch}) the path of a Verilog design through the stages. The
production script of Sec.~\ref{sec:arch} is the O leg of the \code{vtr-qor} harness
(Sec.~\ref{sec:harness}); \code{hardmap} is the script name of \code{partial\_map}. A test harness,
\code{hardmap-diff}, runs a longer script that adds \code{opt -full} and \code{opt\_clean} calls
between these passes so that each stage can be compared with Parmys.

\emph{Parse.} A project (Sec.~\ref{sec:project}) names the files. The preprocessor and the parser
build a parsed AST with source locations, and the symbol table records each declaration
(Phase~2; Sec.~\ref{sec:parser}).

\emph{Before elaboration.} Odin III has no optimization pass here. Yosys simplifies its AST before
\code{genrtlil}; Odin III does not. Elaboration stage~1 evaluates parameters, \code{generate} blocks and
constant functions, because the language fixes their values. A pre-\code{proc} \code{opt}, as
Parmys runs, is possible because the \code{opt} passes accept \code{\$proc} cells, but the
production script does not run it (PHASE4 decision 14, item~5).

\emph{Elaborate.} Two stages through an elaborated AST give word-level IR in which each
\code{always} block is a \code{\$proc} cell (Sec.~\ref{sec:seam}). \code{proc} then turns these
cells into mux trees, latches and flip-flops, step by step as Yosys's \code{proc\_*} passes do.

\emph{Word-level passes.} \code{fsm} finds state machines and recodes them one-hot, as Yosys's
\code{fsm} does, placed right after \code{proc} as Parmys places it. \code{opt} is Yosys's
\code{opt} family: \code{opt\_expr} folds constants, \code{opt\_clean} removes dead cells,
\code{opt\_merge} merges cells with equal inputs, \code{opt\_share} merges operators that feed the
same mux, and \code{opt\_muxtree}, \code{opt\_reduce} and \code{opt\_dff} tidy
muxes, reductions and flip-flops. \code{flatten} inlines the instances, and \code{wreduce}
narrows widths. The paragraphs below describe them.

\emph{Partial mapping.} Following Odin~II's partial mapping and Parmys's hard-block rules,
\code{partial\_map} binds word-level multipliers, adders and RAMs to the hard blocks that the
architecture record lists, and leaves the rest soft (Sec.~\ref{sec:hardmap}).

\emph{Lower, logic and LUTs.} \code{lower} takes every word cell to bits. The linked ABC
optimises the soft logic and maps it to $K$-input LUTs, with VTR's own script as the default.

\emph{Outputs.} BLIF with \code{--vtr} goes to VPR. Verilog, Yosys-schema JSON and LPM Verilog for
Quartus, Graphviz \code{dot} and RTLIL go to other tools. Sections~\ref{sec:backend} to
\ref{sec:harness} describe the Phase~3 stages, and Sec.~\ref{sec:features} lists every feature
with its phase.

\subsection{One IR, two granularities, passes everywhere}

There is one IR (ADR D1). Each cell type carries a granularity tag---\code{word},
\code{bit}, \code{hard}, \code{blackbox}, plus the structural \code{module} and
\code{port}---and two \emph{views} are assertions over that tag: the RTLIL view admits word,
hard and black-box cells; the netlist view admits bit, hard and black-box cells; mixed
granularity is legal only inside \code{lower} (IR-9). Every reader, writer,
checker, the simulator and the matcher therefore exist once.

Every reader, writer and transformation is a pass. Running a pass opens a provenance pass run,
runs the full structural \code{check} before and after it in Debug builds (or with
\code{--check} in Release), times it and logs it (1D spec). Since 2D-1 a pass also declares
whether it handles processes, and refusal is the default (EL-33). The eight \code{opt} passes
accept them and treat \code{\$proc} as opaque, so Parmys's pre-\code{proc} optimizations run in
Parmys's order (``mode~P''; the order changes netlists: 812 against 792 cells on
\code{stereovision3}); every other pass refuses a design that still holds \code{\$proc} cells.

\subsection{Project input}
\label{sec:project}

\begin{figure}[t]
\centering
\odinfit{\columnwidth}{\input{IMAGE/fig_project}}

A design reaches Odin III as one project record that every reader shares
(Fig.~\ref{fig:project}; DESIGN \S4.0). It holds the source files with language and library,
include paths and defines, the top and its parameter overrides, and---unusually for a
synthesis front end---the \emph{architecture} and \emph{partial-mapping rules}: tech libraries
or architecture files, a per-cell inventory (\code{available multiply 112}), research overrides
(\code{hide} a cell, a variant \code{cell ... from ...}), scoped mapping rules with thresholds
and budgets, and optionally the flow script, so that one file reproduces a run:

\begin{lstlisting}
file verilog rtl/top.v
incdir rtl/include
define WIDTH=8
top top
param top.WIDTH 16
arch k6_frac_N10_mem32K.o3lib
map * $mul to multiply min_width 9
limit multiply 40
flow synth.o3
\end{lstlisting}

The same record is filled from an EDA file list (\code{-f}/\code{-F}, \code{+incdir+},
\code{+define+}, \code{-v}/\code{-y}) or a Quartus \code{.qpf}/\code{.qsf}/\code{.qip} project,
whose synthesis assignments (\code{AUTO\_DSP\_RECOGNITION}, \code{MULTSTYLE}, \ldots) become
mapping rules. Rule precedence is source attribute, instance path, module, global, then
architecture default. The rules are read, checked and stored today; a mapper that interprets
them would record the rule (file and line) that chose each binding in provenance, but that
mapper is not in v1.0 (D10). Unknown keys are errors, so a typo never silently changes a
mapping. The grammar of all formats is normative in DESIGN \S4.0 and pinned by a corpus of 55
project cases (36 positive, 19 negative), each written in every format that can express it,
with a stdlib Python reference parser as the oracle for the C readers.

\subsection{Two-stage elaboration and the seam}
\label{sec:seam}

\begin{figure*}[t]
\centering
\odinfit{\textwidth}{\input{IMAGE/fig_elab_seam}}
\caption{Two-stage elaboration (2D spec). Stage~1 is Verilog-only and produces an elaborated
AST; stage~2 is shared by every front end. A later front end would build the elaborated form
through the C ABI and enter at stage~2. \code{write\_rtlil} hands the result to Parmys's Yosys~0.55 for
equivalence checking.}
\label{fig:seam}
\end{figure*}

Elaboration is split at an \emph{elaborated AST} (Fig.~\ref{fig:seam}; PHASE2 \#8 Q3, 2D
EL-2). Stage~1 is Verilog-specific: module lookup, top selection, parameter overrides
(\code{\#()}, \code{defparam}, project \code{param}), specialisation, \code{generate} and
constant functions. Its output is a second AST store in the same format, restricted to a
subset that \code{odin3\_ast\_check} enforces: no generate constructs or \code{defparam}, every
range and parameter a constant leaf, one \code{MODULE} per parameter specialisation, generate
scopes named with their indices. Stage~2 is language-neutral: binding through the symbol table,
widths and signedness, word cells, drivers, memories, processes, inlining and initial values.

The seam exists so that a second front end can reuse stage~2 instead of writing another
elaborator. Such a front end would emit the elaborated subset through the C ABI. The seam is
built, and the only front end today is Verilog.

Stage~2 represents an \code{always} block as a \code{\$proc} cell: a word-level node whose
\code{I} pins are every net the process reads and whose \code{O} pins are every net it drives,
with Yosys's decision structure (switches, cases, actions, syncs) stored as an opaque, validated
parameter whose positions are pin indices (EL-33). Because the connectivity is ordinary pins,
every IR invariant, driver query and fanout walk holds unchanged; a first design that referenced
nets by ID without pins was rejected in review because it broke the ``every driver is a pin''
rule.

\subsection{Parsing}
\label{sec:parser}

The parser (2C; PHASE2 \#10, \#15) keeps Odin~II's Bison/Flex lineage but not its grammar. A
reentrant Flex lexer reads the preprocessor's stream, and a pure LALR(1) Bison grammar
(\code{\%expect 0}, no \code{\%expect-rr}) has no reported conflicts in its 947 states. The
conflicts that Bison resolves by precedence must equal a committed allowlist (731 lines: the
operator pairs and the dangling \code{else}), so a grammar change cannot silently add one.
Precedence follows IEEE~1364 Table~5-4, and every binary operator is left-associative,
\code{**} included, as in Yosys (Odin~II makes \code{**} right-associative). Error recovery
resynchronises at \code{;} and \code{endmodule}, and stops after 20 errors. The Bison and Flex
output is generated at build time, never committed, and compiled inside the core under one
per-file warning flag.

Each parse is checked twice. \code{odin3-parse-check} runs a \emph{location oracle}: every
node's first token must spell the node, its range must end on a token end, and children must
lie inside their parents. It also prints the tree, parses the text again and requires equal
trees. Two independent generators of input go further. A libFuzzer target feeds raw bytes and
token streams with allocation failures injected and every cap lowered, and requires either a
clean tree or 1--20 located errors; about 62,000 raw-mode runs found one bug, a backslash before
a NUL byte in a string, now fixed. A random-module generator covers the coverage audit's
required and recommended rows. It prints with minimal parentheses from its own copy of
Table~5-4 and dumps its own tree, so it is an oracle independent of the parser. Each seed is
classified against Yosys~0.55, and Odin III must reproduce the generator's tree (200 seeds in
CTest).

\subsection{Processes: \code{proc}}

\code{proc} (2E) turns \code{\$proc} cells into mux trees, latches and flip-flops by
re-implementing Yosys~0.55's \code{proc\_*} sub-passes in C (Fig.~\ref{fig:proc}). Each
process is decoded into a working form over the module's nets. The decision-tree phases
(\code{clean}, \code{rmdead}, \code{prune}, \code{arst}) and a clock pre-check run on every
process of a module before the IR changes; then \code{mux}, \code{latch} and \code{ff} lower
it. The flip-flop phase targets eleven word-level flip-flop and latch cells added with Yosys's
simlib ports (\code{\$adffe} to \code{\$sr}; IR change~D). Every walk that Yosys writes
recursively is an explicit stack, and every unit-test expectation was re-derived by running
Yosys~0.55's sub-passes up to the same phase. \code{proc-diff} gives both tools the same RTLIL
and compares their netlists.

The 2E specification declares 19 divergences from Yosys~0.55 (\S20). Most are for robustness or
determinism. Yosys recurses until its stack overflows on a combinational cycle, and 2E stops
after 1,024 hops or treats the cycle as no feedback. 2E memoises the latch walk, which is
exponential in Yosys on shared cones. It caps pattern pools, and it visits processes in node-ID
order. One divergence is a correctness fix (\S20 \#18, Sec.~\ref{sec:compare}).

\subsection{The back end: the Phase 3 script}
\label{sec:backend}

Phase~3 takes word-level IR to a netlist that VPR places and routes. Its exit test runs the
production script of Sec.~\ref{sec:arch} on the VTR benchmarks of the local gate and routes the
result with VPR (PHASE3 exit item~3). Where Odin III and Parmys could differ,
\code{--vtr-compat} makes Odin III do what Parmys does and print a WARNING when the result still
differs (Sec.~\ref{sec:verify}). The harness \code{hardmap-diff} runs a longer script in Parmys's
order, with \code{wreduce} before \code{flatten} and extra \code{opt -full} calls (PHASE3 \#7,
\#30, \#31), so that the netlist before ABC can be compared. The next five subsections describe
the stages.

\subsection{Word-level optimization: \code{opt} and \code{fsm}}
\label{sec:opt}

\code{opt} (2F) follows Yosys~0.55's \code{opt} family and runs its sub-passes to a fixed point.
Each sub-pass is a rewrite of the cell graph.
\code{opt\_expr} folds constants and simplifies arithmetic and logic whose inputs are constant or
repeated. \code{opt\_clean} removes cells and wires that reach no output (dead-code removal).
\code{opt\_merge} merges cells of one type with the same inputs (common-subexpression
elimination); with \code{-ffbits} it also merges identical bits of word flip-flops before
\code{lower}, as Yosys does after \code{techmap} (PHASE3 \#49). \code{opt\_share} merges operators
that feed the same mux (PHASE3 \#52). \code{opt\_muxtree} and \code{opt\_reduce} collapse
muxes and reductions, and \code{opt\_dff} removes flip-flop features that are never used. Each
call is checked as a refinement by \code{opt-equiv} (Sec.~\ref{sec:verify}). \code{opt} never
renumbers IDs; the scripts call \code{compact} when they want that.

\code{fsm} (4.8) is Odin III's port of Yosys~0.55's \code{fsm} (\code{fsm\_detect},
\code{fsm\_extract}, \code{fsm\_opt}, \code{fsm\_recode}, \code{fsm\_map}). It finds a state
register and its next-state logic, extracts the state graph, and recodes it. It runs right after
\code{proc}, where Parmys runs it. The \code{fsm\_encoding} attribute is honoured, and
\code{auto} gives one-hot below 32 states and binary from 32. The recoded register and logic get
DERIVED records whose parents are the original register and logic, and each FSM gets attributes
(state count, encoding) for the analysis flow. It is merged.

\subsection{Width reduction and flattening: \code{wreduce} and \code{flatten}}

\code{wreduce} (3G) narrows word cells to the widths their inputs and readers need, as Yosys
0.55's \code{wreduce} does, signed rewrite included, and visits an operand before its consumer as Yosys does (PHASE3 \#51). It matters because widths decide hard-block
counts: an adder chain has one \code{adder} cell per operand bit, and the multiplier threshold
reads operand widths. Without it, CLB and adder counts drift for reasons unrelated to mapping.
Parmys runs it before \code{flatten}; the production script runs it after.

\code{flatten} (3A) turns a design whose top module instantiates other modules into one flat
top module. It expands instances top-down from a worklist. The nets joined at a port become one
net with IR-2 aliases. Every flattened object gets a dotted instance-path name (the separator is
an option), and the path is kept in a DERIVED provenance record (\code{hier}), so the hierarchy
is recoverable after flattening (Sec.~\ref{sec:re}). Black boxes and library cells stay
untouched, and a pre-flight reports recursive instantiation and any exceeded cap before the IR
changes. Its oracle is Yosys~0.55's \code{flatten}, compared by \code{flatten-diff} on names,
widths and cell types and by an equivalence proof (PHASE3 \#30, \#35).

\subsection{Partial mapping: \code{partial\_map}}
\label{sec:hardmap}

\code{partial\_map} is Odin III's partial mapping. The idea is Odin~II's: bind some of the
word-level design to the hard blocks of the target and leave the rest soft for ABC. The rules
follow Parmys. The pass began as the fixed pass \code{hardmap} (3C), which copies Parmys's defaults for the architecture
\code{k6\_frac\_N10\_frac\_chain\_mem32K\_40nm}, whose \code{<models>} are \code{adder},
\code{multiply}, \code{single\_port\_ram} and \code{dual\_port\_ram} (PHASE3 decisions 2, 4).
Library cells come from \code{lib/vtr.o3lib} (1G), not from code. Phase~4 renamed the pass \code{partial\_map} and kept \code{hardmap} as an alias, and the
script of Fig.~\ref{fig:flow} still says \code{hardmap}. Parmys's rule is the default, and every
improvement is a named option that is off by default (PHASE4 decision 12). The k6 rules, which the
architect approved before any code was written, are:
\begin{itemize}
\item \emph{Multipliers.} A \code{\$mul} becomes a \code{multiply} cell of width 36. Low pins
  carry the operand bits and the rest is padded with \code{unconn}. Small multipliers
  ($2\times2$) and wider ones stay soft, with a warning, for \code{lower}.
\item \emph{Adders and subtractors.} A \code{\$add} or \code{\$sub} becomes a chain of
  $\max(A,B)+2$ \code{adder} cells: a head, one stage per bit and a top stage. A subtraction is
  $a+\lnot b+1$.
\item \emph{RAM.} A \code{\$mem} first merges the flip-flops on its ports, then becomes
  \code{single\_port\_ram} or \code{dual\_port\_ram} slices. Memories that cannot share a RAM
  port are replicated or stay soft, with a warning.
\end{itemize}
Nodes are named \code{<cell>.<role>} and carry a \code{hardmap} attribute.

Phase~4 generalises the pass from the architecture record. \code{read\_arch} (4.1) reads the
\code{<models>} and \code{pb\_type}s of a VPR architecture file into a tech library and an
\emph{arch record} on the design. Six pull requests of \code{partial\_map} were merged. PR~A
is the pass shell, the rule table, the alias and an identity gate, which requires the new pass
to give the same netlist as \code{hardmap} on the k6 architecture. PR~B is \code{memory\_merge}
(4.7), which merges registered reads and writes into the ports of a \code{\$mem}; a
\code{ram\_style} attribute is ignored with a warning. PR~C binds generic hard blocks from the
arch record (4.2), matched by exact port signature as in Odin~II. PR~D (4.4) maps a RAM with a
read enable to the architecture's RAM and emulates the enable exactly in logic, because the
architecture's RAMs have no read-enable pin (PHASE3 decision 56, approved by the architect on
2026-10-20); it also declares D17 and D18 (Sec.~\ref{sec:parmys-bugs}). PR~E (4.5) builds carry
chains from the architecture model. PR~F, multiplier splitting from the architecture (4.3), declares D19.

\subsection{Lowering to bits: \code{lower}}

\code{lower} (3B) turns every word cell into bit cells so that the netlist view (IR-9) holds.
It reproduces Yosys~0.55's \code{simplemap} and \code{techmap.v} structures. Each word cell is
one transaction: new bit nodes on fresh nets, one DERIVED provenance record, then the word node
is deleted. The bit nodes are named after their word cell, so a gate can be read back to the
operator it came from (PHASE3 \#38). The flip-flop family becomes \code{\$\_DFF\_P\_} plus
enable and reset logic. Asynchronous resets are made synchronous, as Parmys's \code{adff2dff}
does (PHASE3 \#19; \code{--async sync}, with \code{--async error} to refuse). A falling-edge
flip-flop is inverted by default (\code{--neg-edge invert}) or kept (\code{keep}). A leftover
\code{\$mem} becomes flip-flops and muxes, and a transparent read port keeps the RTL-correct
bypass (PHASE3 \#40). Hard cells, black boxes, instances and bit cells are left alone.
Section~\ref{sec:verify} describes how it is checked.

\subsection{Linked ABC and VPR-ready BLIF}
\label{sec:abc}

ABC's LUTs return as one new registry cell, \code{\$lut}, with Yosys's semantics: \code{WIDTH}
from 1 to 16, a \code{LUT} parameter of exactly $2^{\mathit{WIDTH}}$ bits, and
$Y = \mathit{LUT}[\sum_j A_j 2^j]$. It was added first and alone (3D-1), as every IR change
is. The \code{abc} pass (3D) runs ABC once per clock domain per module. Hard cells, black boxes,
instances, level latches and other domains' flip-flops are cut points. Soft cells come back as
\code{\$lut}, and provenance follows ABC's correspondence between input and output nodes
(\code{--prov fine} or \code{cone}). Today the netlist crosses to ABC as BLIF text
(\code{--via-blif}). The in-memory exchange (3D-7, PR~148) passes ABC's own in-memory network
(\code{Abc\_FrameGiaInputMiniAig}, \code{\&put}, the script, \code{\&get -m -n},
\code{Abc\_FrameGiaOutputMiniLut}; PHASE3 \#22). On the 29 k6 goldens every design that
finished is equivalent across the two exchanges, and BLIF text is still the default
exchange at v1.0.

The BLIF writers emit \code{\$lut} as a \code{.names} cover: the shorter of the on-set and
off-set irredundant sum of products (Minato--Morreale ISOP), the on-set on a tie (3E-5). Each
\code{abc} run records its arguments and run information in the pass-run table, including the
script's path and SHA-256, and \code{write\_blif --vtr} prints them as \code{\# abc:} header
lines (3D-3). The ABC script can come from the pass argument, \code{--abc-script}, the project's
\code{abc\_script} or the built-in default \code{lib/abc/vtr.abc}, in that precedence
(PHASE3 \#1).

ABC is linked through an adapter, \code{libodin3\_abc.so} (3D spec AB-6, 3D-2), which links
ABC's objects with \code{-Wl,--wrap} for \code{exit}, \code{\_exit}, \code{abort},
\code{\_\_assert\_fail}, \code{system}, \code{popen}, \code{fork}, the \code{exec} calls and
\code{signal}, and exports two symbols. On the session thread an escape \code{longjmp}s to a
\code{setjmp} guard, so the run fails and \code{odin3} continues. ABC starts threads in 18
files, and an escape on any other thread prints one line and stops the process with
\code{\_\_builtin\_trap()}; its exit status, SIGILL (132), cannot be confused with an
out-of-memory kill (137) (PHASE3 \#28). The process-control wrappers refuse with
\code{EPERM}. The wraps do not catch \code{std::terminate}, glibc's fatal paths or signals such
as the SIGSEGV of an unchecked ABC allocation; the specification lists those. A script other
than the default runs in the \code{odin3-abc} child process under a timeout, after the checker
(3D-4) has read the whole script and allow-listed every command.

\code{write\_blif --vtr} (3E) writes the top module as BLIF that VPR reads with
\code{-start vpr} and that VTR's ABC stage reads with \code{-start abc}. A preflight refuses,
with a located error and before any byte is written, every construct that VPR would reject or
misread (a hierarchical top, a falling-edge latch, a tri-state, a multi-driver net). The plain
writer writes constants as Parmys does, as \code{gnd}, \code{vcc} and \code{unconn}
generators, and only those a module uses. \code{--name-style provenance} (3E-6) names every net
\code{hier/path/name@file:line}, so a VPR block traces to its source line without Odin III
loaded; short names stay the default until the VPR time and memory cost of long names is
measured (DESIGN \S13 \#6). \code{blif-vtr-check}, a VPR-free checker in Python's standard
library, mirrors VPR's BLIF lexer and its \code{read\_blif} checks, so CI gets VPR's verdicts
without building VTR.

\subsection{The QoR harness: \code{vtr-qor}}
\label{sec:harness}

\code{vtr-qor} (3H) runs designs through VTR's own scripts, read-only, collects VTR's metrics
and renders the table and gate of the Phase~3 exit. Each run is a \emph{leg}, which separates
the causes of a gap (PHASE3 exit item~5; 3H spec \S3):
\begin{itemize}
\item \textbf{P}: the Parmys flow, the baseline (\code{run\_vtr\_flow.py} on the Verilog);
\item \textbf{O}: Odin III alone, then VPR (\code{-start vpr}), the exit leg;
\item \textbf{O$'$}: Odin III's netlist through VTR's ABC stage (\code{-start abc});
\item \textbf{P$'$}: Parmys's BLIF through Odin III's \code{read\_blif}, \code{abc} and
  \code{write\_blif --vtr};
\item \textbf{R}: Parmys's BLIF read and rewritten by \code{write\_blif --vtr}, evidence that
  \code{--vtr} does not perturb the baseline;
\item \textbf{Oprov}: O with provenance names, reported for the cost of long names.
\end{itemize}
The harness schedules the smallest designs first under \code{tools/heavy-run} caps, caches jobs
by key, and gates on a geomean ratio of at most 1.20 and no design above 1.50 on CLB count,
channel width, critical-path delay and routed wirelength. Its \code{fcheck} step is the
functional check of Sec.~\ref{sec:verify}.

\section{Verification}
\label{sec:verify}

Odin III's code was written by agents, so correctness evidence must come from outside the code
(Sec.~\ref{sec:method}). Every pass is checked against an oracle, by a tool that is separate
from the pass, and the tools follow one reporting discipline.

\subsection{The methods in plain words}


Figure~\ref{fig:flow-verify} marks which technique checks which stage. Six methods do the work.

\emph{Golden comparison.} An oracle runs on a design, and its netlist is stored as a golden
(Sec.~\ref{sec:background}). Odin III runs on the same design. \code{netlist-compare} reads both
BLIF files, renames and orders them in a canonical way, and says whether they are identical. An
identical netlist is the strongest result. A different one is not yet a bug, because two correct
tools can build different netlists.

\emph{Equivalence checking.} \code{equiv-check} reads two BLIF files and asks ABC whether they
compute the same outputs. \code{cec} compares combinational logic. \code{dsec} compares
sequential behaviour from the initial state. The answer is equivalent, not equivalent with a
counterexample, or unproven when the proof runs out of time or size.

\emph{Simulation.} Odin III has a cycle-based, two-state simulator that uses the semantics of the
op registry. \code{lower-sim} simulates a design before and after \code{lower} on random vectors.
In Phase~1 the simulator was compared with Icarus Verilog on the goldens.

\emph{Functional check against the source.} \code{fcheck} compares a netlist with the Verilog
source, not with another netlist (Sec.~\ref{sec:fcheck}).

\emph{Random generators and fuzzers.} Sec.~\ref{sec:fuzz} explains them.

\emph{Exit codes and the Parmys rule.} Every tool reports in one code convention, and Odin III
matches Parmys and warns where it differs (Sec.~\ref{sec:exitcodes}, Sec.~\ref{sec:parmys}).

\subsection{Oracles and equivalence tools}

The oracles are VTR commit \code{3c9a4d23} (Yosys~0.55 with Parmys, ABC and VPR) and the Odin~II
build in the same tree (ORACLES). Goldens from both are kept in a separate repository, with the
commit that produced each. Table~\ref{tab:tools} lists the tools. Most share two engines: ABC's
\code{cec} (combinational) and \code{dsec} (sequential) through \code{equiv-check}, and Yosys
0.55's \code{miter}, \code{sat} and \code{equiv} passes.

A refinement proof (\code{lower-equiv}) states that every behaviour of the lowered design is a
behaviour of the original, compared at every named wire. It runs under VTR's power-up convention:
a flip-flop's \code{init} is honoured and the others start at 0 (PHASE3 \#41).

(PHASE0 \#8). It proves the logic around the RAM pins through a RAM black-box cut, and RAM port
behaviour is covered by simulation against Odin III's RAM model.

77 & skipped (CTest convention: a precondition such as Yosys is missing) \\
\bottomrule
\end{tabular}
\end{center}
Three rules follow. First, \emph{a listing never counts as a pass}: a file of expected
differences (an ``expect list'') can absorb a known difference with a reason, but it never turns
an unproven result into a pass (PHASE2 \#30; no listing absorbs an unproven refinement), and code 3 is never absorbed. Second, \emph{a skip
is never a pass}: \code{lower-sim} reports a cell type without a simulate hook as
\code{skipped (reason)}, and the sweeps print how many designs they compared against a floor.
Third, an unproven design is recorded with its reason, for example ``untested for now (size
limit)'', and is carried to a larger machine, not dropped.

\subsection{Random generators and fuzzers}
\label{sec:fuzz}

Two kinds of random testing run, and they find different bugs.

\emph{Differential generators.} A generator writes a random valid Verilog design from a seed. The
same seed always gives the same design. \code{tools/verilog-gen} has one profile for the parser,
elaboration, \code{proc}, \code{opt}, \code{lower} and \code{flatten}. The driver runs Odin III
and a reference on the design, and compares the results. For the parser the reference is Yosys:
Odin III must accept what Yosys accepts and must print the generator's own tree. A mutated design,
with one token dropped, duplicated or swapped, must be rejected with a located error whenever
Yosys rejects it. For the passes the driver compares Odin III's netlist with the netlist of the
Yosys pass, and an equivalence tool decides. A \emph{bug} is a case in which Odin III rejects
a valid design, prints another tree, produces a netlist that is not a refinement of the original,
crashes, hits a sanitizer report or times out. A case in which Odin III accepts what Yosys rejects
is reported but is not a failure. The driver keeps the files of every failing seed. A separate
generator, \code{pp-fuzz}, makes random projects for the preprocessor and predicts the output with
its own reference expander.

\emph{Crash fuzzers.} Seven libFuzzer targets (the preprocessor, parser, elaboration, \code{opt},
\code{lower} and two for ABC scripts) run under ASan and UBSan with allocation failures injected
and the caps lowered. They have no oracle. Each target states its invariants, for example that
\code{opt} returns OK or out-of-memory, that the structural \code{check} passes afterwards, and
that nothing leaks or hangs. A \emph{bug} is a violated invariant, a sanitizer report, a leak or a
hang.

Hand-written fixtures miss interactions, so each front-end pass has a seeded random generator
(\code{tools/verilog-gen} with one profile per pass: elaboration, flatten, \code{proc},
\code{opt}, \code{lower}) whose designs go through the same differential tools. The \code{lower}
generator (3B, PHASE3 \#47) makes one \emph{kind} of module per seed: combinational,
flip-flop, latch or memory. It reports each seed as \emph{ok} (equivalent, and the structure
tier holds), \emph{structural} (proved equivalent, but the gate histogram differs from Yosys's
\code{techmap} by one or two gates), \emph{empty} (\code{opt} folded away every word cell, so
nothing was lowered), or \emph{BUG} (not a refinement; the directory is kept and the run exits
1). The 200-seed run gives 200 ok. The 5,000-seed run gives 4,830 ok, 142 structural, 28 empty
and 0 bugs. Equivalence is the pass criterion for the long run, so a histogram difference is
counted, not failed.

\subsection{The functional check}
\label{sec:fcheck}

Equivalence tools compare netlists, and a netlist can be equivalent to a wrong reference.
\code{fcheck} compares against the Verilog source. It runs VTR's own
\code{run\_random\_check.py}, which builds the RTL and the post-synthesis BLIF with Verilator and
drives both with 50,000 random vectors (seed 1). Verdicts are \code{pass}, \code{fail},
\code{error}, \code{capped} and \code{skipped}. The gate passes an O-leg \code{fail} only when a
recorded divergence applies, or when the Parmys netlist fails for a reason outside Odin III
(\code{baseline-fails}). A check that did not run leaves the gate INCOMPLETE, not failed.

An equivalence check needs a legal start state. Yosys's \code{fsm} recodes a state register
one-hot, and ABC starts that register all-zero, a state the one-hot design never reaches, so
the tool reports ``not equivalent'' although no reachable behaviour differs. The checkers
therefore classify by initial state. A ``differs'' needs a trace from the initial state (a
\code{sat -seq 20 -set-init-zero} check after \code{clk2fflogic}). A difference that only an
illegal start reaches is ``unproven'', not ``differs'' (PHASE3 \#41, \#43). On
\code{ch\_intrinsics} a copy of the golden with the state-0 bit initialised to 1 compared
equivalent.

\subsection{Match Parmys, warn where different}
\label{sec:parmys}

The rule for the VTR flow is: where Odin III and Parmys differ, match Parmys under
\code{--vtr-compat} and print a WARNING, and keep no list of known differences. The \code{fsm} pass is an example of the rule at work: it runs where Parmys runs it, right after
\code{proc}, so that flip-flop counts on designs with state machines match Parmys (PHASE4
decision 6).

Two divergences are deliberate, because Parmys is wrong and Odin III is correct to the RTL
(3C spec, divergence table). \textbf{D1}: signed operands of \code{\$add} and \code{\$sub} are
sign-extended into the adder chain, where Parmys pads with \code{unconn}. \textbf{D2b}: the top
stage of an unsigned \code{\$sub} uses \code{vcc}, where Parmys leaves \code{unconn} and loses
the borrow bit. The architect ruled D1 RTL-correct, and a probe (\code{parmys-probe}) confirmed D2b: the Odin III
netlists of three small designs match their RTL for 3,000 cycles each, where Parmys's own
netlists fail (PHASE3 \#42). On the large designs the same defect shows up in \code{fcheck}
(Sec.~\ref{sec:status}). Table~\ref{tab:parmys-bugs} (Sec.~\ref{sec:parmys-bugs}) lists every
Parmys defect found so far, among them D17 (the soft memory path drops the registered read data)
and D19 (a multiplier split on operand B sign-extends the low product).

\section{Internal Data Structures}
\label{sec:data}

All data structures follow four rules from the code standard (DESIGN \S15): cross-references
are typed 32-bit IDs, never pointers; IR objects live in their module's paged storage and passes
never allocate them; traversals use explicit worklists, never recursion; and every fallible
operation reserves before it mutates, so an out-of-memory failure leaves the structure
unchanged. Sizes below are \code{sizeof} on x86-64 with gcc, and timings are Release builds on
the development machine (Intel i7-13700 under WSL2) as recorded in the phase logs.

Figure~\ref{fig:ir} shows the objects and Sec.~\ref{sec:ids} the IDs that link them. The order of
this section follows the data. First the containers and the arena. Then the IR: design, module,
node, net, port and wire, at word and at bit granularity. Then the op registry that gives each
node its type, the provenance store, the source manager, and the AST and symbol table with their
link to the IR. Last come the tech library with the arch record, the C ABI and the caps.

\subsection{Containers}

\begin{figure}[t]
\centering
\odinfit{\columnwidth}{\input{IMAGE/fig_util}}
\caption{\code{src/util}: the only generic containers in the tree, over one allocation wrapper
whose test hook fails the $n$-th allocation. Arrows point from a container to what it uses.}
\label{fig:util}
\end{figure}

\code{src/util} is the only place allowed to define a container (Fig.~\ref{fig:util}; 1A
spec). Containers are \code{void*} plus an element size, typed at the per-kind accessors,
rather than macro-generated (which hides control flow from the linters) or intrusive (which leaks
container fields into IR structs). \code{pagevec} stores pages of $2^k$ elements
($4 \le k \le 16$) behind a growable page table, so elements never move, lookup is a shift, a
mask and two loads, and growth never copies elements. Both hash tables use open addressing with
Robin Hood probing~\citeall{celis1986robinhood} and backward-shift deletion. \code{idindex} is an
ID-only hash-cons index: its 16-byte slots hold a hash and an ID, and the caller supplies
equality, so interned strings and provenance records are stored once. String ID~0 is the empty
string, so a zeroed field means ``no name''. A bump \emph{arena} serves the small arrays that belong to one owner, such as parameter vectors,
wire net vectors and attribute values. Its blocks never move, and one call frees all of them.
The hash seed is a fixed constant; nothing that
reaches output depends on hash-map iteration order. A benchmark interned 2M names in
0.36--0.45\,s, made 2M \code{u64map} insertions in 0.35--0.39\,s and 2M \code{pagevec} pushes in
0.01\,s, at 176\,MiB maximum RSS.

\subsection{The IR}
\label{sec:ids}

\begin{figure*}[t]
\centering
\odinfit{\textwidth}{\input{IMAGE/fig_ir_model}}
\caption{The IR object model (IR.md). A module keeps nodes, pins, nets and wires in
per-kind paged arrays; every reference is a typed 32-bit ID (blue; double-headed arrows are the
two directions of one relation), and grey arrows are ownership. A node's pins are contiguous; a
net owns a contiguous pin array, drivers first. Record sizes are \code{sizeof} on x86-64.}
\label{fig:ir}
\end{figure*}

A design holds a string table, the provenance store, the cell-type table and its modules
(Fig.~\ref{fig:ir}). It also holds containers of facts that are not IR objects: the project
record and, since Phase~4.1, the \emph{arch record} that \code{read\_arch} fills from a VPR
architecture file (Sec.~\ref{sec:techlib}). A module owns nodes, pins and nets as peers, Odin~II's model: a node has
pins, a pin belongs to one node and attaches to one net, and a net has driver and sink pins.
A \emph{port} is not a separate kind of object. It is a node of a built-in type
(\code{\$port\_in}, \code{\$port\_out} or \code{\$port\_inout}), and a \emph{wire} is a name for an ordered
vector of nets. The same objects serve two granularities. In the word-level view, \code{assign y
= a + b;} on 8-bit signals is one \code{\$add} node with three ports of eight pins each. After
\code{lower}, the same eight-bit nets feed bit cells such as \code{\$\_XOR\_} and
\code{\$\_AND\_}. Only the node types change; the nets and the pins are the same kind of object.
The key decisions, numbered as in IR.md:

\emph{Every net is one bit (IR-1).} A port of width $w$ is $w$ consecutive pins, so a port is a
slice of its node's pins and word structure stays visible; word- and bit-level cells differ only
in type. Slicing and concatenation are which nets a pin vector uses, so there are no
\code{\$concat} or \code{\$slice} cells, and \code{lower} replaces cells without
splitting nets.

\emph{Wires are names, not connectivity (IR-2).} A wire is a named, ordered vector of nets with
a range and signedness. A net has at most one primary (wire, bit) and any number of aliases, so
\code{assign b = a;}, flattening and net merging keep every name.

\emph{Ports are nodes and constants are cells (IR-3, IR-4).} Each port is a \code{\$port\_in},
\code{\$port\_out} or \code{\$port\_inout} node, and constant bits come from shared constant
cells, so every driver is a pin and \code{check} has one driver rule.

\emph{Typed IDs, stable until \code{compact} (IR-5, IR-6).} Each kind has its own
\code{struct \{uint32\_t v;\}}, so the compiler rejects a net ID passed as a node ID; slot~0 is a
reserved dummy, so zero means ``none''. Deleting marks an object dead and keeps its slot.
\code{compact} renumbers live objects in ID order, frees dead slots and writes a tombstone per
dead object (module, kind, cell type, name, provenance, parameters, last connected net names) so
history still resolves.

\emph{Storage (IR-18).} Records are arrays of structs in per-module \code{pagevec}s: node
40\,B, pin 24\,B, net 40\,B, wire 40\,B. A throwaway spike (2M nodes, 4 pins each, 2.2M nets)
decided the layout: the whole IR took about 260\,MB, and a fanout walk took 2.8\,s with
intrusive linked pin lists, 0.85\,s with struct-of-arrays link fields and 0.24\,s with
contiguous per-net pin arrays. The net-to-pin representation, not AoS versus SoA, decides
traversal speed, so a net owns a pin array from a size-class pool (capacities 2, 4, 8,
\ldots), partitioned drivers-first so the driver lookup is O(1) and fanout is a slice.

\emph{Invariants (IR \S9).} \code{check} verifies eleven rules: pin ownership and index ranges,
pin--net agreement, the driver/sink partition, single drivers except declared tristate buses,
pin counts against port widths, unique names and agreeing name maps, valid provenance, wire
membership, port consistency, the granularity view, and dangling pins. The 1B benchmark on the
real implementation (2M nodes, 2.2M nets, each with a source record) measured build 0.835\,s,
full \code{check} 0.741\,s, fanout walk 0.313\,s, deleting 10\% 0.098\,s and \code{compact}
0.393\,s at 792\,MiB maximum RSS, inside the 2\,GB budget for Titan-scale designs.

\subsection{Op registry and cell types}

Each cell type is one table entry in one file (IR-8): name (Yosys spelling where one exists),
granularity, flags, ports with a width rule (a constant, an integer parameter, a function, or a
compiled expression supplied by the tech library), parameters with defaults, and hooks that may
be NULL: \code{verify}, \code{const\_value} (one predicate for ``is this net constant''),
\code{simulate} with its scratch-sizing hook, and writer hooks. Simulation flags distinguish
edge-triggered storage, which cuts the simulator's combinational graph, from level latches, which
do not. 75 types are built in. Phase~1 brought 53: ports, constants, the BLIF \code{\$sop} cover
and latch family, bit gates, and the word set (\code{\$add}, \ldots, \code{\$pmux},
\code{\$dff}, \code{\$mem}, \code{\$reduce\_*}). 2D-1 added nine Yosys simlib cells and
\code{\$proc}, 2E-1 eleven flip-flop and latch cells, and 3D-1 \code{\$lut}. The table is
append-only, so a built-in type's index never changes. Plugins register types at load time. Each module instantiates as a cell type of granularity \code{module} whose ports
mirror its port nodes, and each parameter specialisation is its own module (IR-7).

\subsection{Provenance}


Every node, net and wire carries one 32-bit provenance ID into an append-only, hash-consed
lineage DAG (Fig.~\ref{fig:prov}; IR-12, IR-13). A record holds its kind (SOURCE, IMPORTED from a
netlist, or DERIVED by a pass), the pass run and the operation number within that run, source
locations (file, line, column and the raw source-manager location from which macro and include
chains are derived on demand), the AST node, the hierarchical path, and parent records. The
run and operation fields are what keep lineage precise: without them, 100 \code{\$add}s from one
line of a generate loop would share a record and the gates their lowering produces would be
indistinguishable. Decomposing one object is one operation whose pieces share a record with a
single parent; clumping $N$ objects is one operation with $N$ parents; a pass that only rewires
keeps the records. Records are never edited or deleted, and provenance never names object IDs,
so \code{compact} cannot break lineage.

Navigation runs both ways without recursion. The backward walk visits the SOURCE and IMPORTED
leaves of a record. The forward index, built by one sweep over every live and dead object and
tombstone, answers ``everything that came from \code{foo.v:42}''. On the 2M-node benchmark it
was built in 0.064\,s (168\,MB), a query on the busiest line returned 200,000 hits in
0.341\,ms, and a backward walk over all 1.8M live nodes took 0.060\,s. Writers can name objects
\code{hier/path/cell@file:line}, so a VPR block can be traced to its source line without Odin III
loaded.

\subsubsection*{Provenance along the flow}

\begin{figure*}[t]
\centering
\odinfit{\textwidth}{\input{IMAGE/fig_flow_prov}}
\caption{The flow of Fig.~\ref{fig:flow}, annotated with the provenance records that each stage
makes or reads. SOURCE, DERIVED and IMPORTED are the three record kinds. Phase~5.4 is
shown where it applies.}
\label{fig:flow-prov}
\end{figure*}

Figure~\ref{fig:flow-prov} shows where each kind of record comes from. No stage builds a record by
hand. A pass runs with a context that knows its pass run, starts an operation, and asks for a
record with a list of parents (IR-13).

\emph{SOURCE, at parse and elaboration.} The parser gives every AST node a source range in the
source manager's location space. The read pass is a pass run. When elaboration creates an IR
object from an AST node, it makes one SOURCE record with the file, line and column, the raw
location and the AST node, and the object carries the record's ID. One origin in one run is one
record.

\emph{DERIVED, in each pass.} A pass makes a DERIVED record in one of three ways, depending on
what it does to the objects. A pass that only rewires keeps the existing records. A pass that
splits one object into many makes one operation and one record with the original as the single
parent. \code{proc}, \code{partial\_map} and \code{lower} work this way, so all bit cells of one
\code{\$add} share a record. A pass that joins several objects into one makes one operation whose
record has all of them as parents. \code{opt\_merge} works this way. \code{flatten} adds the
instance path to a DERIVED record, \code{fsm} gives the recoded state logic the original register
and logic as parents, and \code{abc} pairs each new LUT with the old cells that compute the same
function and takes those as parents. Records are never edited, and a deleted object leaves its
records and, after \code{compact}, a tombstone.

\emph{IMPORTED, on read.} A netlist reader has no HDL. It makes an IMPORTED record with the
file and line of the netlist, so that an object read from BLIF still says where it came from.

\emph{Names in the outputs.} With \code{--name-style provenance}, the writers name each object
\code{hier/path/name@file:line} from the first location of its backward walk, so a VPR block can
be traced to a source line without Odin III loaded.

\emph{5.4: locations survive write and read.} The IMPORTED record points at the netlist, not
at the HDL, so after a read-back the HDL location of a written object was lost. Phase~5.4 fixed
that. Writers print only the HDL locations, which are the SOURCE leaves of an object's walk:
the provenance name in BLIF, a \code{src} attribute in Verilog, and the \code{src} field in
JSON. Readers decode them. The architect approved an amendment to IR-13 on 2026-10-20: a reader
makes one DERIVED record whose parents are the restored HDL SOURCE record and the reader's own
IMPORTED record. The location then survives any number of writes and reads as an HDL location,
and a line of a netlist never becomes one. The coverage gate of Phase~6.5 measures the result.

\subsection{Source manager}

\begin{figure}[t]
\centering
\odinfit{\columnwidth}{\input{IMAGE/fig_srcman}}
\caption{The location space for \code{`define INNER(p) (p + 1)},
\code{`define OUTER(q) `INNER(q * 2)} and \code{assign y = `OUTER(xx);}: buffers in allocation
order, left to right. Arcs above: where a buffer was entered (\emph{parent}); dashed arcs below:
where its bytes are spelled (\emph{def}); both point to earlier buffers. The segment map ties
each run of the preprocessed stream to a location.}
\label{fig:srcman}
\end{figure}

A location is one 32-bit offset into a virtual source space, as in Clang~\citeall{clangsm}
(Fig.~\ref{fig:srcman}; 2A AST-1--AST-3). Buffers are allocated in creation order, each
reserving its length plus one: FILE buffers for source and project files (and a
\code{<command line>} buffer for project defines), an EXPANSION buffer per macro use, a
MACRO\_ARG buffer per contiguous spelled run of a substituted argument, and SCRATCH for pasted
text. Each buffer records its \emph{parent} (the macro use, the formal, the
\code{`include} or the project word that opened it) and its \emph{def} (where its bytes are
spelled). From these, three loops over buffer records give the spelling, the expansion location
(Clang's \code{getExpansionLoc}) and the file location, and a chain walk prints
``in argument of macro'', ``expanded from macro'' and ``included from'' lines. Each expansion
costs its body length once and each substitution its argument length once, so nesting does not
multiply space. The design owns the source manager, so provenance prints full chains for the
design's life while storing one 32-bit location per source record.

The preprocessor emits a \emph{segment map}: a new segment wherever the output stops following
the spelled bytes one for one, and a location-0 segment of its own for every inserted byte. The
lexer turns output offsets into locations with a monotone cursor. On \code{mcml.v} (650,837
bytes, 24,508 lines), location decode ran at 16.4\,M/s and the sequential cursor at 475\,M/s.
Preprocessing \code{mcml.v} produced 5,590 segments in 2,776 buffers and took 2.751\,ms (target
50\,ms) with a heap of 2.18 times the input; all 31 VTR benchmark files took 0.011\,s in total
at 4\,MiB maximum RSS (PHASE2 \#12).

\subsection{AST and symbol table}

\begin{figure}[t]
\centering
\includegraphics[width=\columnwidth]{fig_ast}
\caption{The 24-byte AST record (byte offsets above each field) and the stores for
\code{assign y = a + 1;}. Nodes are made bottom-up, so every child ID is below its parent's. Each
node owns one span of the shared child table (shaded alike); absent optional slots are ID~0;
literals live in a payload table.}
\label{fig:ast}
\end{figure}

The AST mirrors the IR's storage discipline (Fig.~\ref{fig:ast}; 2A AST-4--AST-16). A node is
24 bytes: kind and sub-kind (one byte each), 16 per-kind flag bits, a source range of two
32-bit locations, a string-table name, and a span (first index, count) into one shared child
table; payload kinds (numbers, reals, opaque text) reuse the span field as a payload index. A
normative \emph{slot table} fixes, for each of 68 kinds, its sub-kinds, whether it has a name,
its flags, its positional slots (absent optional slots are ID~0, so a slot's index never
moves) and its tail class and bounds; the builder validates every node against it, and
\code{check} verifies child classes. Nodes are built bottom-up, so every child ID is smaller
than its parent's: a forward sweep over IDs visits children first, and the store is
append-only and immutable once finished. Literals are stored as written and sized later
following Yosys's \code{read\_verilog} rules exactly. Comments go to a side table sorted by
location; attributes attach through a map from node to a span of attribute nodes.

A builder-enforced depth cap of 32,768 (ten times the deepest real expression found, a
2,032-term chain in Koios~\citeall{arora2021koios} \code{lenet.v}) bounds every explicit stack.
On a synthetic 2M-node AST the store measured 41.17 bytes per node against a 40-byte target,
which was missed and relaxed (the 24-byte record plus number payloads); building took 0.101\,s,
a walk 0.015\,s and a full check 0.127\,s at 94,324\,KiB maximum RSS. A Verilog printer gives the
parser a parse--print--parse oracle.

The symbol table (AST-14) is a scope tree---design, one scope per library, one per module
specialisation, then generate (with loop index), block, function and task scopes---with one
\code{u64map} keyed \code{(scope << 32) | name} for Verilog's single namespace per scope.
Symbols record kind, net or variable kind, flags (signed, implicit, port, overridden, how
assigned), direction, declaration node, packed and unpacked dimensions, parameter value, every
assigning node, and the IR wire they became. ASTs and symbol tables are freed at the end of
their read pass unless a pass asks to keep them; SOURCE records keep the raw location either way.

The AST and the IR are separate stores, and a provenance record links them. When elaboration
creates an IR object from an AST node, it makes a SOURCE record that holds the node's ID, and the
object holds the record's ID. The AST is the high layer, with the syntax and the scopes. The IR is
the low layer, with cells and nets. The symbol table also points forward: each symbol records the
IR wire it became. A pass that needs the syntax of an object follows its record to the AST node,
if the store is still held. If it is not, the record still gives the file, line and column.

\subsection{Tech library and arch record}
\label{sec:techlib}

\begin{figure}[t]
\centering
\odinfit{\columnwidth}{\input{IMAGE/fig_techlib}}
\caption{The \code{.o3lib} tech library: one text format (here the VTR \code{multiply} cell,
verbatim) read into local cell types whose widths may be parametric and whose functions are
expressions over the ports.}
\label{fig:techlib}
\end{figure}

The tech library is Odin III's own line-oriented text format, \code{.o3lib}
(Fig.~\ref{fig:techlib}; 1G spec), target-agnostic so that a flow can map to plain gates
first and FPGA targeting grows from the same format. Liberty is ASIC-timing-centric with no
word-level functions, genlib covers only combinational gates, and VPR XML has no functions and
keeps widths in \code{pb\_type}s, so importers for those formats would produce \code{.o3lib}
cells instead (VPR XML import, 4.1, is built). A cell is \code{gate}, \code{hard} or \code{blackbox}; port widths may be integer
expressions over parameters (\code{A\_WIDTH + B\_WIDTH}); outputs are driven by \code{fn}
expressions, \code{seq} statements or a \code{memory} description; \code{area} and \code{delay}
are stored for later cost models. One function serves as the simulation semantics of the cell. A VPR architecture file reaches the same form through \code{read\_arch} (4.1). It reads the
\code{<models>} and \code{pb\_type}s into generic black-box cells of a tech library, and keeps what
\code{partial\_map} needs in the \emph{arch record}, a container on the design shaped like the
project record. The record owns no node, net, wire or ID. When a netlist declares a library cell
as a \code{.blackbox}, the reader matches its ports by name in any order and infers the
parameters from the declared widths: the goldens hold 49 distinct black-box stanzas whose port
order varies between files.

\subsection{C ABI and plugins}
\label{sec:abi}


Section~\ref{sec:abi-summary} defines an ABI and says why Odin~III has a C one. An API describes
the same contract at the source level, and a change that keeps an API can still break an ABI, for
example by adding a field in the middle of a structure. Odin~III therefore hides its internals,
exposes only IDs and an opaque handle, versions the ABI, refuses a plugin that asks for a different
version, and keeps room in its structures for later hooks.

\code{include/odin3/odin3.h} is the only header plugins see (Fig.~\ref{fig:abi}; 1D spec,
DESIGN \S15.3). ABI version~4 at v1.0 (7 in v1.2.0) declares its functions over an opaque design handle; IR objects
are raw 32-bit IDs passed with their module handle, every function returns
\code{odin3\_status} with results through out-pointers, NULL handles are rejected at the
boundary, and every declaration has a paragraph on purpose, ownership and failure modes.
\code{libodin3.so} is built with hidden visibility and exports only the definitions in
\code{src/api}; a script checks that the exported symbols equal the header's declarations.
Plugins are shared objects with an \code{odin3\_plugin\_init(abi\_version)} entry point that
registers passes and cell types (a mismatched ABI is refused); cell-type structs reserve hook
slots so later hooks do not break the ABI. Python uses the same header through cffi in ABI
mode, and executable hooks exchanging JSON are specified (DESIGN \S15.3) and were not built for v1.0: an executable run at a hook
point (\code{--hook after:partial\_map ./myscript}) gets the IR as JSON on its standard input and

\section{Reverse Engineering and Graph Analysis}
\label{sec:re}

Reverse engineering was one of the three threads that started the project (DESIGN \S1): read a
flat netlist and recover the higher-level structure a designer would recognise. The architect
scoped it in ADR D10 and D11 as an analysis flow that serves graph methods and keeps provenance
back to the HDL. This section says what the goal is, what the built system already provides for
it, how it compares with Gate-Breaker, and what open problems are left.

\subsection{The goal: from Altera all the way up}

The goal is framed \emph{from Altera all the way up}. The architect's words (D10): ``we
will be looking reverse engineering from a different perspective of the goal of going from
altera all the way up \ldots\ I would like to target Altera devices with LPM and structured
verilog, but I'm not interested in their low-level formats.'' The start point is therefore Verilog that
Quartus-style flows produce or accept: a netlist of LPM megafunctions (\code{lpm\_add\_sub},
\code{lpm\_mult}, \code{lpm\_compare}, \code{altsyncram}) for Cyclone~V plus generic gates and
assigns. The end point is a higher-level description: word-level operators, memories and
registers, with every recovered object tied to the lines of netlist text it came from.

Phase~5.1, the Altera target, was the first step. Its LPM tech library (\code{.o3lib}) and the
pass \code{lpmmap} write structural Verilog that instantiates LPM modules with their parameters,
and the same library lets the front end read them back, with each LPM instance becoming a hard
cell. An \code{lpm\_add\_sub} in the input is then already a word-level adder in the IR, and a
memory is an \code{altsyncram} hard cell, instead of an anonymous cone of gates. The test is a
write, read and write fixpoint plus a Verilog lint. Equivalence under the LPM simulation models
and a Quartus compile were not done for v1.0; they wait until the architect needs that step
(PHASE5 decisions 1 and 6).
Recovering structure \emph{between} the LPM cells (counters, shift registers, FSM state registers
built from plain gates) is the part that needs graph methods (Sec.~\ref{sec:re-graph}).

\emph{Provenance (D9; IR-12, IR-13).} A record's kind is SOURCE, IMPORTED or DERIVED, and it
holds the pass run, the operation, the source location, the hierarchical path and the
\emph{parents}. Following the parents chain from a gate of the lowered netlist gives the word
cell it came from, and from there the AST node and the source line (Sec.~\ref{sec:data}). For
reverse engineering the same chain records what \emph{an analysis} decided: a recovered adder
would have as parents the gates that formed it. Netlists read from BLIF get structural-only
provenance until an analysis adds more (D9).

\emph{Stable IDs.} IR objects are 32-bit IDs in paged storage. \code{compact} renumbers them, but
provenance never names object IDs, so lineage survives. An analysis can hold a cell's ID safely
while it runs, and the C ABI hands out IDs, not pointers.

\emph{Hierarchy.} A design keeps its modules until \code{flatten} (DESIGN \S5.1).
\code{flatten} (3A) gives every object a dotted instance path (\code{u1.x}) and keeps the path in
the object's provenance, so a flat netlist still says which instance a gate came from. A
structure recovered from a flat netlist can be reported by instance.

\emph{Reads.} \code{read\_verilog --lib} reads module definitions as library cells (3C's
\code{hardmap-diff} reads its n-bit adder this way), and \code{read\_blif} reads BLIF with black
boxes into the same netlist view. \emph{Names.} \code{lower} names bit nodes after their word
cell (3B, PHASE3 \#38), and \code{write\_blif --vtr --name-style provenance} and
\code{write\_verilog --name-style provenance} print \code{hier/name@file:line}, so a name read in
a netlist leads to a source line.

\emph{Moving up a level (Phase~7.4).} Four operations commit a guess and check it. \code{submod}
moves the nodes that carry one attribute value into a new module, with the boundary nets as
ports, so a recovered block becomes a hierarchy level. \code{Design.copy} (the ABI call
\code{odin3\_design\_copy}) copies a design, so that level~1 is built on a copy and level~0 is
never edited. \code{cone\_check} cuts the marked cone and proves it equivalent to a template cell
of a given type and parameters; the answer is equivalent, differs with a counterexample, or
unproven within a time limit. \code{raise} replaces a cone that \code{cone\_check} proved by that
one word-level cell. Each new object carries provenance to the fine nodes it replaces, so a
recovered adder still leads to its gates and, through them, to the netlist text.
\code{plugins/python/re\_round.py} runs one round of the loop on a small example: mark, bind the
boundary nets, check, raise, and write the new level. Writing the example showed the limits of
the ABI for such tools, and I recorded them (\code{docs/RE-ARCHITECTURE.md}, section 5):
attributes are strings with no remove, \code{cone\_check} is combinational and keeps one result
per module, node IDs are module-local and change after \code{submod}, and there are no bulk
readers.

\emph{Walk and view.} A plugin, in C or in Python through cffi, walks nodes, nets and
provenance through the ABI (1D exit test: ``a Python plugin walks the IR''). \code{write\_dot}
draws a cone, an instance or all objects from a source line, and refuses to draw more than a node
budget without a focus, so a large netlist stays readable.

\subsection{Graph analysis: the architect's vision}
\label{sec:re-graph}

The architect's vision for reverse engineering is graph methods on the netlist: find the
high-level structure of a flat structural Verilog netlist by analysing its graph, and link every
result back to the AST through provenance, so that a recovered block points at lines of source
and the result can inform downstream decisions. The structures in view are datapaths, FSMs,
register files, counters and bus groupings. Which graph methods to use is not decided
(Sec.~\ref{sec:re-open}). This paper reports the \emph{hooks} that the core keeps for them, and
the Phase~6 items that build the flow around them, not results. Phase~6 has five items, all
built and closed for v1.0 (PHASE6 decision 10): gate-level netlist ingest (6.1); \code{write\_dot --color-by} and
HDL locations on node labels (6.2); graph export as Yosys JSON plus versioned Odin III keys, which
networkx and PyTorch Geometric can load without Odin III (6.3); a \code{levelize} pass that stores
the combinational level of each cell (6.4); and a provenance coverage gate (6.5). The gate asks
that every LUT, latch, hard block and LPM instance of the final netlist resolves to at least one
HDL location, with named exception classes, and reports the coverage and the number of distinct
lines per object. The hooks are:
\begin{itemize}
\item provenance on every object and an append-only parents chain, so an analysis can add
  records without rewriting any;
\item stable IDs, hierarchy paths and the instance structure, so results are reported by
  instance;
\item the C ABI and Python plugins that walk the graph, and the registry that lets a plugin add
  cell types for the structures it finds;
\item the netlist and word-level views, so a recovered word-level cell can sit among bit cells;
\item the FSM attributes (state count, encoding) that \code{fsm} leaves on recoded registers.
\end{itemize}
The route after v1.0 is the one the architect named: add the research techniques through libraries
and plugins, without changing the core. D10's last rule protects that route: IR provenance, IDs,
hierarchy and the C ABI stay intact. The tool that follows this route is Loki~III
(Sec.~\ref{sec:v1plan}).

\subsection{Gate-Breaker as the method baseline}
\label{sec:re-gb}

The baseline for this work is Gate-Breaker~\citeall{faruque2025gatebreaker}, a netlist-to-RTL tool
that I co-authored. It takes a gate-level netlist that Yosys produced, with obfuscated wire names
and a six-cell CMOS library, formats it into a prompt, asks a language model to write the RTL,
and checks the result by simulation with Icarus Verilog against the original. It was evaluated
on 156 problems from VerilogEval~\citeall{liu2023verilogeval} with four models. The best model,
OpenAI's O3-Mini, recovered functional RTL for 75.1\% of the runs, and for 53.4\% on the
fourth quartile of code complexity. The metrics were functional correctness and the similarity of
the abstract syntax tree and of the control flow graph. The paper's own conclusion is that
external graph tools should help the model: clustering to name buses, a classification of signals
as datapath or control, and partitioning of the netlist into smaller parts.

Loki~III's flow differs in three ways (Sec.~\ref{sec:v1plan}). First, it has no language model for
now: pattern detectors give likelihoods, and the hypotheses are updated by Bayes' rule. Second,
a guess is checked by proof, not by simulation: \code{cone\_check} says equivalent, differs or
unproven, and that is a strong term in the update. Third, a confirmed guess is committed as a
new level of an ordinary Odin III design (\code{submod}, \code{raise}), so the result can be
written, drawn and traced back to the gates, and the next round runs on that level. Loki~III
targets exactly the three items that Gate-Breaker leaves as future work. It is now built, and the first measurements exist. On the renamed-instance check, L0 is naming-neutral: it labels every netlist object with neutral \code{n}$k$ names, so renaming a design's wires and instances changes nothing in the provenance dataset, as it should. L1's recovery on renamed floors is the honest baseline: macro-F1 0.021 on the calibrated f2 floor (expected calibration error 0.083) and 0.019 on f1; much of the miss is grouping and footprint geometry, not localisation. The Gate-Breaker comparison ran the paper's harness and metrics on the simple benchmarks (three Q1 and seventeen Q2 designs, one run, K=10, with the only model available on the host, Claude Opus, whose CLI exposes none of the paper's sampling parameters): success rate 0.933 on Q1 and 0.829 on Q2, success@10 1.000 in both quartiles, AST similarity 0.576 and 0.444, CFG similarity 1.000 and 0.736, and 169 of 174 extracted candidates passed a 120-cycle differential simulation. The later CFG probe found the experiment's feature-vector padding differs from a common-width node kernel, so the AST and CFG columns will be recomputed in the VerilogEval rerun. The deviations from the paper are logged in the experiment notes: the benchmark set is the fallback micro set rather than VerilogEval, the model is not one of the paper's four, and the validation is differential vectors rather than the VerilogEval testbenches, so the numbers are a first replication, not a model comparison.

\subsection{Open problems}
\label{sec:re-open}

\begin{enumerate}
\item \emph{What is recoverable from LPM?} LPM hides the carry chain and the memory port logic
  inside the megafunction. How much structure the surrounding gates still show, and how to name
  it, is open. The 5.1 write-and-reread test shows only that a netlist Odin III wrote can be
  read back.
\item \emph{Which structures first?} Counters and shift registers are small cycles, and FSM
  state registers need state recoding to be undone (the \code{fsm} pass does the forward
  direction). The order is undecided.
\item \emph{How to score.} A score needs designs with known structure. Round-tripping
  Odin III's own output is circular, so it needs designs from outside.
\item \emph{Equivalence at scale.} A check of each recovered structure needs ABC on cones, and
  \code{dsec} already gives ``unproven'' on several large designs (Sec.~\ref{sec:verify}).
\item \emph{Naming.} Recovered structures need names that mean something. Provenance names
  point to source lines, and a netlist from Quartus has none that carry intent.
\item \emph{Which graph methods.} Which graph methods work best on structural netlists, and
  for which structures, is a research question this paper does not answer.
\item \emph{The plugin interface.} An analysis plugin needs to add cells and provenance records
  safely. The Phase~7 review of the ABI found ten gaps for such tools; v1.0 fixed one, the
  registration of the linked ABC in the Python binding, and nine stay open
  (\code{docs/RE-ARCHITECTURE.md}, section 5): string-only attributes, one \code{cone\_check}
  result per module, no sequential check, no bulk readers, module-local IDs, no cell creation
  through the ABI and others.
\end{enumerate}

\emph{C17, a lint gate and no recursion.} The core is structured C17 (ADR D8$'$), replacing an
earlier C++20 plan, for five reasons: code an agent writes and a human reviews in one pass,
a stable language-neutral plugin boundary, ABC being C, the Odin~II lineage, and complexity
that a linter can enforce. The gate is blocking in pre-commit and CI: clang-format, clang-tidy, cppcheck, lizard
(cyclomatic complexity at most 15, functions at most 60 lines and 5 parameters), a rules script
(no \code{exit} outside the CLI, no \code{abort} outside \code{check}, \code{goto} only to a
single \code{cleanup:} label), \code{-Wvla} under \code{-Werror}, and ASan with UBSan on every
unit test. Recursion is
banned in traversals because the IR can be 2M nodes deep; Yosys's AST simplification and Odin
II's expression reduction are recursive, which is reasonable for hand-written RTL but is a stack
risk for machine-generated designs such as Koios's 2,032-term chains.

\emph{IDs and paged storage instead of pointer graphs.} RTLIL's SigSpec, a list of wire slices
per connection, is expressive but makes every rewrite split slices; Odin~II's pointer graph
makes serialisation and safe external handles hard. Odin III's one-bit nets with contiguous
pin arrays keep rewiring a matter of pin moves, give O(1) drivers and slice fanout, make
\code{compact} and the ABI straightforward, and cost little: the spike measured 260\,MB for 2M
nodes. The price is per-bit storage for wide buses, which the 2M-node benchmarks show is within
budget.

\emph{Provenance as a first-class structure.} Yosys keeps a \code{src} string attribute that
passes propagate where they choose; Odin~II keeps a pointer to the AST node that made a netlist
node. Neither records which pass made an object from which others. Odin III's lineage DAG
records every decomposition and clump, survives deletion through tombstones, and is queried in
both directions, because the research threads need it: reverse engineering reports which
netlist region became which recovered structure, mapping explains which rule chose a binding,
and a user can trace a VPR block to a source line.

\emph{Explicit caps and OOM safety.} Section~\ref{sec:data} explains the caps. Neither Yosys
nor Odin~II defines input-driven limits; both rely on the host. For a tool meant to be fuzzed
and run unattended on shared machines, a located error is better than a killed process.

\emph{Project files carry the architecture and the ABC script.} Odin~II took an architecture
file and an XML configuration; Yosys takes scripts. Odin III makes the project the unit of
reproducibility: sources, defines, top and parameters, the architecture with its inventory and
research overrides, the mapping rules, and the flow. The architect's decision for Phase~3 extends
this to ABC: the project file names the ABC script (\code{abc\_script <file>} in
\code{.o3proj}), \code{--abc-script} on the command line overrides it, and the \code{abc} pass
records the script's path and SHA-256 in its run record, so a soft-logic experiment is recorded
with the design rather than in a wrapper script.

\emph{Linked ABC for the vetted script, a sandbox for the rest.} Yosys's \code{abc} pass writes
the netlist to a per-run temporary directory and runs ABC on it, in a child process or, in builds
with ABC linked, in-process; VTR runs ABC as a separate flow step. ADR~D3 links ABC instead (its permissive license allows linking into the MIT core),
so the \code{abc} pass can hand ABC the soft-logic cone in memory, keep black boxes and
provenance, and stitch the LUTs back. The 3D-0 spike gave a go for the in-memory exchange
(MiniAIG in, MiniLUT out) on two micros, a hand-made \code{scorr} input and five Parmys goldens:
every LUT had at most six inputs, \code{dsec} proved each result equivalent, every register name
mapped back (0 state mismatches in a 256-cycle lockstep simulation), 1,000 runs in one process
gave identical results with no leaked bytes, and two processes gave the same hash (PHASE3
\#22). Linking has a price that a child process does not: ABC calls \code{exit} and
\code{abort}, asserts, and dies on some options, and in-process it takes the IR with it. The
script checker (3D-4) therefore parses every script against an allow-list built from ABC's
sources at the pin, with its 112 aliases, and refuses file, process and latch commands and a
fourth class: options that crash the pinned ABC. Its audit is the finding that decided the
design (PHASE3 \#27). About 70,000 runs of the pinned \code{abc} over six rounds did not
converge. Every round that tried new design shapes, $K$ values or option values found new crash
classes, because ABC's asserts and unchecked allocations depend on the design as much as on the
options. The guard catches an assertion only on the session thread, nothing in a Release
\code{libabc}, and no runaway output (\code{print\_kmap} on a 20-input node prints $2^{20}$ cells).
The architect's ruling (PHASE3 \#28) splits the difference. The built-in default script, the
eight logic commands VTR's ABC stage runs every day, runs in-process through the linked engine.
Any other script, from \code{abc --script}, \code{--abc-script} or the project, still passes the
checker and then runs in a child \code{abc} process with a wall-clock limit and an output cap,
and a crash or timeout there fails that run, not \code{odin3}. The checker, the SHA-256 identity
and the run record are the same on both paths. Odin III thus keeps linking where it is safe and
measured, and pays for isolation only where the input is untrusted.

\emph{Yosys~0.55 semantics as the oracle, with declared divergences.} Rather than reinterpret
IEEE~1364-2005~\citeall{ieee1364} independently, Odin III adopts the semantics of the Yosys inside
Parmys (0.55) as its oracle for literal sizing, widths and signedness, parameter precedence and
process generation, and checks against it through \code{write\_rtlil} and equivalence checking.
Where it differs, the difference is declared and tested: the 2D specification lists 24
divergences (for example, automatic top selection requires a single uninstantiated module,
\code{\$readmem} files are never searched in the working directory, and unconnected inputs are
driven by \code{x}), and the preprocessor declares its own (for example, directives inside
macro text are errors, recursion is judged on the spelling ancestry, and includes never search
the working directory). Parity yields to correctness in one place so far (2E \S20 \#18,
confirmed by the architect in PHASE2 \#16). When a \code{casez} group ends on a path that
builds no cell, Yosys~0.55's \code{proc\_mux} keeps the mux open, and the next group's case
appends to a mux that no longer reaches the result, so its value is lost. For
\code{casez (s) 2\textquotesingle b00: y=x0; 2\textquotesingle b01: y=a; 2\textquotesingle b??: y=a; k: y=b;} Yosys gives $y = a$ where
Verilog gives \code{x0} for $s = 00$. A \code{miter}/\code{sat} check finds the
counterexample, Yosys's own \code{eval} of its netlist disagrees with the source, and Icarus
gives Verilog's value. 2E ends the open mux and gives Verilog's value; \code{proc-diff} and an
equivalence check against a Parmys golden flag such inputs, with 2E on the correct side.
Odin~II is kept as a read-only reference: a coverage audit of 159 synthesizable Verilog-2005
constructs~\citeall{ieee13641} (100 required, 25 recommended, 10 ignored, 24 rejected) probed
Odin~II and Yosys with about 340 one-module tests and found constructs Odin~II's grammar lacks
(e.g.\ \code{casez}, attributes, ANSI function headers) and constructs it elaborates
differently from Yosys (e.g.\ dropped signedness), shown with equivalence checking.

\emph{The elaboration seam.} Yosys gains SystemVerilog by translating slang's elaborated design
into RTLIL inside a plugin; Odin~II has no SV path. Odin III's seam (Fig.~\ref{fig:seam}) puts
the shared work, widths, signedness, drivers, memories and processes, in one stage~2, so that a
second front end after v1.0 would feed one stage~2 and need no second elaborator.

\emph{Agentic, spec-first development with oracles.} Odin~II and Yosys grew through human
contributions. Odin III is written by AI coding agents under an architect's control, so its
correctness evidence must come from outside the code: golden BLIFs from Parmys and Odin~II on
two architectures (2,380 oracle runs: 1,846 succeeded, 522 failed and 12 hit the memory cap),
\code{netlist-compare} (canonicalised identity), \code{equiv-check} (ABC \code{cec}/\code{dsec}),
a differential preprocessor check against Icarus Verilog~\citeall{icarus} and Yosys, the project
corpus, and fuzzers. Section~\ref{sec:method} describes the method.

\section{Development Methodology}
\label{sec:method}

Section~\ref{sec:discussion} sets this method against agent-driven work that evolves existing
tools; this section gives its mechanics.

Every sub-project follows the same path: a specification in \code{docs/specs} with numbered
decisions, an independent critique by a fresh read-only agent, an implementation plan, tasks
dispatched to implementer agents with disjoint files and a written interface, a critique of every
pull request before it opens, and a merge only on a green CI gate (PHASE0 \S A.1). Decisions are
logged per phase; the architect makes or reviews every design-rule decision (specification, ADRs,
IR invariants, mapping algorithms), in some phases after the fact, and the agent proceeds on its
own recommendations elsewhere, logging each as a default he may override. Exit tests are external: the Phase~1 BLIF round trip
ran over every successful golden, the simulator was compared cycle by cycle with Icarus running
an independent dump of the same netlist, and the writers were validated through Yosys.

Review is layered. A controller agent owns git and dispatches each plan task to an implementer
agent, which may not dispatch agents of its own. A fresh reviewer then reads the task's diff and
reports findings graded critical, important or minor; the implementer fixes them in numbered
fix rounds, and an important finding gets a re-review. Before a pull request opens, a
whole-branch review reads the entire branch against its specification and plan, on a different
model (Fable) where one is available, else Opus at extra-high effort. The spec reviews were graded the same way; the 2D
specification's first review, for example, raised 2 critical, 10 important and 17 minor
findings, all applied before approval (PHASE2 \#13). Commit messages name each round and the
findings it answers, so the history records why each fix was made.

Several agents share one 23\,GiB WSL2 virtual machine, and an out-of-memory condition there kills
the whole machine (PHASE0 \#29). Every heavy job (a benchmark sweep, a long fuzz run, VPR)
therefore goes through \code{tools/heavy-run}: a machine-wide lock admits one heavy job at a
time, and the job runs in a systemd slice capped at 6\,GiB with no swap (9\,GiB for the few
jobs that need it), so a runaway job is killed alone. Nesting is decided from the job's cgroup
and the inherited lock descriptor, never from environment variables alone, because a review
found that a leaked variable could let a job run uncapped. Sweeps are CTests registered so that \code{heavy-run}
alone decides whether they may run.

Cost is logged from the agents' transcripts by \code{tools/token-cost}
(\code{docs/log\_cost\_of\_tokens\_and\_time.md}), regenerated at the end of each session, with the
v1.0 count frozen in \code{docs/log\_cost\_of\_tokens\_and\_time-v1.0.md};
Sec.~\ref{sec:results} gives the totals. Controller sessions can run on Claude or on DeepSeek's
Anthropic-compatible API, and because the transcripts record Claude model names either way, the
DeepSeek windows are listed by hand in \code{docs/token\_backends.txt}.

\subsection{Known gaps at v1.0}

Seven gaps are open at the release (from \code{docs/RELEASE-NOTES-1.0.md} and the phase
logs). (1) \emph{The five largest
designs.} \code{mcml}, \code{LU32PEEng}, \code{bgm}, \code{LU8PEEng} and \code{LU64PEEng} are
shipped out to a larger machine as ``untested here: too big for this machine'', and their tables
are report-only (PHASE3 decisions 54 and 55). No new Parmys-parity work was started: comparable
results are the target, not parity (PHASE3 decision 53). The O-leg QoR table was not run for
v1.0 (PHASE3 decision 58). (2) \emph{The plain-LUT architecture.} On \code{k4\_N4\_90nm},
\code{mkDelayWorker32B} reaches the 3600\,s ABC limit. (3) \emph{Dead adders.} On some EArch
designs the QoR harness prints its \code{hardblocks\_lost} warning, because the adders are unused
after VTR's ABC step. I did not investigate it. (4) \emph{Functional check.} \code{fcheck}
classes designs with latches or the \code{--nolatches} precheck as untested, and \code{diffeq1}
is not equivalence-tested because \code{equiv-check} cannot name three of its five multiply
black boxes. (5) \emph{Cell types.} The types \code{\$\_DFFSR\_*}, \code{\$\_ALDFF\_*} and
\code{\$\_SR\_*}, and latches with reset, are not registered; a netlist that uses them reads
them as implicit black boxes (PHASE5 decision 12). (6) \emph{Name style.} The cost of provenance
names in VPR (the Oprov leg) is not measured, so short names stay the default (DESIGN \S13
\#6). (7) \emph{ABI gaps for tools.} Attributes are strings only, with no remove;
\code{cone\_check} is combinational and keeps one result per module; node IDs are
module-local; and there are no bulk readers (\code{docs/RE-ARCHITECTURE.md} section 5). FF
feature matching (4.6) was dropped from v1.0. The CIRCT writer (ADR D12) and the EDIF and VQM
writers (ADR D10) are not part of v1.0.

\subsection{After v1.0}
\label{sec:v1plan}

After v1.0 the new tools live in their own repositories and use Odin III as a pip package, with
no change to the core. I named the whole suite Yggdrasil~III, the world tree
(Fig.~\ref{fig:yggdrasil}). Odin~III is the trunk, and each project below grows from it; M\'{\i}mir~III, the dataset harvested from their runs, is the fruit. The
decisions are mine of 2026-10-21.

\emph{Odin~III} is the trunk. Core features after v1.0 are patch releases, so that the v1.0 base
stays clean. Version 1.0.1 is the route retry for a one-CLB VPR failure. Version
1.0.2 maps ABC's result onto library gates. Version 1.0.3 adds S1, a per-cycle
simulation API: open a design, set inputs by port, step one clock, read outputs and named nets,
and write a VCD whose signal names come from provenance. Version 1.0.4 is unmap, the inverse of
partial mapping: VTR hard cells return to \code{\$add}, \code{\$mul} and \code{\$mem} with
provenance. Version 1.0.5 adds two options that Loki~III's L1 needs: \code{raise -const} and vector
ports for \code{submod}. Each release is tagged only on my go. Version 1.1.0 adds the SystemVerilog
front end (ADR D13, ABI 6): a vendored slang~v12 with a C++ shim that rebuilds Odin III's AST
through the C ABI, leaving the core untouched (Fig.~\ref{fig:sv}). The gate path runs
\code{abc --gates cmos6} and \code{dfflibmap cmos6} over the elaborated design, and
\code{write\_verilog} writes the structural gate netlist back as structural Verilog, the synthesis
path from SystemVerilog with no VTR required. The VerilogEval corpus test pins all 156 references
(Part~I, Sec.~\ref{sec:verify-evidence}), and a clang-tidy C++ profile covers the adapter in CI.
Version 1.1.1 (tools and Python layer only, ABI 6 unchanged) adds critical-path attribution to HDL:
\code{odin3-flow --timing-attr} joins VPR's setup timing report to the provenance names and
\code{odin3-timing} reports which statements, modules and words set the critical path. Version
1.2.0 (released 2026-10-28, ABI~7; plugins built for ABI~6 must be rebuilt) makes provenance exact
at every granularity as a two-way DAG (ADR D14): an object keeps the chain of HDL constructs it came
from, a step that blends two constructs is labelled a join, and the record is exported through
the version~2 hash name map, read back by \code{names --lookup} and \code{names --chain}, and extended
after place and route by \code{odin3-prov-post}. The same release makes hash names independent of the
build. After the tag, \code{odin3-flow} on \code{main} passes design paths relative to their common
directory, so that one design gives the same names in any directory.
VHDL (ADR D11) and FF feature matching (4.6) still come later.

\emph{Wyrd~III} takes its name from wyrd, fate, which the Norns weave at the well under the tree. It
(\url{https://github.com/drpaj12/wyrd}) is a GUI wrapper around Odin III and an experiment
runner. Its first piece, W1, is a command-line runner with projects in TOML, a run store
in SQLite and a scheduler that respects a memory budget. W2 is a Qt GUI with a project tree,
source and report tabs, a Messages pane and a Quartus-like report. W3 adds a simulation panel on
Bifrost~III.

\emph{Bifrost~III} is the rainbow bridge. Here it is \code{wyrd.bifrost}, a session over S1 with
named inputs and outputs, step, reset and VCD. The Wyrd~III simulation panel and Midgard~III are both
its clients, so I design its interface with Midgard~III in mind.

\emph{Midgard~III} is the world where people live, and here it is where people play. It is the Verilog
Town game~\citeall{verilogtown2017}, my Verilog teaching game, ported to pygame-ce on Bifrost~III. One
game tick is one simulation step, and the player's Verilog is compiled when a level starts, with
errors shown in the game at file and line. It reuses the original images and levels under the
MIT licence.

\emph{Loki~III} (\url{https://github.com/drpaj12/loki}) is the reverse-engineering tool for
structural netlists (Sec.~\ref{sec:re}). L0 makes the provenance ground-truth datasets from the
benchmarks; a queued change carries \code{cell\_type} into every graph label, so hard blocks that
are already reverse engineered stay visible in the reconstruction. L1 is the Bayesian hypothesis
flow: pattern detectors give likelihoods, \code{cone\_check} proofs confirm them, and \code{raise}
and \code{submod} move the design up the hierarchy. L2 is built end to end: graph export
(edgelist, GraphML, PyTorch Geometric), region and partition records, clustering (k-means,
affinity propagation, spectral, Louvain), a global-signal classifier from the L1 roles, structural
features (Weisfeiler-Leman colours, NPN signatures, graphlet signatures through ORCA, GraphCrunch
cited only), and GNN training (SAGE, GCN) with a 1-WL baseline. On the real micros the honest
result is that a node-only GNN loses to the 1-WL baseline (macro-F1 0.2413 against 0.2711) and
beats it once node, graphlet, WL and NPN features combine (0.3545 against 0.2711). There is no
LLM step. The first measurements, the renamed-instance check and the Gate-Breaker replication,
are in Sec.~\ref{sec:re-gb}. Loki~III targets the future work of
Gate-Breaker itself: clustering for bus naming, separating datapath from control, and
partitioning. A Trojan detection step comes later.

\emph{Leman~Russ~III}, the wolf-king hunter, is a placeholder for higher-level detection techniques
that build on the structure Loki~III recovers. The first target is hardware Trojan detection as the
Seeker's Dilemma poses it~\citeall{sarihi2024seekers}: the detector does not know whether a circuit
holds a Trojan, so it must decide whether one exists and, if so, where. Loki~III's clusters and L2
graph analysis would supply the evidence.

\emph{The Norns~III} is the placement experiment. It uses the provenance, or the clusters that
Loki~III recovers, as VPR placement constraints (\code{--read\_vpr\_constraints}). Urd uses what the
design was (the provenance hierarchy), Verdandi what is recovered now (Loki~III clusters), and Skuld
what shall be (the placement they constrain); they run as Wyrd~III steps. It revisits the study of
system-level information and FPGA
placement~\citeall{gharibian2010finding,gharibian2013analyzing}. It has its own repository
(\url{https://github.com/drpaj12/nornsIII}) and paper, a placement corpus and run records that
Odin~III's hub snapshot v1.2.0 pins by commit, and it changes none of the pieces it runs.

\emph{Verdandi~III} (\url{https://github.com/drpaj12/verdandiIII}) is the Micro through the Macro,
a desktop app in the Wyrd~III style (PySide6). It runs a micro design through the real, current
Odin~III through the Python binding, records every stage, pass and logged event, and replays the run
as a playthrough: the code that ran, the data structures before and after, and where in the Verilog
the touched objects came from. It never changes the core. (It is a different tool from the
Verdandi step of The Norns~III above, which only shares the name of the second Norn.)

\emph{M\'{\i}mir~III} (\url{https://github.com/drpaj12/mimirIII}) is the fruit of the tree: the
circuit knowledge base and dataset to be mined. It reads the output of Odin~III, VTR, The Norns~III
and Loki~III into one store, records for every value how it was obtained, measures the designs
(Hutton-style structure statistics and Rent's rule), and keeps design meta, lineage and the flow
configurations and runs behind each result. It changes none of the pieces that feed it.

The hub (\url{https://github.com/drpaj12/YggdrasilIII}) pins one commit of every component per
snapshot. Its snapshot for Odin~III v1.2.0 (2026-10-28) pins Wyrd~III, Loki~III, Verdandi~III and
M\'{\i}mir~III at their package version 0.1.0 and The Norns~III by commit; only Odin~III has releases
of its own.
