# Odin III: v1.1.1 critical-path attribution to HDL

Branch `feat/timing-attribution`. Python and tools only: no change to the C core, the IR, the ABI
(`include/odin3`), the op registry, attributes or IDs. Not a pass (no `docs/PASSES.md` row). No tag,
no release.

**Goal (Peter, 2026-10-24: "the Norns 1 ... should be a feature in Odin-III shown via Wyrd").**
After the VTR flow, tell the user which HDL statements, modules and words set the critical path
and Fmax. This patch is the Odin III part: attribution, a machine-readable report and a text
summary. Wyrd III builds the view later from the JSON; Norns round 4 uses the Python API.

## Spec

### Inputs (all produced by the flow; nothing new is needed from VPR or the core)

1. **VPR timing report.** `report_timing.setup.rpt` in the VPR run directory: the worst N setup
   paths of the routed design (VPR default N = 100, `--timing_report_npaths`; detail `netlist`
   is the default and is enough: one row per atom pin with its incremental delay). Fmax and CPD come
   from the `Final critical path delay` line of `vpr.crit_path.out` (else `vpr.out`).
2. **Provenance BLIF.** The VPR atom names are the net names of the BLIF that VPR reads (short
   names such as `$n312`, which carry no source information). With `--timing-attr` the
   odin3 step of the flow appends one more `write_blif --vtr --lut-k K --name-style provenance
   timing/prov.blif`. The writer is read-only on the netlist, so the BLIF VPR reads is
   byte-identical (checked in the evidence run). The provenance BLIF holds the same blocks in the
   same order with every net named `<module path>/<net>@<file>:<line>`. Block `i` of the short BLIF
   and block `i` of the provenance BLIF are the same block; the join is by net token position
   (and is refused with a message if the two files do not line up).

### Join

Report pin `ATOM.port[bit] (type)` gives the atom name. The atom name is a net token of the short
BLIF (VPR names a block after the net its first output drives; I/O pads are the port name, output
pads with an `out:` prefix). The same token position in the provenance BLIF gives
`module path / net @ file:line`. From that:

- **span** = `file:line` (the writer encodes the first HDL location of the net; columns are not in
  the name; see Limits);
- **module** = the module instance path of the name;
- **word, bit** = the net name when it is a source name (`S[3]` gives word `S`, bit 3); a
  generated net (`$nNNN`) has no word (reported as null);
- atoms that are I/O pads count as `port` (word and bit from the port name, no span);
- anything else (no `@` in the name, name not in the BLIF) is `unmatched` and listed with its
  count; delay share and node share are reported for matched, port and unmatched separately.

### Delay model

For one path the rows after the launch (`[clock-to-output]` row, or the pad row after
`input external delay`) form the data path. A row whose atom equals the previous row's atom is an
arc inside the cell: its increment is **cell delay** of that atom. A row whose atom differs is the
first pin of the next cell: its increment is the **interconnect delay** of the net driven by the
previous atom. The contribution of an atom is its cell delay plus the interconnect delay on the net
it drives. Launch-clock latency and setup time are not data delay and are reported per path
(`arrival_ns`, `required_ns`) but not attributed.

### Aggregation

Over the top N paths, per span (`file:line`), per module instance, per word: paths through it
(a path counts once), worst slack of those paths, number of nodes, and on the critical path
(path 1) the delay contribution and its share of the critical data path. The critical path is also
reported as an ordered list of spans, consecutive nodes of one span collapsed.

### Outputs (under `<odin3-flow out>/timing/`)

- `attribution.json` with `schema_version` (1); the one file Wyrd III reads. Documented
  field by field in `docs/user/timing-attribution.md`.
- `summary.txt`: Fmax / CPD, matched share, "these statements set your Fmax" (top spans with
  `file:line`, module, word, delay and share, slack, the source text of the line).
- `prov.blif`, `inputs.json` (what the standalone command needs).

### Entry points

- `odin3-flow ... --timing-attr [--timing-paths N]` (`--timing-paths` implies `--timing-attr`;
  default 100). Needs `--target vtr` and VPR. Extra VPR flag only when N is not 100:
  `--timing_report_npaths N` (report-only; checked in the evidence run).
- `odin3-timing FLOW_DIR [--paths N] [--out DIR]`: attributes an existing flow output dir without
  rerunning anything; needs the `timing/prov.blif` that a flow run with `--timing-attr` wrote.
  Exit codes as `odin3-flow`: 0 ok, 1 failure (missing report, BLIFs that do not line up), 2 usage.
- Python: `odin3.timing_attribution(flow_dir, paths=None) -> dict` (the same data as the JSON).

### Limits

Setup paths only (hold paths are not attributed). Source spans are line-level because the
provenance name carries the line; a statement spanning several lines is represented by its first
location. Generated nets have no word. Names VPR renames or merges are listed as unmatched. The
VPR run must be the one that routed the BLIF in the flow dir.
