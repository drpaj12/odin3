# 5.3 `read_json` (Yosys JSON reader) Implementation Plan (v1)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans. Steps use checkbox
> (`- [ ]`) syntax. Commit and push after every task and after each rule or sub-step inside a long
> task (PHASE5, "commit incrementally"). Never use `cd X && git ...`; use `git -C` and absolute

v1 (2026-10-20). Spec: `docs/specs/2026-10-20-5.3-read-json-design.md` v1 (rule IDs J, M, E, R, T are
binding). The spec's ten questions are taken as **agent defaults** (PHASE5 decision 10, logged by
Task 6); this is a front end, not a mapping algorithm, and changes no IR, ABI, ADR or the behaviour of
any existing reader or writer, so the controller approves the plan. **Stop and report** if a task
finds it needs an IR or invariant change, an ABI change, a registry change (a new cell type), an ADR
or design-rule change, or a change of what an existing writer prints (the R-5 check is the one
possible exception and is reported first).

**Goal:** `read_json` reads Yosys 0.55 JSON and Odin III's own JSON into the IR; `write_json`,
`read_json`, `write_json` is a fixpoint on every micro at the word, gate and LUT levels; the micros
written by Yosys read back and are equivalent to their RTL; every bad file is a located error.

**Architecture:** an iterative JSON value-tree parser (Task 1), a schema walk into the IR reusing the
BLIF reader's module, port, wire and net construction (Tasks 2 and 3), the `read_json` pass, and a
Python round-trip tool over level scripts with committed Yosys fixtures (Tasks 4 and 5).

**PR split (one pass per PR, CLAUDE.md rule 1):**

## Task 1: the iterative parser and its limits (E-1 to E-5, T-1)

**Files:** new `src/frontends/json/json_parse.h`, `json_parse.c` (and `json_lex.c` if the parser
exceeds 400 lines), `limits.h`; new `tests/unit/test_json_parse.c`; `CMakeLists.txt`
(`odin3_add_unit_test(test_json_parse)` and the source list); `src/frontends/README.md` (a `json/`
line).

Interface (written first in `json_parse.h`, with a doc paragraph for each function):
`odin3_json_parse(const uint8_t *text, size_t len, const odin3_json_limits *lim, odin3_json_doc *doc)`
makes a tree in `doc->arena`; accessors `odin3_json_kind`, `odin3_json_member(obj, "key")`,
`odin3_json_first`/`odin3_json_next` (children in file order), `odin3_json_string`, `odin3_json_int`,
`odin3_json_pos(node, &line, &col)`; `odin3_json_doc_free`; an error struct (line, col, message)
filled on failure. No recursion anywhere (parse and free are worklists).

- [ ] Step 1 (tests first, `test_json_parse.c`): every kind; string escapes, `\u` BMP, a surrogate
  pair, a lone surrogate (error), `\u0000` (error), a raw NUL (error); ints at `INT64_MIN`/`INT64_MAX`
  and one beyond (error), a fraction and an exponent (errors); duplicate key (error naming the key and
  both lines); trailing comma, leading comma, missing colon, unterminated string, unterminated array
  at EOF (all located); BOM skipped; depth 32 reads, depth 33 is the depth error; a 200,000 deep `[[[`
  is the depth error with the stack limited by `ulimit -s 256` (the test re-executes itself or runs in
  a thread with a small stack); string longer than the limit; file larger than the limit (limit lowered
  by the test hook); truncation at every byte offset of a 2 KB sample file is an error with a line and
  column and never a crash; allocation-failure sweep (`odin3_util_set_alloc_fail_after`) leaves no leak
  and returns NO_MEMORY. Run: they fail to link.
- [ ] Step 2: implement the parser. Keep every function within 15/60/5.
- [ ] Step 3: `ctest -R test_json_parse` green under ASan and UBSan; `tools/lint.sh` clean.
- [ ] Step 4: commit and push.

**Acceptance:** `test_json_parse` green with the case list above; no function over the lizard limits;
the 200,000-deep case runs in bounded stack; a 100 MB generated file parses in under 5 s in Release
(measured and quoted in the commit message, not gated).

## Review focus (for the critique agent, one pass per PR)

- 5.3a: any recursion; any allocation not bounded by a limit; error positions (line and column are the
  value's first byte); `\u` handling (surrogates, NUL); integer overflow in the number parser.
- 5.3b: a bit number used as an index; net creation order (M-3) against R-1; width checks that resize
  instead of failing; registry lookups that treat a `$` name as a module; attribute typing against
  J-10; the second-driver check; the unknown-type and `--auto-blackbox` wording; the top choice
  (M-1) on a file with several black boxes; module cycle detection without recursion.
- 5.3c: a fixture or an expect line that hides a failure; the equivalence legs actually run (a zero
  count of compared designs fails, as 5.2's review H1); Yosys-only tests marked local-only and CI runs
  the committed fixtures.

## Risks

- **R-1 and net order (spec risk 1):** Task 3 sub-step (a) tests it first.
- **A writer defect found by read-back** (R-5 or another): report, do not patch the writer inside a
  reader PR; the fix is its own small PR.
- **Fixture size and drift:** limited by Task 4 step 1's rule and the `VERSION` check.
- **CTest time:** the sweep is labelled `sweep` and out of the default set.
- **Registry gaps:** the `SKIPPED` list of Task 4 makes the gap visible per micro.
