# 4.1: VPR-XML architecture import (`read_arch`): design (spec only, for review)

Status: v1 (2026-10-20), **awaiting controller review**. No code yet. Phase 4, item 4.1
(`docs/PHASE4.md`). Rules have IDs (**X-n** XML reading, **M-n** models, **P-n** pb_type facts,
**L-n** library generation, **C-n** command and API, **T-n** tests) so they can be approved or changed line
by line. The open questions are in section 12, each with a recommendation. Nothing in section 12
needs a new third-party dependency or a `.o3lib` format change; section 12 says so per question.

Scope is 4.1 exactly: `read_arch <file.xml>` reads a VPR architecture's `<models>` and its pb_type
hierarchy, registers the hard cells as `.o3lib`-model cell types, keeps the facts that 4.3 to 4.6
need, and `write_techlib` dumps the generated library as `.o3lib` text for diffing. **No mapping
changes.** `hardmap` stays as it is and keeps reading `lib/vtr.o3lib`; 4.2 to 4.6 consume the import.

Inputs read for this spec:
- D10, D11, PHASE4 (4.1 to 4.8, 4.13, open item 1, decisions 1 to 8), DESIGN §6 step 7, §7;
- the 1G spec with its 2026-10-19 amendment, `src/techlib/reader.h`, `reader_cell.c` (the `.o3lib`
  grammar as built), `lib/vtr.o3lib`;
- the 3C spec §3 (H-3) and `src/passes/hardmap/hm_kit.c` (`shape_matches`: what hardmap needs);
- `src/frontends/project/xml.[ch]` (the subset XML reader that exists);
- VPR (read only): `libs/libarchfpga/src/read_xml_arch_file.cpp` (`process_model_ports`, the
  `<models>` loop), `arch_util.cpp` (how a model port gets its size), and Parmys
  `parmys-plugin/parmys_arch.cc`, `core/multiplier.cc` (`find_hard_multipliers`);
- all 300 architecture files under `vtr_flow/arch` (surveyed with a throwaway script; the numbers
  below come from that survey, not from memory).

## 0. What the survey of the 300 archs found

1. **Models carry no widths.** `<model>` lists ports with direction, `is_clock`, `clock="clk"` (the
   port is sampled by that clock) and `combinational_sink_ports`. Widths exist only in the
   pb_types. VPR sets a model port's size to the **maximum** `num_pins` over all leaf pb_types that
   use the model (`arch_util.cpp:783`, `min_size` the minimum). `k6_frac_N10...`: `multiply` leaves
   are 9, 18 and 36 wide, so the model's `a` is 36 and `out` 72; `single_port_ram` `addr` is 15 and
   `data` 64 (`addr` 9 to 15, `data` 64 down to 1).
2. **VPR keeps model ports in reverse XML order** (`process_model_ports` pushes to the front of a
   linked list). `lib/vtr.o3lib` lists the RAM ports in that reversed order (`clk data addr we`,
   outputs `out2 out1`) but `adder` in XML order (`a b cin`, `cout sumout`): the order is Odin II's
   and the goldens'. `hardmap` compares ports **by index** (`shape_matches`), so the imported
   `multiply`, `adder`, `single_port_ram` and `dual_port_ram` must have exactly `vtr.o3lib`'s order
   and parameter names.
3. **Parmys sees only the model.** `find_hard_multipliers` takes the model named `multiply` and its
   one port size (the maximum). For the 22nm 4add arch that is 27 (leaves 18x19 and 27x27); it is
   the square-`WIDTH` view even though a leaf is not square. `parmys_arch` registers every other
   model as a black box.
4. **File properties** (all 300 archs): valid UTF-8, no DTD, CDATA, processing instruction (only
   the `<?xml ...?>` declaration, four spellings), entity or `xi:include`; largest file 5.6 MB
   (`multi_die/stratixiv_3d`). The existing XML reader accepts all of that.
5. **Model names.** 6,479 `<model>` elements; 27 archs (titan, noc, multi_die, stratixiv) have model or port
   names that are not identifiers, for example `stratixiv_ram_block.opmode{dual_port}.output_type{reg}...`
   (up to 346 models in one file). `.o3lib` names are `[A-Za-z_][A-Za-z0-9_$]*`.
6. **Hard-block shapes seen.** `multiply` (square 9/18/36; 18x19 plus 27x27; 25x18), SP/DP RAM
   with 5 to 11 modes, `adder` with `pack_pattern` chains, generic blocks (`pcie`, `mult_8`,
   `dpram_128x8`, `dff`/`dffe`/`dffr`/`dffer`, `int_sop_4`, `mac_*`), and archs with no `<model>`
   at all (`k4_N4_90nm`, `k6_N10_40nm`: only `.input .output .names .latch`).

## 1. XML reading (X-1 … X-3)

- **X-1 Reuse the existing reader.** `src/frontends/project/xml.[ch]` (PRJ-15) is a
  non-recursive, line-numbered subset reader: BOM, declaration, comments, CDATA, the five
  entities, numeric references, a node cap. It rejects exactly what no VPR arch uses. No
  third-party parser (D3 stands: no new dependency). The importer includes `xml.h` in place; it
  is not moved (question 1).
- **X-2 Cap.** `max_nodes` is `1 << 24` (the 5.6 MB file has well under 10^6 nodes); over the cap
  is a located error naming the cap. Input over `UINT32_MAX - 1` bytes cannot occur.
- **X-3 Errors** are `file:line: message` (`ODIN3_ERR_PARSE`), the line from the element's
  `line`; an XML syntax error uses the reader's offset and `what`. `ODIN3_ERR_IO` when the file
  cannot be read; `ODIN3_ERR_NO_MEMORY` is not located.

## 2. Models (M-1 … M-6)

- **M-1 Input.** The root must be `architecture`; `<models>` is optional (an arch with none is
  valid and imports an empty library plus the pb_type facts). Children of `<models>` other than
  `model` (including `xi:include`) are a located error `unsupported element '<tag>' in <models>`.
- **M-2 Model.** Name from `name` (required, unique: `duplicate model 'X'`, VPR's check). Ports
  come from `<input_ports>` and `<output_ports>`; a port has `name` (required, unique within the
  model), optional `is_clock` and `is_non_clock_global` (both true: error, as VPR), `clock` (a
  port name; stored as a fact), and for inputs `combinational_sink_ports` (names of output ports of
  the same model; an unknown name, or the attribute on an output, is an error, as VPR's
  `check_model_combinational_sinks`).
- **M-3 Facts kept** per model (in `odin3_arch`, section 5): ports in XML order with direction,
  clock flags, `clock` reference, sink list, the **maximum and minimum `num_pins`** over the leaf
  pb_types that use the model (P-4), and the source line.
- **M-4 Unused port width.** A model port no leaf mentions has no size. The library uses width 1
  and logs an INFO line `model 'X' port 'p' is not used by any pb_type; width 1`.
- **M-5 Registered or not.** A model whose name and all port names are `.o3lib` identifiers
  (and no port is named `signed` or `x`) becomes a library cell (section 4). Otherwise it is kept
  in the arch record only, and one WARNING per arch counts them: `N models have names that are not
  .o3lib identifiers and are not registered (first: 'name')`. The import still succeeds. These
  are the 27 titan, noc, multi_die and stratixiv archs; none is a sweep arch (question 5).
- **M-6 Builtin leaf kinds.** `.input`, `.output`, `.names`, `.latch` are not models; they get no
  library cell (BLIF built-ins).

## 3. pb_type facts (P-1 … P-7)

The importer walks every top-level `<pb_type>` under `<complexblocklist>` (a `<tiles>` section is not
read: 4.1 needs the logical blocks; question 6). It records, without interpreting:

- **P-1 Leaves.** Every pb_type with a `blif_model` is a **leaf**: kind (`.input`, `.output`,
  `.names`, `.latch`, `.subckt NAME`), `class`, its ports (`input`, `output`, `clock`, with
  `num_pins` and `port_class`), `num_pb`, the source line, and its **path**: the chain from the
  top-level block down, each level as (pb_type name, mode name or none, `num_pb`). A `.subckt`
  leaf must name a model of `<models>`, else `pb_type 'p' uses model 'X', which is not in
  <models>` (VPR's check). Its port names must exist in the model with the same direction and
  clock-ness, else a located error (VPR's check).
- **P-2 LUT size K** (for `abc --lut` and `write_blif --lut-k`). K is the maximum `num_pins` of
  the `in` port over `.names` leaves; the minimum is kept too (fracturable LUTs: 4 in arithmetic mode, 5 and 6). An arch
  with no `.names` leaf: K absent (`odin3_arch_lut_k` returns 0). Reference values: `k4_N4_90nm` 4,
  `k6_N10_40nm` 6, `k6_frac_N10` 6 (min 4), the 22nm 4add arch 6 (min 3).
- **P-3 FF facts (for 4.6).** The `.latch` leaves with their ports are kept as they are. No feature
  classification (enable, reset, set) is made in 4.1: standard VPR archs have only `D`, `Q`, `clk`,
  and archs with featureful FFs use `.subckt` models (`dff`, `dffe`, ...) whose meaning is a
  4.6 decision, not a guess here.
- **P-4 Model widths.** For each model port, the maximum and minimum `num_pins` over the leaves
  using it (the VPR rule, item 1 of section 0).
- **P-5 Multiplier facts (for 4.3).** Nothing extra: the `multiply`-model leaves with their widths
  and paths give the sizes (`a`, `b`, `out`) and the mode tree (for `k6_frac`: `mult_36` with mode
  `two_divisible_mult_18x18` of two `divisible_mult_18x18`, each with modes `two_mult_9x9` and
  `mult_18x18`, and mode `mult_36x36`). The leaf list is the product; 4.3 derives split sizes.
- **P-6 RAM facts (for 4.4).** Likewise the `single_port_ram`/`dual_port_ram` (any model with a
  `memory` `class`) leaves with `addr`, `data`, `out` widths per mode, `port_class` values, and
  the enclosing block's own pin counts (`memory` has `addr1 15`, `data 64`).
- **P-7 Carry facts (for 4.5).** For each `<interconnect>` child (`direct`, `mux`, `complete`) its
  name, `input`, `output`, and every `<pack_pattern name in_port out_port>` child; and every
  `<directlist>/<direct>` (`name from_pin to_pin x_offset y_offset z_offset`). A flag
  `has_adder` is true when a leaf uses a model whose name is `adder` with ports `a b cin cout
  sumout`. Which pack patterns form a chain (those that reach `cin` and `cout` of an adder leaf)
  is derived in 4.5; 4.1 only supplies the raw lists and `has_adder`.

## 4. Library generation (L-1 … L-7)

The importer builds `.o3lib` **text** in memory and gives it to `odin3_techlib_read_text`. So the
imported library is, by construction, what the `.o3lib` reader accepts: the same model, no new
registration path, and `write_techlib` is the same text.

- **L-1 Library name** is the XML file's stem (`k6_frac_N10_frac_chain_mem32K_40nm`), made an
  identifier by replacing other bytes with `_`; the file's path is in the first comment line.
- **L-2 Templates for the four VTR primitives.** If the model name is `multiply`, `adder`,
  `single_port_ram` or `dual_port_ram` and the model's port names, directions and `is_clock`
  flags equal the template's (any order), the cell is generated from a compiled-in template that
  is **the text of the corresponding `vtr.o3lib` cell**: same port order, same parameters and
  defaults (`WIDTH 1`, `ADDR_WIDTH 15`, `DATA_WIDTH 1`), same `fn` and `memory` statements.
  These carry the simulation and memory semantics 1E and hardmap rely on; the arch cannot state
  them. The templates live in one C file; a unit test (T-1) compares them to `lib/vtr.o3lib`
  cell by cell, so they cannot drift.
- **L-3 Template mismatch.** A model with one of these four names whose ports differ (a renamed or
  missing port, a different clock) is **not** given the template: it becomes a generic cell (L-4)
  and one WARNING names the difference. (Example: none of the 300 archs does this; the rule keeps
  a hand-written arch from silently getting a wrong function.)
- **L-4 Generic cell.** Every other registered model is `cell NAME blackbox`, ports in XML order,
  `in`/`out`, width = the maximum `num_pins` (P-4, M-4), the `clock` modifier on `is_clock`
  inputs, no `fn`. A generic block is therefore matched by its exact port signature in 4.2
  (D10), which is the VPR size of the model. `pcie`, `mult_8`, `dpram_128x8`, `dffe` are examples.
- **L-5 Template widths are parametric, the arch's widths are facts.** `multiply` keeps
  `param WIDTH int 1` even when the arch's model is 27 or 36 wide; the arch's size is in
  `odin3_arch` (P-4, P-5) and is what 4.3 reads. Reason: `vtr.o3lib` and every golden use the
  parametric form, and one cell type must serve the 9, 18 and 36 leaves.
- **L-6 Squareness.** The `multiply` template is square (`a`, `b` of `WIDTH`, `out` of
  `2*WIDTH`), VTR's primitive. An arch whose `multiply` leaves are not square (18x19, 25x18) still
  gets the template; the model's `a` and `b` maxima are what VPR and Parmys use. The leaf list
  records the real shapes for 4.3. (Question 4: whether 4.3 needs an asymmetric cell.)
- **L-7 Registration.** A cell whose name the design already has (for example `vtr.o3lib` was
  read first) is the reader's located error `cell 'adder' is already defined`; `read_arch`
  replaces `read_techlib lib/vtr.o3lib` in a script, it does not stack on it. A second
  `read_arch` of any arch in the same design is the same error for a shared model name: one
  architecture per design.

## 5. The arch record (C-1 … C-3)

- **C-1 `odin3_arch`** (new, `src/frontends/arch/arch.h`): file name, library name, the model
  list (M-3), the leaf list with paths (P-1), K and min K (P-2), the interconnect and directlist
  facts (P-7), `has_adder`, and the generated `.o3lib` text. It lives with the design
  exactly as the project record does: `odin3_design_get_arch`, `odin3_design_arch`,
  `odin3_design_drop_arch` in `src/ir/design.[ch]` (a container hook; no IR object, invariant or
  ID changes; question 2). The accessors are const; sizes are `uint32_t`; strings are strtab-free
  C strings in the record's arena.
- **C-2 Queries** 4.2 to 4.6 will use (names, not yet needed by any pass): `odin3_arch_lut_k`,
  `odin3_arch_model_count/at/find`, `odin3_arch_leaf_count/at`, `odin3_arch_leaves_of_model`,
  `odin3_arch_has_adder`, `odin3_arch_library_text`. Not in the C ABI (`include/odin3/`):
  Phase 4 consumers are core passes; the ABI review is 7.4.
- **C-3 Idempotence.** One arch record per design; a second successful `read_arch` is rejected
  by L-7 before the record is replaced; a failed `read_arch` leaves no record and no types.

## 6. Commands (C-4 … C-6)

- **C-4 `read_arch <file>`** (a new builtin pass, `processes` OK, like `read_techlib`). A file
  ending in `.xml` is imported; a file ending in `.o3lib` is read as `read_techlib` reads it (so
  DESIGN §6 step 7 holds for both); another extension is `read_arch: expected a .xml or .o3lib
  file`. INFO line: `read_arch: <lib>: N models (R registered), L leaves, K=<k>`.
- **C-5 `write_techlib <file>`** writes the library text of the design's arch record (what
  `read_arch` generated) to `<file>`; `-` is stdout. With no arch record: `write_techlib: no
  architecture has been read (read_arch first)`. It is not a general dumper of a registered
  `.o3lib` (that would need an expression printer; question 3).
- **C-6 No script changes.** The Phase 3 script keeps `read_techlib lib/vtr.o3lib`. 4.2 switches
  it to `read_arch` when it needs the arch facts.

## 7. Output format of the dump

The first lines are comments: `# generated by odin3 read_arch from <file> (VPR architecture)` and
`# models: N, registered: R`. Then `library NAME`, then the cells in XML model order, each with its
template or generic text. Template cells keep `vtr.o3lib`'s comments out (they are generated);
the cell stanzas are otherwise byte-identical to `vtr.o3lib`'s.

## 8. Diagnostics

| Condition | Level | Text |
|---|---|---|
| file unreadable | error | `read_arch: cannot read '<path>'` |
| XML syntax | error | `<file>:<line>: <reader message>` |
| root not `architecture` | error | `<file>:<line>: expected the root element 'architecture'` |
| duplicate model/port | error | `<file>:<line>: duplicate model 'X'` / `duplicate port 'p' in model 'X'` |
| unknown sink | error | `<file>:<line>: combinational sink 's' is not an output of model 'X'` |
| leaf uses unknown model | error | `<file>:<line>: pb_type 'p' uses model 'X', which is not in <models>` |
| leaf port not in model | error | `<file>:<line>: pb_type 'p' port 'q' is not a port of model 'X'` |
| direction/clock mismatch | error | `<file>:<line>: pb_type 'p' port 'q' is an input but model 'X' declares an output` (and clock) |
| template mismatch | warning | `<file>:<line>: model 'multiply' differs from the VTR primitive (port 'a' missing); imported as a black box` |
| non-identifier names | warning | M-5 text |
| unused model port | info | M-4 text |

## 9. Memory and speed

One pass over the node array, no recursion (the pb_type walk keeps an explicit stack, spec §15.1).
All growth through `src/util` containers with reserve-before-mutate; a budget check is not
needed (the XML cap bounds it). Target: the 5.6 MB file under 2 s in the debug (ASan) build.

## 10. Provenance, IDs, hierarchy

Cell types carry the library data (`odin3_techlib_cell`: file, line of the generated text). The
import adds no IR objects; it registers types only, as `read_techlib` does. Provenance, IDs, ABI
and attribute rules are untouched.

- **T-3 Facts.** On `k6_frac_N10...`: K 6 (min 4), `multiply` leaves 9/18/36 with their

## 12. Open questions (each with a recommendation; agent defaults unless marked)

1. **XML parser.** Reuse `src/frontends/project/xml.[ch]` in place, or vendor a C XML parser
   (expat is MIT but a new dependency; mxml, roxml, tinyxml2 are C++/other licenses), or move the
   existing reader to `src/util/`. **Recommend: reuse in place.** It parses all 300 archs'
   features, has line numbers and a node cap, and costs no dependency or license entry. Moving it
   to `src/util/xml.[ch]` is a mechanical rename that touches the project lane's files; do it
   only if a reviewer dislikes `frontends/arch` including `frontends/project/xml.h`. No Peter
   decision.
2. **The arch record on the design.** `odin3_design_get_arch` (a container hook in
   `src/ir/design.[ch]`, same shape as the project record) versus a global in the pass layer
   versus facts as design attributes. **Recommend: the design hook.** It is not an IR object or
   invariant, but CLAUDE.md rule 10 says Peter reviews IR changes, so the controller decides
   whether `design.[ch]` counts. Fallback with no `src/ir` edit: keep the record in a pass-layer
   registry keyed by the design pointer (uglier, not recommended).
3. **`write_techlib` scope.** (a) dump only the library `read_arch` generated, (b) a general
   dumper of any registered library, (c) a `-o` option of `read_arch` only. **Recommend (a)**, the
   task's diff use case; (b) needs an expression printer for `fn`/`seq`/`memory` and has no
   consumer.
4. **Asymmetric multipliers (18x19, 25x18).** The `multiply` template is the square VTR
   primitive (L-6). **Recommend: keep it in 4.1.** The arch's real leaf shapes are recorded;
   whether 4.3 needs `A_WIDTH`/`B_WIDTH` parameters (a `.o3lib` cell change, a new library file,
   not a format change) is a 4.3 decision.
5. **Models with non-identifier names** (27 titan, noc, multi_die, stratixiv archs). Options: skip with one
   warning (M-5); mangle to an identifier and keep the original name in the arch record; error.
   **Recommend: skip with a warning.** D10 removed Titan from v1.0, and a mangled name would
   not match a BLIF `.subckt` anyway. Revisit if Titan returns.
6. **`<tiles>` and grid.** Read only `<complexblocklist>` (P-1), not tiles, sub_tiles, grid or
   switches. **Recommend: that.** 4.2 to 4.6 need logical-block structure; capacity and layout
   matter only to VPR.
7. **Generic cell kind.** `blackbox` (no function) versus `hard`. **Recommend `blackbox`**: the
   arch states no function, `hard` requires one (1G spec), and 4.2 matches by port signature only.
8. **When scripts switch to `read_arch`.** 4.1 changes no script (C-6). **Recommend: 4.2**
   makes `hardmap` read the arch types, and the sweep (4.13) runs `read_arch` per arch. Until
   then `lib/vtr.o3lib` stays, and T-1 guards the two staying equal.

## 13. Recommended sweep archs (PHASE4 open item 1)

The sweep is the Phase 3 arch plus one DSP arch and one plain-LUT arch. Goldens in
`~/odin3-ws/golden` today: `EArch` and `k6_frac_N10_frac_chain_mem32K_40nm` only (38 leaf dirs
each; EArch is a copy of the k6_frac shape, with the same 36/18/9 multiplier and RAM modes, so it
adds nothing). The other two need goldens from `tools/run-oracle.sh` (an oracle run through the VTR
flow, not an oracle rebuild; heavy-run, when lanes are idle).

- **DSP arch: `COFFE_22nm/k6_frac_N10_4add_2chains_depop50_mem20K_22nm.xml`.** Why: (1) its
  hard multiplier is a different shape (leaves 18x19 and 27x27, model max 27 against 36), so
  4.3's "split size and threshold from the XML" is really exercised, which `k6_frac`, `EArch`,
  `k6_N10_mem32K` (all 36/18/9) cannot do; (2) its RAM is the 20K family with `data` 40/20/10 and
  `addr` 9 to 11, so 4.4 splits to something other than the 32K family; (3) it has `adder` and two
  carry chains (`pack_pattern chain`), K 6 fracturable with 5 and 3 input LUTs, so 4.5 and 4.6
  see a second chain layout; (4) it is a VTR regression arch (`vtr_reg_strong/strong_two_chains`,
  `strong_soft_multipliers`) run through the Parmys flow, so a Parmys golden is obtainable with
  `run-oracle.sh` (verified: those configs list it; **not verified:** that Parmys completes every
  VTR design on it). **Fallback** if a Parmys run fails on the designs: `timing/k6_N10_mem32K_40nm.xml`
  (36/18/9 multiplier, 32K RAM, **no `adder` model**, K 6): lower coverage, but it tests the
  "no carry model" path of 4.5 and is the most-used arch in the VTR regressions.
- **Plain-LUT arch: `timing/k4_N4_90nm.xml`.** Why: K is 4 (the others are 6), so the K from the
  arch (`abc --lut`, `write_blif --lut-k`) is exercised for the first time; it has no `<model>`,
  no multiplier, RAM or adder (everything must stay soft logic, the "unknown block is soft" path of
  4.2 to 4.5); 9 KB; a VTR regression arch (`strong_pack_place_route`, `strong_mcnc`) in the
  Parmys flow. **Caveat:** the Phase 3 designs with `$mul` or memories have no hard block here,
  so a Parmys golden for them is obtainable only if Parmys completes with soft multipliers and
  memories on this arch (not verified); 4.13 then runs the designs Parmys completes, and the
  sweep file lists them. **Fallback:** `timing/k6_N10_40nm.xml` (K 6, otherwise the same).
- Both are imported in T-4 and T-5 whatever the golden outcome. Cost note: one oracle sweep per
  new arch is hours of CPU; run smallest-first when the lanes are idle.

## 14. What this does not do

No mapping change; no `hardmap` change; no `.o3lib` format change; no new third-party code; no
read of `<tiles>`, grid, routing or timing; no FF feature classification; no chain derivation; no
asymmetric multiplier cell; no tool-level change to `abc --lut` (the K accessor is the hand-off).
