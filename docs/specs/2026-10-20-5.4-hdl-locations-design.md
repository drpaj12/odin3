Phase 5, item 5.4 (PHASE5.md, D11): the HDL location of an object (the `file:line` of the Verilog it

with its HDL locations. This spec fixes the exact text of each format, what is lossless and what is best
effort, and the measurement that gives Phase 6.5 its coverage numbers.

## 0. What the repo already gives, and what it does not

**Already there.**
1. Provenance records (IR-12): `SOURCE` (HDL text), `IMPORTED` (a netlist file), `DERIVED` (a pass
   operation, with parents); `locs` `{file, line, col, end_line, end_col}`; `hier`. `odin3_prov_leaf`
   and `odin3_prov_sources` walk back to the leaves. Readers use `odin3_prov_source` and
   `odin3_prov_imported` (IR-13).
2. A JSON `src`: `"file:line.col"` of the first leaf (`jw_src`), on cells and netnames
   (`write_attrs`, `jw_cell_attrs`); modules carry none. It takes the first leaf **of any kind**, so for a design read from BLIF it
   is the BLIF line, not an HDL line.
3. Verilog: `// file:line` at the end of a line (`vw_eol`, the first leaf of any kind), `(* name = v *)`
   attributes before modules, ports, wires, nets, instances and `always` (`put_attrs`), and
   `--name-style provenance` (`hier/<short>@file:line` as an escaped identifier).
4. BLIF: `write_blif --vtr --name-style provenance` names every net but a top port bit and a generator
   `hier/<short>@file:line` (then VB-10 legalisation: `%XX` escapes and a `%` prefix). The plain dialect
   writes `.cname`, and `.attr`/`.param` only for what the BLIF reader kept.
5. Every reader makes its own records: BLIF IMPORTED `{file, line, col}`; Verilog SOURCE at the HDL
   being read; a `src` read by 5.3 stays an attribute (5.3 M-12).

**Not there.**
1. No reader turns a location in a file back into a record, so after a read the HDL location of a
   written object is gone (the object has only the netlist's own line).
2. No rule says which leaf kinds a writer prints. Printing an IMPORTED leaf as `src` pollutes a later
   read: a location in `design.blif` would come back as an "HDL" location and inflate Phase 6.5's
   coverage.
3. `src` carries no end position (Yosys's does), only the first leaf (Yosys's can hold several,
   `|`-separated), and a Verilog `assign` cannot carry an attribute (Icarus rejects it), so gate and
   LUT level Verilog, which is all `assign`s, has only the trailing comment.
4. A way to measure it: which objects had a location, which keep it, and why not.

## 1. Vocabulary

- **HDL location**: the `{file, line, col, end_line, end_col}` of a `SOURCE` leaf reached by the backward
  walk from an object's record (`odin3_prov_sources`). A netlist location (an `IMPORTED` leaf) is not
  an HDL location.
- **First HDL location**: the first `SOURCE` leaf with a location in walk order (parent order), the one
  names and comments carry.
- **Restore**: a reader makes, for an object with a location text, the record of D-1.
- **Lossless** for an object kind in a format: every HDL location the object has, up to the cap of W-3,
  comes back equal (file, line, column, end line, end column), in order. **Best effort**: a location comes
  back for some objects or with less detail, and the loss is a named class (X-n) that the test counts.

## 2. The location text (L-1 to L-8)

**L-1 Grammar.** `LOC := FILE ':' LINE [ '.' COL [ '-' ENDLINE '.' ENDCOL ] ]`, `SRC := LOC { '|' LOC }`.
It is Yosys's `src` (`file:1.1-4.10`, with `|` between several) plus the shorter forms Odin III writes
(`file:12` in names and comments, `file:12.3`). Numbers are unsigned decimal without a sign, from 1 (line
0 does not occur).

**L-2 Parsing is from the right.** A `LOC` is the longest suffix of the text (before the next `|`
boundary) that matches `:LINE[.COL[-ENDLINE.ENDCOL]]` with the last `:` that makes it match; the rest is
the file, taken byte for byte, never resolved, never checked for existence. So `C:\x\a.v:3.1-4.2` and
`a:b.v:3` parse. The separator `|` splits only where what follows starts a `LOC` ending in digits; a file
name that contains `|` is not writable in a multi-location text (W-5) and is read as part of the file
name in a single one.

**L-3 Numbers** over `UINT32_MAX` are an error of that text; `end` before `start` is accepted and kept
(Yosys never writes it; a corrupt text is not a reason to drop the rest of the file).

**L-4 Where it goes** (`LOC` or `SRC`, per format): JSON `"src": "SRC"`; Verilog `(* src = "SRC" *)`
(string value, `\\` and `\"` escaped; a byte outside 0x20..0x7e makes the file unwritable, W-5) and the
trailing comment `// LOC` (only line, `file:12`) on an `assign`; BLIF names `hier/<short>@file:line`
and plain-dialect `.attr src "SRC"`.

**L-5 Names (BLIF and Verilog provenance names).** `NAME := [ HIER '/' ] SHORT '@' FILE ':' LINE [ '$' N ]`.
`HIER` and `SHORT` are split at the **last** `/` before the **last** `@`; the text after that `@` is
parsed by L-2 with only the line form. `$N` (decimal) is the writer's uniqueness suffix (BLIF VB-10 rule
4 and the Verilog writer's `$1`, `$2`) and is not part of the location. BLIF names are percent-decoded
first (VB-10 inverse: `%XX` with upper-case hex is the byte; a leading `%` followed by anything else is
the reserved prefix and is dropped). A name with no `@`, or whose tail after the last `@` does not match,
is not a provenance name and is kept as it is.

**L-6 No guessing.** A text that does not match its grammar is never an error and never a partial
location: the object keeps the text as it was (a `src` stays an attribute `src` with the text, a name
stays its name) and the reader counts it; one WARNING per file reports the count and the first example
with its line. (A source file can legitimately contain any attribute; the reader must not reject it.)

**L-7 HDL only.** Writers print only `SOURCE` leaves (W-2). Readers restore every restored location as a
`SOURCE` record (D-1), so a location survives any number of write and read generations as an HDL
location, and a netlist line never becomes one.

**L-8 JSON `src` and 5.3.** 5.3 reads `src` as the attribute `src` (5.3 M-12). 5.4 turns it into a
record (D-2) and removes the attribute, so a later write of the design prints the location from
provenance, not a stale string; the reader switch `odin3_json_opts.src_to_prov` of 5.3 is true by default
afterwards, and `read_json --keep-src-attr` keeps the attribute and makes no record (the 5.3 behaviour).

## 3. Writers (W-1 to W-6)

**W-1 One helper.** `odin3_hdl_locs(design, prov, cache, out_locs, cap)` in
`src/backends/common/hdl_loc.{c,h}` (new; pure format code and one prov walk, no IR change) returns the
HDL locations of an object (W-2, W-3); `odin3_hdl_loc_print(locs, buf)` prints `SRC` or `LOC` (L-1);
`odin3_hdl_loc_parse(text, locs, n)` is the parser (L-2, L-3) the readers call. The three writers use
the first and second; they stop calling `odin3_prov_location` for this purpose.

**W-2 Which leaves.** The backward walk (`odin3_prov_sources`, a worklist, no recursion) visits leaves
in parent order; a leaf is taken when its kind is `SOURCE` and it has at least one location with a file
(`n_locs > 0`, `locs[0].file != 0`), and the file's bytes are all in 0x20..0x7e. `IMPORTED` leaves are
skipped. This changes what the existing JSON `src` and Verilog `// file:line` print for a design read
from BLIF (they print nothing there, where they printed the BLIF line): intended, and the unit tests
that read a BLIF and expect a location are changed to read a Verilog (question 2).

**W-3 How many.** For `SRC` (JSON, Verilog attribute, BLIF `.attr`): every distinct location
(`file, line, col, end_line, end_col`) of the taken leaves, in walk order, at most **8**; a record with
more has its first 8 printed (best effort, X-3). For names and the Verilog trailing comment: the first
location only, line only. The cap keeps a LUT that clumped hundreds of cells from writing a line a
reader would reject (E-3's string limit of 5.3) and bounds output size.

**W-4 Precision.** In `SRC` each location is printed with its columns and its end when the record has
them: `file:L.C-EL.EC` (Yosys's form) when `end_line != 0`, else `file:L.C` when `col != 0`, else
`file:L`. The existing JSON writer printed `file:L.C` and no end; netlistsvg and nextpnr read the start
only, Yosys's reader keeps the string, so the longer form is compatible (question 3).

**W-5 Unwritable.** A location whose file contains a byte outside 0x20..0x7e, a `|` (in `SRC`), an `@`
(in a name), or a `"`/`\` that the target cannot escape is skipped with one WARNING per file (count and
first example); the object is then written without that location (X-4).

**W-6 Per format, exactly:**

| format | object | text | where |
|---|---|---|---|
| JSON | module | `"src": SRC` | module `attributes` (new: today modules carry no `src`) |
| JSON | cell | `"src": SRC` | cell `attributes` (existing key, new content W-2 to W-4) |
| JSON | wire (netname) | `"src": SRC` | netname `attributes` (existing) |
| JSON | named net | `"src": SRC` | netname `attributes` (existing, one-bit entry) |
| JSON | port | none | the `ports` object has no attributes; the port's netname carries it |
| Verilog | module | `(* src = "SRC" *)` | before `module` (existing attribute slot) |
| Verilog | port, wire, net declaration | `(* src = "SRC" *)` | before the declaration (existing slot) |
| Verilog | instance | `(* src = "SRC" *)` | before the instance (existing slot) |
| Verilog | storage cell | `(* src = "SRC" *)` | before the `always` (existing slot) |
| Verilog | `assign` cell | `// file:line` | end of the line, unchanged (an attribute is illegal there) |
| Verilog | net name, `--name-style provenance` | `\hier/short@file:line ` | the escaped identifier, unchanged |
| BLIF VTR | net | name `hier/short@file:line` | `--name-style provenance`, unchanged (net names only) |
| BLIF VTR | cell | none | the dialect has no `.cname`/`.attr` (3E: nothing but names); the reader inherits (D-5) |
| BLIF plain | cell | `.attr src "SRC"` | after `.cname`, new option `write_blif --src-attr`, plain dialect only |
| BLIF plain | net | none | the plain dialect names nets with their own names |

A user `src` attribute on an object still wins over the provenance `src` and is printed verbatim (the
existing writer rule); after 5.4's readers there is none to win, because restored `src` is a record
(L-8). The Verilog writer adds nothing to the file header and keeps its name styles.

## 4. Readers (D-1 to D-7)

**D-1 The record.** For an object with a restorable HDL text, the reader makes
`DERIVED{ run = the read run, op = the run's single restore operation, parents = [SOURCE, NETLIST],
hier = H }` where `SOURCE = {kind SOURCE, run, locs = the parsed locations, ast 0, hier H}` and
`NETLIST` is the record the reader would have made without 5.4 (IMPORTED at the JSON value, the BLIF
directive, or, in `-netlist` mode, the Verilog line). **The HDL parent is first**, so `odin3_prov_leaf`,
`odin3_hdl_locs` and every "first location" consumer see the HDL, and the netlist line stays reachable as
the second leaf. `H` is the `HIER` of L-5 (BLIF and Verilog names) and 0 otherwise. Records are hash-consed
by their parents, so equal text on many objects is one `SOURCE` and one `DERIVED` per distinct pair. The
reader begins one operation (`odin3_prov_begin_op`) for the whole file. This is the "beside the IMPORTED
record" of PHASE5 5.4. The use of `DERIVED` by a reader is new: IR-13 says readers use
`odin3_prov_source` and `odin3_prov_imported`; the amendment to IR section 6 is one sentence ("a reader
that restores locations a writer printed makes one DERIVED record per object, parents = the restored
SOURCE then the reader's own record") and no field, invariant, ID or check rule changes (question 1).

**D-2 JSON.** `read_json` (5.3 M-11) parses a `src` value of a module, netname or cell attribute with
`odin3_hdl_loc_parse`. A cell and a module get the record of D-1 on the node or module; a netname gets
it on its wire, and on the net of a one-bit netname; nets of a wider wire that have no netname of their
own keep the netlist record only (X-1). A parse failure keeps the attribute (L-6). A port's wire takes
the location of its netname (Yosys and Odin III both write one).

**D-3 Verilog (`read_verilog -netlist`).** New option `-netlist` / `--netlist` (both spellings, as
`-icells`). It says "this file is a netlist, written by `write_verilog` or Yosys": the reader's own
records become `IMPORTED` (a netlist line, not HDL: L-7), and then:
(a) a `src` attribute on a module, port, wire, net, instance or `always` is parsed (L-2) and restored
(D-1) on that object, and the attribute is not kept; a non-matching value stays an attribute (L-6);
(b) a trailing `// LOC` line comment on the line where a continuous assignment ends is restored on the
node the assignment makes (a gate, a `$sop`, a word cell), found through the comment side table
(`ast/comment.c`: stream order, sorted by location, so a lookup is a binary search); a comment that is
not exactly one `LOC` (after `//` and blanks) is not a location and is ignored;
(c) an identifier of the form L-5 (`\hier/short@file:line `) is split: the name becomes SHORT, the record
carries `hier`, and the location restores as in (a); a name that does not match stays as is.
Without `-netlist` nothing changes (`src` is an ordinary attribute, comments are comments, identifiers are
identifiers): reading user Verilog is unchanged, which is the same rule as 5.2's `-icells`. `-netlist`
composes with `-icells`, and the tools use both.

**D-4 BLIF (`read_blif --hdl-locs`).** New option. Without it nothing changes (names byte for byte,
PHASE1 #2; goldens unchanged). With it: (a) every net name that matches L-5 after VB-10 decoding becomes
SHORT, with `hier` and the HDL location restored on that net (D-1); if SHORT is already a net name in
the module, `$N` is appended with the first free N (IR-14: names are unique per kind); the original text
is not kept; (b) `.attr src "SRC"` (the Yosys form and the plain writer's, `blif.attr:src`) after a cell is
parsed (L-2) and restored on that cell; the `blif.attr:src` attribute is dropped (the reader's
`blif_extras` list loses that key); (c) a cell with no location of its own takes **the first HDL location
of the first of its output pins' nets that has one** (D-5).

**D-5 Cell from output net (BLIF VTR only, best effort).** The VTR dialect writes net names and no cell
names, so a LUT or latch's HDL location is only on its output net. After the nets are restored, a cell
without an HDL location whose first output net (pin order, an output pin with a net) has one gets
`DERIVED{ parents = [the net's SOURCE record, the cell's IMPORTED record] }`. This is correct for the
ABC output the 3D spec produces (a LUT's output net is anchored to the logic that computes it) and is
counted separately from locations that were written for the cell itself (T-3: `inherited`). It never
replaces a location the cell has.

**D-6 Hierarchy.** `hier` is restored only from names (D-1 with L-5). JSON and Verilog attribute forms
carry no hierarchy (X-5).

**D-7 Errors.** Never a failure for a bad location text (L-6); a file that cannot be read is the
reader's own error. The reader's limits (5.3 E-3) apply to the text, and one record holds at most 8
restored locations (W-3's cap; a text with more keeps the first 8 and counts the rest).

## 5. What is lossless and what is best effort (X-1 to X-8)

Lossless means the exit test's "same location": per object kind in a format, where "the cell had an HDL
location before writing", it has the same ones (up to W-3's cap) after reading.

| object | JSON | Verilog (`-netlist`) | BLIF VTR (`--hdl-locs`) | BLIF plain (`--src-attr`) |
|---|---|---|---|---|
| module | lossless | lossless | n/a (no per-model record) | n/a |
| cell (node) | lossless | instance and `always`: lossless; `assign`: line only (X-2) | inherited from output net (X-6) | lossless |
| wire | lossless | lossless (declaration) | n/a (BLIF has bits, not wires) | n/a |
| named net | lossless (one-bit netname) | declared net: lossless; otherwise X-1 | lossless (name) | X-7 |
| unnamed net | X-1 | X-1 | X-1 | X-1 |
| port | via netname | via declaration | not carried (X-8) | not carried (X-8) |

The named exception classes, each counted by the tool (T-3) and none silent:

- **X-1 No carrier.** A net with no netname (JSON), no declaration of its own (Verilog: it is written
  as a bit of another wire or a literal), or no name (BLIF) cannot carry a location. Count reported per
  format; these nets keep the netlist record.
- **X-2 Assign line only.** A cell written as an `assign` has `// file:line`: column, end and later
  locations are lost (the Verilog attribute cannot go there). The first location's file and line are kept.
- **X-3 Cap.** More than 8 distinct locations: the first 8 kept.
- **X-4 Unwritable file name** (W-5).
- **X-5 Hierarchy** in JSON and Verilog attributes (module-relative `hier` of IR section 6 lives in
  names only).
- **X-6 BLIF VTR cells** carry no location of their own: restored by D-5 from the output net, flagged
  `inherited`, correct where the net's location is the cell's and approximate where one net is read by
  or driven by merged logic.
- **X-7 BLIF plain nets** are written under their own names; the plain dialect never names by
  provenance (3E: PLAIN requires short names).
- **X-8 Ports and generators.** BLIF port bits keep their names, and `gnd`, `vcc`, `unconn` generators
  have no location; JSON ports are restored through their netname, and a port with no netname (a
  foreign file) has none.
- **X-9 Constants and writer-added cells.** The port buffers, `.names gnd`, constant drivers and the
  helper `$not` of an OFF-set `$sop` are made by the writer or reader, not by the user's HDL, and have no
  location before or after (3E, the 6.5 class "constant drivers, buffers the writers add").

Locations **gained** on read-back (an object with none before that has one after) are bugs, except the
`inherited` class of D-5; the tool fails on them.

## 7. Tests (T-1 to T-6)

**T-1 Unit** (`test_hdl_loc`): L-1 to L-6 as a table: the forms of L-1; files with `:`, `.`, `-`, `@`,
`|`, spaces; the Windows drive form; numbers at `UINT32_MAX` and over; empty file; `|` splitting; names
of L-5 with `/` in the short name, with `$N`, percent-escaped, reserved-prefix; a printer/parser fixpoint
over 100,000 random locations; W-2 (an `IMPORTED` leaf is never printed; a `DERIVED` record with three
parents prints the `SOURCE` leaves in parent order, deduped, cap 8).

**T-2 Per-format round trips** (unit, hand-built designs with known locations):
- JSON: module, cell, wire, one-bit named net each with locations; write, read, compare all five fields;
  `--keep-src-attr` keeps the string; a malformed `src` stays an attribute with one warning (L-6); a
  Yosys-written `src` (`a.v:3.1-4.10`, and `a.v:3.1-4.10|b.v:5.2-5.3`) restores both locations.
- Verilog: every row of the W-6 Verilog lines; with and without `-netlist`: without it a `src` is an
  attribute and a comment is a comment (T-5); with it the records of D-1; the assign comment lookup on
  two statements on adjacent lines; a trailing user comment `// see a.v:3` after an assign is a location
  by L-1 and so is restored (documented: `-netlist` is for netlists written by tools, question 4).
- BLIF: names (VB-10-legal and not), the collision suffix, `--hdl-locs` off leaves every name byte for
  byte (a golden test over the existing BLIF goldens: read, write, compare unchanged), `.attr src`
  parse, D-5 inherit including a cell with two outputs and a latch.

**T-3 The micro round trip and the numbers** (`tools/loc-check`): for each micro at each level (word:
JSON, Verilog; gate: JSON, Verilog, BLIF VTR and plain; LUT: the same; LPM: Verilog, JSON): elaborate
from the Verilog, run the level script, `dump_locs` (before); write the format; read it back with the
5.3/5.4 options (for Verilog `-netlist -icells`); `dump_locs` (after); compare per `(module, kind,
name)` where `name` is the name as the written file has it. The result per design, level and format,
**and per object kind**:

| column | meaning |
|---|---|
| `objects` | live objects of the kind |
| `had` | objects with a first HDL location before writing |
| `same` | `had` objects whose full location list (to W-3's cap) is equal after |
| `line` | `had` objects whose first location's file and line are equal, but not the rest |
| `inherited` | objects with an HDL location after only through D-5 |
| `lost` | `had` objects with none after, each assigned to one class X-1 to X-9 |
| `gained` | objects with a location after that had none and are not `inherited` (must be 0) |
| `spec_before`, `spec_after` | the specificity of Phase 6.5: median and 90th percentile of distinct HDL
  lines per object, over the `had` cells, before and after |

The tool **fails** when `lost` has an object outside X-1 to X-9, when `gained` is not 0, when the
comparison matched zero objects (as 5.2's review H1), or when a format-kind cell marked lossless in the
table of section 5 has `same + line < had` outside its exceptions. `line` counts are reported, and for
the cells the table marks lossless (JSON; Verilog instances and `always`; BLIF plain) it must be 0.
The totals go in the PR description and in PHASE5's decision; they are Phase 6.5's baseline for "after a

## 8. Risks

- **Reader records as DERIVED (D-1).** If Peter does not accept readers making `DERIVED` records, the
  fallback is one `SOURCE` record per object with the restored locations and the netlist position
  dropped; everything else stands (question 1).
- **`-netlist` mode changes the Verilog reader's record kind** from `SOURCE` to `IMPORTED` for the file's
  own objects: `elab2_prov` (and its `elab1` callers) must take a flag; a missed spot leaves a `SOURCE`
  at the netlist line, which the tool sees as a `gained` location. T-3 and a unit test that reads a
  netlist and checks no `SOURCE` leaf points at it guard this.
- **Name decoding (L-5) false positives.** A user net named `x@a.v:3` would be taken as a provenance
  name; options default off and a netlist-writing tool is the only thing that produces the form. The
  warning (L-6) reports names that look like one but fail.
- **Gate and LUT Verilog is all `assign`s**: its locations are line only (X-2) unless the reader and
  the writer are extended to a column form; the trailing comment is kept by the task statement. The exit test
  is per location (file, line), which X-2 satisfies, and the table says so.
- **Output size.** `src` with 8 locations and columns on every cell grows a JSON by a few percent; the
  cap bounds it.
- **BLIF D-5 flatters coverage.** A cell's inherited location is only as good as its net's; the
  `inherited` column keeps it out of the `same` count, so 6.5 can choose whether to count it.

## 9. Out of scope

location, by design); source-manager buffers (`loc` is 0 in restored records, so no `srcman_chain` text);
SystemVerilog; any pass; EDIF/VQM.

## 13. 5.4f hashed names

Peter's idea: provenance names (`hier/short@file:line`, L-5) can be long; a hash of the provenance can
name the object with a short stable identifier, and the tool can get the full name back. This section is
a spec only (no code yet). Every choice marked **(default)** is an agent default; Peter may override it
(alternatives under "Choices for Peter").

**H-1 Option.** `--name-style hash` on `write_blif` (VTR dialect, next to `short|provenance`),
`write_verilog` (next to its existing name styles) and `write_json` (new `--name-style` with `short`,
`provenance`, `hash`; JSON names today are the IR names). It only renames objects that
`--name-style provenance` would rename, that is objects with an HDL location (W-2); every other name is
written as before. The option writes a name map (H-4); without a map path the write is refused, so a hash
name is never written without a way back.

**H-2 Hash input (default).** The full provenance name exactly as `provenance` style writes it before
any VB-10 or Verilog escaping: `HIER '/' SHORT '@' FILE ':' LINE` with the writer's `$N` uniqueness
suffix when two objects of one kind in one module share the text (L-5, IR-14). The bytes are the IR
strings as stored (UTF-8 as read), no normalisation, no trailing byte, no module name, no object ID, no
pointer. The module is not hashed: the map and the name's uniqueness are per module (IR-14), so equal
text in two modules gives equal hash names, which is fine and keeps names stable when modules move.

**H-3 Hash, width, alphabet, collisions (default).** SHA-256 of H-2 (a fixed, well-specified function,
the same on every platform; implemented in the repo, about 60 lines, no new dependency). Take the first
50 bits (big-endian) and write them as 10 characters of lower-case base32 (`a-z2-7`), prefixed `h`:
`h` + 10 chars, 11 characters, legal unescaped in BLIF (also VB-10), Verilog and JSON. Collision rule:
within one module and object kind, if two distinct full names give the same 10 characters, **both**
take 15 characters of the same hash (then 20, ... up to the 52 characters of the full 256 bits), so the
result does not depend on object order. A hash name that equals a name that is not renamed (a user net
called `habcdefghij`) extends the hash name the same way. Determinism: the output depends only on the
set of full names, never on iteration order, IDs, the host, locale or run (T-hash-2).

**H-4 Name map (default).** A sidecar text file, written by the writer next to the netlist
(`out.blif` gives `out.blif.names`, or the path of `--name-map <path>`), UTF-8, LF lines, no BOM:

```
# odin3-names 1 hash=sha256 width=10
module<TAB>kind<TAB>short<TAB>full<TAB>hier<TAB>file<TAB>line
```

one line per renamed object, sorted by module, kind, short (byte order), so equal designs give equal
files. `kind` is `net`, `node` or `wire`; `short` is the hash name; `full` is the H-2 text; `hier`,
`file` and `line` repeat its parts for tools that do not parse L-5. In each field TAB, LF, `\` and `%`
are written `%09`, `%0A`, `%5C`, `%25`. A reader of the map ignores lines starting `#` after the header,
rejects an unknown version with a located error, and checks that `short` is the hash of `full` at the
header's width (or longer, H-3): a mismatch is a located WARNING and the entry is ignored.

**H-5 Lookup in the tool (default).** A pass `names`:
`names --map <file> --lookup <short>` prints the map line of that name (exit status failure when it is
absent) and `names --map <file> --reverse <full>` prints the short name of a full name. Both are plain
text on stdout for scripts. `names --map <file> --check` verifies every entry (H-4) and reports counts.
Because it is a pass it also works on the CLI as `odin3 -c "names --map out.blif.names --lookup h..."`
and needs no design.

**H-6 Read back (default).** `read_blif --name-map <file>`, `read_json --name-map <file>` and
`read_verilog -netlist -name-map <file>` replace each hash name found in the map with its full name
before anything else, so the rest of the read is exactly the read of a `provenance` write: with
`--hdl-locs` (or `-netlist`) the full names then decode to SHORT, `hier` and a location (D-4, D-3 c). A
hash name that is not in the map stays and is counted; one WARNING per file reports the count and the
first example with its line (L-6). A map entry with no object in the file is ignored. Without the option
a hash name is an ordinary name (nothing changes without options, T-5). Ports are never hashed (their
names are the interface), as in D-4.

**H-7 Tests.** T-hash-1: the SHA-256 and base32 steps against published test vectors and a table of
names with known `h...` results (fixed in the test, so a change of function or alphabet fails). T-hash-2:
write the same design twice, from two orders of construction, and under `LC_ALL=C` and `de_DE.UTF-8`:
byte-equal netlist and map. T-hash-3: a test hook that narrows the width to 1 character forces collisions;
both colliding names extend, the result is independent of object order, no two objects share a name.
T-hash-4: write with `hash`, read with `--name-map --hdl-locs`, write with `provenance`: equal to the
direct `provenance` write (BLIF, Verilog, JSON). T-hash-5: the map round trip, escapes (TAB, `%`, `\`, a
space in a file), a corrupted entry (warning, ignored), an unknown version (error). T-hash-6: `names`
lookup, reverse and check on a written map. T-hash-7: length numbers, measured and reported (not a gate):
bytes of `provenance` against `hash` output on the micros and the 14 small VTR designs.

**H-8 Where the code goes (plan sketch).** 5.4f-a: `src/backends/common/hash_name.{c,h}` (SHA-256,
base32, collision resolution over a set of names) and `name_map.{c,h}` (write, parse, check), with
unit tests; 5.4f-b: the three writers and the `names` pass; 5.4f-c: the three readers. Depends on 5.4a
only (it reuses `odin3_hdl_name` and the provenance-name builder); independent of the other 5.4 tasks.

**Choices for Peter (agent defaults first).** Approved by Peter 2026-10-20: all eight defaults, the spec as written.
1. Hash function: **SHA-256 truncated** (stable, specified, no collisions in practice at 50 bits plus
   the extension rule). Alternatives: xxHash64 (faster, not cryptographic, 64 bits, simpler code but a
   third-party algorithm to carry), FNV-1a 64 (tiny, weaker spread).
2. Width and alphabet: **`h` + 10 base32 chars (50 bits)**. Alternatives: 8 chars (40 bits, shorter,
   collisions common above about 1,000 names so the extension rule runs often), 12 chars (60 bits,
   never extends in practice), hex (longer for the same bits), base36 (mixed case problems in
   case-folding tools are avoided only by lower-case; base36 includes digits first, so a prefix is still needed).
3. Hash input includes the hierarchy and the `$N` suffix **(yes)**. Alternative: location only (`file:line`),
   shorter input but then many objects of one line collide and need a counter anyway.
4. Collision handling: **extend both colliding names**, order independent. Alternative: first object
   keeps the short form and later ones get `$N` (smaller names, but a name then depends on object order,
   so it is not stable when the design changes).
5. Map format: **TSV sidecar next to the netlist, required when hashing**. Alternatives: JSON (heavier,
   one more parser), the map inside the netlist as comments or `.attr` (one file, but BLIF VTR has no
   comment channel that VPR keeps, and a netlist then carries the long names again), no map and a
   recomputation from the design (impossible without the design).
6. Which objects: **only objects with an HDL location, never ports**. Alternative: also hash every
   generated name (`$n12`), which shortens more but hides names a user may recognise.
7. Lookup: **a `names` pass** (CLI and script). Alternatives: a stand-alone `tools/` script (no build
   dependency, but a second implementation of the hash), a flag of `dump_locs`.
8. Read-back option name: **`--name-map`** on the three readers. Alternative: automatic detection of a
   neighbouring `<file>.names` (convenient, but a read then depends on a file the command line did not
   name, against the 5.4 rule that nothing changes without an option).

## 14. v1.1: what the implementation changed, and the numbers (5.4e)

`tools/loc-check` (`loc_check.py`, level scripts `tests/loc/{word,gate,lut,lpm}.script`, CTests
`loc_word`, `loc_lpm`, `loc_gate`, `loc_lut` and, label `sweep`, `loc_micros_<level>`,
`loc_vtr14_<level>`) implements T-3. The rules below are what it does; where they go beyond section 5
the reason is the measurement. The tool pairs objects by `(module, kind, name)` where both names are not
generated, and every other object in a pool per `(module, kind)`: exact location list first, then (only
for the formats that keep a line only: Verilog cells and nets, BLIF VTR nets and cells) first file and
line. The readers renumber generated names (`$c12`, `$n3`), so no other pairing exists.

**Classes the tool assigns (rule, then count).** A lost object gets its class from the format's carrier
table (section 5) and the facts below; an object with no class fails the run.

| X-7 | a named net in plain BLIF |

**What 5.4e found that section 5 did not say.**
- **X-9 objects have a location before writing.** The spec said constant drivers and writer-added cells
  have none before or after. The elaborator gives a constant driver the location of the statement (or
  of the module). They are lost in JSON and the BLIF dialects (no cell is written), and counted as X-9
  with a location.
- **Reader-made constants take the module's location.** `modgained` counts objects with none before that
  have their module's own location after: the literal `1'b0` or `1'b1` that `read_verilog -netlist` reads
  becomes a driver cell and net located at the module, in every Verilog read-back (81 cells, 748 nets and
  12 wires over the micros, 2 and 2 over the VTR14, not 3 as first measured: the first count capped them
  by the objects with no location before). Not a loss; `expect.txt` allows it in `verilog` only, with a
  reason, and `pins.txt` pins the count per design set, level and kind.
- **`inherited` has a second source.** A net with no location before takes the location of a declared
  wire: the JSON reader the netname's, the Verilog reader the declaration's (D-2, D-3). The reader
  renumbers nets, so the net's own wire cannot be told from the dump; the tool counts a net with a
  generated name and the location of a declared wire as `inherited` while a bit of such a wire is
  left (a wire of width n gives its location to n nets, the width read from the JSON file's netnames),
  and a named net only when the wire of its name has that location. Any other surplus net is `gained`.
  The net that was replaced keeps its own loss class (X-1: its statement's location is gone).
- **Reading Verilog splits cells.** A LUT written as an `assign` with a long expression reads back as
  several word cells and nets, all with the cell's line (`bm_expr_all_mod` at the LUT level: 853 cells
  before, 7728 after). They are counted `split` (reported, not a failure) when the first file and line
  equals that of a located cell or net before in the same module; any other located surplus is `gained`.
- **Cap (X-3).** `capped` counts objects with 8 locations before (the dump holds at most 8). It is large
  at the LUT level, where a LUT clumps many statements.
- **Specificity** is the median and 90th percentile of the distinct lines per cell, before and after
  (after: the cells that kept a location).

**The gate (what the tool refuses to hide).** The fix round of 5.4e closed these holes; each has a planted
test in `tests/tools/test_loc_check.py`.
- A lost cell is classed from its type before writing (X-8 port, X-9 constant); a cell dropped from a
  written file is no class, so a writer that drops a non-constant cell fails.
- A module missing from a read-back fails unless `expect.txt` lists it as `absent` for that design, level
  and format, and only Verilog and BLIF VTR may be listed; a listed module that is there, or that a
  present module instantiates, fails too. 286 modules are listed over the sweeps (each is a module no
  instance reaches after `opt` or `flatten`).
- `wrong` (an object that has a location after, different from before) is a separate column and always
  fails; it is never given a class. `lost` is no location after.
- Every located after-object nobody took is `gained` (no longer capped by the objects with no location
  before), unless it is `inherited`, `modgained` or `split` as above. `modgained` fails unless
  `expect.txt` lists the format with a reason.
- `tests/loc/pins.txt` pins the count of every lost class and of `modgained` per design set, level,
  format and kind (a class with no line is pinned at 0). A count above its pin fails; below it the run
  prints "improved, update the pin". `loc-check --print-pins` prints the lines.
- **Verilog cell loss is a lower bound.** The Verilog cells pool by location (exact list, then first file
  and line: X-2), so a cell that lost its location and another that has the same line pair off against
  each other. Over the Verilog read-back, "cells that kept a location" is exact only per module and line.
- **The BLIF rules assume no locations.** RULES gives every BLIF wire and module X-1 or X-8 because
  neither dialect writes a location for them. The tool fails a BLIF wire or module that has a location
  after (`same`, `line`, `inherited`, `gained`), so the day a dialect starts to carry one, the rule is
  revisited instead of silently counting it as kept.
- Without ABC, `loc_gate` and `loc_lut` are registered as a named skip (CTest `Skipped`), so the gap is
  visible in a report.
