# 4.2 to 4.7: arch-driven partial mapping (`partial_map`): design (spec only, for review)

Status: v1 (2026-10-20), **for Peter's review** (a mapping algorithm, DESIGN §12, CLAUDE.md rule
10). Nothing here is coded. Phase 4, items 4.2 to 4.7 (`docs/PHASE4.md`). Rules have IDs so they
can be approved or changed line by line: **S-n** structure, **B-n** generic hard blocks (4.2),
**X-n** multipliers (4.3), **R-n** memories (4.4), **C-n** carry chains (4.5), **F-n** flip-flops
(4.6), **G-n** memory port merge (4.7), **D-n** differences from Parmys, **T-n** tests. The open
questions are in section 12, each with a recommendation. The plan is
`docs/plans/2026-10-20-4.2-partial-map-plan.md`.

The shape of this spec: 4.2 to 4.7 are not six passes. They are one pass, `partial_map`, that
replaces `hardmap` (PHASE4 "Dependencies on Phase 3") by making the constants 3C fixed for the k6
arch come from the arch record of 4.1. Where the record gives the k6 numbers, the output must be
byte-identical to 3C's. Everything new is either an extra input the arch supplies (a different
multiplier width, RAM depth limit, no carry model), or a rule 3C did not have (oversize multiplier
split, generic blocks, FF models, a separate memory-merge pass).

## 0. What the evidence says

1. **Parmys is arch-driven by very little.** Its effective configuration (3C §1) has three numbers
   that come from the arch: the multiplier size is the `multiply` model's port sizes (the maximum
   `num_pins` over its leaves, 4.1 section 0 item 1), the memory depth limit is the largest
   address width of any `*port_ram` leaf (`determine_memory_addr_width` in the VTR script,
   passed as `PPP`), and the existence of the `multiply`, `adder` and RAM models. The other knobs
   (`min_hard_multiplier` 3, `min_threshold_adder` 1, width slice 1, no fracturing) are constants
   of the VTR flow, not arch data. PHASE4 item 4.3 says "threshold from the XML": the XML has no
   such field (question 4).
2. **The two sweep archs exercise different numbers.**

   | | `k6_frac_N10_frac_chain_mem32K_40nm` (Phase 3) | COFFE 22nm 4add 2 chains 20K | `k4_N4_90nm` |
   |---|---|---|---|
   | `multiply` model a, b, out | 36, 36, 72 | 27, 27, 54 (leaves 18x19 and 27x27) | no model |
   | RAM address pins (SP / DP) | 15 / 15 | 11 / 11 (modes 9 to 11) | no model |
   | RAM data pins | 64 | 40 (SP), 20 (DP) | none |
   | `adder` model | yes | yes (two chains in a cluster) | no model |
   | `.latch` only FFs | yes | yes | yes |
   | K | 6 | 6 | 4 |

   Of the 213 archs with a `multiply` leaf, 187 have the 36 square model, 25 the 27 square model,
   1 (`timing/xc6vlx240tff1156.xml`) is 25x18, and 2 (`xilinx/7series_BRAM_DSP_carry.xml`) have
   differently named ports. So the square `WIDTH` template covers 212 of 213 (question 5).
3. **FF models in archs have no standard port names.** Models that are flip-flops use `dff`
   (`C D Q`, `D clk Q`), `dffe` (`D E clk`), `dffr` (`R`), `dffrn` (`RN`), `FDRE` (`C CE D R`),
   `DFF` (`clk data out`), `dffeas` (eleven ports), `scff` (`D DI clk reset`), `fourteennm_ff`.
   Whether `R` is synchronous or asynchronous, and its polarity, is stated nowhere in the XML.
   Item 4.6 cannot be done by reading the arch alone (section 7).
4. **Odin II binds a hard block by model name and port names, and is lenient on widths.** Its
   `create_hard_block` finds the model by name (else the error "Found Hard Block X: Not supported
   by FPGA Architecture"), looks each connected port up by name (else "Non-existant port P in hard
   block X"), pads a narrower input with ground and silently drops the bits of a wider one.
   Parmys registers every model except the four primitives as a Yosys black box with the model's
   maximum port widths (`parmys_arch.cc`), so Yosys's `hierarchy` does the binding: unknown port
   is an error, a width difference is resized with a warning.
5. **Odin III already binds.** Elaboration resolves an instance to a registered cell type by name
   (EL-6), an unknown port is the located error `cell type 'X' has no port 'p'`
   (`elab1_inst.c`), an instance parameter on a parameterless type is an error (2D §17 #78),
   and a width difference is extended or truncated with a warning (`elab2_inst.c`). What is
   missing is the arch side: which cell types are the arch's, and a check that nothing unknown
   reaches VPR.
6. **3C has no FF mapping.** Every FF stays a word cell and `lower` turns it into `$_DFF_P_` plus
   glue (3B §6, decision 19). The only FF-related hardmap code is the `$mem` read-port merge
   (R-8). A memory FF merge exists, so 4.7 is largely a move and a test (G-1).

## 1. Structure (S-1 … S-6)

- **S-1 One pass, `partial_map`.** `hardmap` is extended and renamed, not re-implemented. The
  code moves from `src/passes/hardmap/` to `src/passes/partial_map/` with `git mv` in the first PR
  (a pure rename, no behaviour change), the pass registers as `partial_map`, and `hardmap` stays
  registered as an alias of the same entry for this phase (so the Phase 3 script, `hardmap-diff`
  and the Phase 3 tests keep working). The node attribute key `hardmap` and all node and net names
  stay unchanged, so BLIF, RTLIL and names are byte-identical. Log prefixes change from `hardmap:`
  to `partial_map:` (the Unity tests that quote warnings are updated mechanically in the same PR).
  Test and tool directory names (`tests/hardmap`, `tools/hardmap-check`) are not renamed in this
  phase (question 1).
- **S-2 The rules record.** The hard-coded constants (`ODIN3_HARDMAP_MUL_WIDTH 36`, the RAM address
  limit 15, the RAM data slice 1, `min` multiplier 3, `min` adder 1) move into one `pm_rules`
  struct that every rule reads. It has two constructors:
  - `pm_rules_k6_fixed()`: the 3C values. Used when the design has no arch record (the Phase 3
    script, `read_techlib lib/vtr.o3lib`).
  - `pm_rules_from_arch(arch)`: the values derived from the record (X-1, R-1, C-1, F-2).
  The pass looks for the record with `odin3_design_arch()`. With a record, a `multiply`,
  `adder` or RAM type that the library does not hold is simply "no such block" (S-3), where 3C
  gave the H-3 error.
- **S-3 Absent block means soft, with one INFO line.** If the arch has no `multiply` model, every
  `$mul` is left for `lower`; no `adder` model: every `$add`/`$sub`; no RAM model: every `$mem` and
  every explicit RAM instance. One INFO line per kind and design:
  `partial_map: architecture 'k4_N4_90nm' has no 'multiply' model; 3 '$mul' cells left to lower`.
  Without a record the 3C rule stays: a missing type is the H-3 error.
- **S-4 Phases and order.** Per module, in node-ID order within each phase (3C H-8): bind check
  (B-1), `$mul` (X), explicit `multiply`, `$add`/`$sub` (C), RAM instances and `$mem` (R, G),
  then flip-flops (F). Mapping is transactional per source cell (3C H-7, H-9), unchanged.
- **S-5 Default is Parmys; improvements are options.** Every choice where Parmys has a rule takes
  Parmys's rule by default. Anything better than Parmys is a named option that is off unless given
  (`--mem-width arch`, `--ff-file` on `read_arch`, `--min-mult N`, `--min-add N`). So the Phase 3
  script gives the 3C result with no extra flags, and the Parmys-default policy is met without
  passing the `read_verilog --vtr-compat` flag to a pass (a pass cannot see it). Each option, when
  it changes the result, prints one WARNING per design: `partial_map: --mem-width arch: memories
  are sliced to the arch's widest mode, not 1 bit as Parmys does` (question 2).
- **S-6 Provenance, IDs, ABI.** As 3C H-7: one DERIVED record per source cell, parents the source.
  No IR change, no ABI change. The arch record is read through `src/frontends/arch/arch.h`
  accessors only. New accessors (section 9) are internal.

## 2. 4.2: generic hard blocks by exact port signature (B-1 … B-7)

A **generic block** is a model of the arch that `read_arch` registered as a cell type
(`odin3_arch_model.registered`) and is not one of the four primitives bound to a template (4.1
L-2). Its cell type is `blackbox`, ports in XML order, widths the VPR model sizes (4.1 L-4).
Examples in the corpus: `pcie`, `mult_8`, `dpram_128x8`, `dffe`, `mac_*`.

- **B-1 Binding is by name.** An instance whose cell type name equals a registered model name is
  that model. Elaboration (Verilog), the BLIF reader (`.subckt`) and the techlib already do this;
  `partial_map` adds no second binder. It adds the check in B-3 to B-6 and a report.
- **B-2 The exact signature** of a model is its list of (port name, direction, clock flag, VPR
  width), from the record. "Exact" means a connected port must be a port of the model with the
  model's direction. Widths are decided by B-4.
- **B-3 Unknown port: located error** (existing, kept): `file:line:col: error: cell type 'pcie'
  has no port 'foo'`. It is raised by elaboration or the BLIF reader, and `partial_map` raises the
  same text, located at the node, for a netlist built by other means (a `check`-valid IR cannot
  hold one, so this is a test of the existing check, not new code).
- **B-4 Width difference: pad or truncate with a WARNING, as Odin II and Parmys do.** A narrower
  input is extended with gnd, a wider connection is truncated; both are warned by elaboration
  (existing). No new rule. Recommendation against making it an error: Yosys and Parmys accept it,
  and the hard-block widths VPR derives (the maximum over leaves) are often wider than a design's
  use.
- **B-5 Input port not connected:** tied to gnd with a WARNING (`partial_map: instance 'u' of
  'pcie': input port 'x' is not connected; tied to gnd`). Parmys does this ("Signal is not driven,
  padding with ground"), Odin II pads ground. An unconnected output is fine and silent.
- **B-6 Unknown block with an arch loaded:** an instance of an implicit black box (2D EL-11, a
  `--auto-blackbox` module with no definition) while the design has an arch record, whose name is
  not a model of the arch, is a located error: `partial_map: instance 'u' of 'foo': 'foo' is not
  a model of architecture 'k6_...' (VPR would reject the netlist)`. Odin II gives the same error
  ("Not supported by FPGA Architecture"). Without a record nothing is checked (the netlist-only
  flows of Phase 3 and Phase 6). Option `--allow-unknown-blocks` demotes it to a warning, for
  netlists meant for another tool.
- **B-7 Soft alternative: none, by design.** A generic block has no function, so it cannot be
  made soft. The only soft case is a user module with a body that has the name of a model. That
  is the existing EL-6 error ("has the name of cell type") unless the module comes from a
  `--lib` read, where 2D §3.1a decides by parameter fit. 4.2 changes neither. **Recommendation:
  mismatch is an error (rename the module); no soft binding** (question 11).

Output: a generic block is written as `.subckt NAME port[i]=net ...` with every formal bit (3E
rules); nothing about it changes in `write_blif`. INFO line:
`partial_map: N instances of M generic blocks bound (pcie 2, dpram_128x8 1)`.

## 3. 4.3: multiplier split from the arch (X-1 … X-10)

Base: 3C M-1 to M-7 unchanged, with 36 replaced by `W` (X-1) and the oversize case (X-4).

- **X-1 Width from the record.** `have_mul` is true when the arch has a `multiply` model that
  became the template cell (4.1 L-2), i.e. its ports are `a`, `b`, `out`. `W` is the maximum
  `num_pins` of the model's `a`, and must equal that of `b`: `W = 36` for k6, `27` for COFFE.
  The mapped cell is `multiply WIDTH=W` with `a`, `b` of W pins and `out` of 2W, the unused pins
  `unconn` (3C M-3, M-4, unchanged). Parmys does exactly this (`pad_multiplier`, fixed size,
  fracturing off).
- **X-2 The square-template question (4.1 question 4), resolved: option W1.** Options:
  - **W1 (recommended).** Keep the square `WIDTH` template. COFFE's 18x19 and 27x27 leaves are one
    model of `W = 27`; a `$mul` of any size up to 27 is one `multiply WIDTH=27` with its unused
    pins open, which is Parmys's netlist. Nothing in the library changes. VPR chooses between the
    18x19 and 27x27 modes when it packs. (Not verified in this spec: that VPR packs a
    27-pin-declared block whose used pins fit into the 18x19 leaf. Either way the netlist is legal
    and equals Parmys's. 4.13 shows which.)
  - W2: add `A_WIDTH`/`B_WIDTH` parameters to `multiply`. Rejected: it changes `lib/vtr.o3lib`
    and every golden, BLIF reader path and `fcheck` model, for one arch in 213.
  - W3: for the one asymmetric arch, make the importer emit a non-parametric cell with the
    model's real widths (25x18). A 4.1 importer change, deferred until an arch needs it.
  - **Asymmetric or differently named models** (`a != b`, or ports not `a b out`): `have_mul` is
    false, one WARNING (`partial_map: 'multiply' model of 'xc6vlx240tff1156' is 25x18, not
    square; '$mul' cells are left to lower`), and the `$mul` cells go to `lower`. Parmys pads such
    a model to its two sizes; that is difference D-17.
- **X-3 Threshold.** A `$mul` goes hard unless `max(a, b) < T` and neither is 1, where `T = 3`
  (Parmys's `min_hard_multiplier` as `run_vtr_flow.py` sets it; 3C M-2). The XML has no
  threshold, so `T` is the option `--min-mult N`, default 3 (question 4). The 2x2 case stays soft
  (3C D6); the AND-and-adder form of Parmys remains out of scope.
- **X-4 Oversize operands: split, as Parmys does.** If `a > W` or `b > W`, the `$mul` is
  rewritten into smaller `$mul` and `$add` word cells, and the ordinary rules map those (the
  smaller `$mul` as X-1, the `$add` by the adder rule). This replaces 3C's "wider than 36 stays
  soft" (D7). Let `a0 = W`, `a1 = a - W`, `b0 = W`, `b1 = b - W`. The cases are Parmys's
  (`iterate_multipliers`):
  - both oversize: four products `A0*B0`, `A0*B1`, `A1*B0`, `A1*B1` and, for a square model
    (always true under X-2), two adders for the cross terms and one for the total, exactly
    Parmys's `split_multiplier` `addsmall`, `addsmall2`, `addbig` with the zero fill of the low
    bits. Four multiplies, three adds.
  - only `a` oversize: `A0*B` and `A1*B` plus one adder (`split_multiplier_a`). Two multiplies,
    one add. Likewise only `b` (`split_multiplier_b`).
  - a piece that is still oversize is split again (a worklist, no recursion; CLAUDE.md).
  The hard multiplier count equals Parmys's by construction. The adder bit widths follow the
  zero-fill Parmys uses; **they are fixed by a probe before the rule is frozen** (plan Task 1):
  `$mul` 40x40, 40x8, 8x40 and 80x80 go through Parmys on k6 and COFFE and the multiply and adder
  counts are recorded. If the counts differ from the rewrite, the rewrite changes to match.
- **X-5 Signed, light.** Both-signed `$mul` (the PHASE2 #25 rule): when `Y_WIDTH <= W`, the 3C M-5
  rule (both operands sign-extended to `Y_WIDTH`, unsigned product, low `Y_WIDTH` bits). Otherwise
  the cell stays soft with a WARNING (`partial_map: signed '$mul' 'm' needs Y_WIDTH 36 > 27;
  left to lower`). A signed oversize `$mul` is never split. Consequence on COFFE: a signed
  16x16 (`Y = 32 > 27`) is soft, on k6 it is hard. **Option for Peter (question 7):** the
  correction-term form, an unsigned `a x b` product (when `a, b <= W`) minus `2^a * (sign(B) * A)`
  and `2^b * (sign(A) * B)`, built from `$and` and `$sub` cells. It keeps signed multiplies hard
  at the cost of two subtractors. **Recommendation: not in v1.** Parmys does not handle signed at
  all (it pads with `unconn`), PHASE4 says "light", and soft is correct.
- **X-6 Explicit `multiply` instances.** 3C M-6 unchanged with `W`: `WIDTH = 2` becomes a `$mul`,
  `2 < WIDTH < W` is padded to `W` (warning), `WIDTH = W` untouched. `WIDTH > W` was an error;
  it now becomes the equivalent `$mul` and is split (X-4) with the same warning, as Parmys does.
- **X-7 No `multiply` model:** S-3. The `$mul` cells go to `lower` (3B's multiplier). Parmys
  would build a partial-product array from hard adders when an `adder` model exists (D-19).
- **X-8 Provenance and names.** Split pieces are named `<cell>.<role>` with roles `m00 m01 m10
  m11 add0 add1 add2` and share the one DERIVED record of the source cell (3C H-7).
- **X-9 Fracturing is not included.** Parmys's `split_hard_multiplier` (pick the smallest leaf
  that fits) is off in the VTR flow. The record already lists the leaves and modes (4.1 P-5), so
  it can be added later without a record change (question 8).
- **X-10 Determinism and budget:** 3C H-8, H-9 apply. The split multiplies the cell count by up to
  4 per level; the budget check runs per source cell.

## 4. 4.4: memories from the arch (R-1 … R-8)

Base: 3C R-1 to R-12 unchanged with the constants replaced.

- **R-1 What is available.** `have_sp` / `have_dp` are true when the record has a
  `single_port_ram` / `dual_port_ram` model that took the template (4.1 L-2). Neither: S-3, the
  `$mem` and any RAM instance go to `lower`.
- **R-2 Depth limit `D` (the address bits of one block).** `D` is the largest `num_pins` of any
  input whose name contains `addr` on any leaf using a `*port_ram` model (VTR's
  `determine_memory_addr_width`; Parmys passes it as `PPP`). It is one number for SP and DP, as in
  the VTR flow. k6: 15. COFFE: 11 (the 2048x10 modes). The 3C depth split (R-2 there: recursive
  on the lowest address bit, registered select, D4) uses `D` instead of 15.
- **R-3 Width slice `w`.** Default 1 (Parmys `split_memory_width = 1`), one slice per data bit.
- **R-4 Mode-aware width slice (option `--mem-width arch`, off by default, question 9).** For a
  memory with `A` address bits after the depth split (`A' = min(A, D)`), `w` is the largest data
  width among the leaf modes of the model whose address width is at least `A'`. COFFE SP: modes
  (9, 40), (10, 20), (11, 10), so a 256-word by 32-bit memory is one block with `DATA_WIDTH` 32,
  `A' = 8`, `w = 40`, and a memory of 2^11 words by 10 bits is one block. A memory wider than
  `w` is cut into slices of `w` bits (the last one narrower). DP uses the DP leaves. The depth
  split of R-2 is unchanged. One WARNING per design when the option changes anything (S-5).
  Rationale: with `w = 1`, `LU32PEEng` needs 5,251 RAM blocks; with the arch's widest mode far
  fewer. The option is a mapping algorithm for Peter to review; the default does not use it.
- **R-5 Address padding.** Address bits above the memory's `A`, up to `D`, are `unconn`
  (3C R-4). The node parameters are `ADDR_WIDTH = D`, `DATA_WIDTH = w`. The BLIF writes all
  formal bits, so VPR sees `D` and `w` pins.
- **R-6 Port patterns, merge, INIT, soft cases:** 3C R-5 to R-12 unchanged (D5, D8, D9, D12 to
  D15 keep their meaning). A memory that needs a DP block when the arch has only SP (or the
  reverse) follows 3C R-10 and then R-11 ("no fixed-subset mapping") if the needed model is
  missing: soft, with the warning.
- **R-7 Explicit RAM instances** (`single_port_ram #(.ADDR_WIDTH(16))`): legalised to `D` and `w`
  as `$mem` is. An instance with fewer address bits than `D` is only padded. The 3C bound of 31
  address bits stays.
- **R-8 Soft fallback size.** A `$mem` left to `lower` because the arch has no RAM model can be
  huge. `lower` has its own node caps (3B §11); `partial_map` adds only the INFO line of S-3 with
  the total bits (`3 memories, 98,304 bits left soft`). On `k4_N4_90nm` that is the whole memory
  set; Parmys also builds these from flip-flops.

## 5. 4.5: carry chains from the arch (C-1 … C-5)

Base: 3C A-1 to A-9 unchanged. The chain shape (dummy head, `n + 2` adders, `a + ~b + 1`) is
Parmys's fixed form; it does not depend on the arch beyond the model.

- **C-1 The carry model** is the model named `adder` with ports `a b cin cout sumout` that took
  the template (4.1 L-2, `odin3_arch_has_adder`). Nothing is guessed from other names: a model
  such as `carry_follower` or `lut_cin` is a generic block (B), never a carry chain. `have_adder`
  false: every `$add`/`$sub` goes to `lower` (S-3). On k4_N4 this is the case.
- **C-2 Chain sanity check (WARNING only).** The record holds the pack patterns (4.1 P-7). If the
  arch has an `adder` model but no `pack_pattern` reaches the adder leaf's `cin` and `cout`, one
  WARNING: `partial_map: architecture 'x' has an 'adder' model but no carry pack pattern; chains
  may not pack`. Parmys does not check.
- **C-3 Two chains (COFFE).** A cluster has two chains with their own start and end. This is a
  packing matter. Each `$add` is already its own independent chain with a dummy head; VPR assigns
  chains to sites, and a chain longer than one cluster continues through the `directlist`
  (`adder_carry`). `partial_map` does nothing different for one chain or two. INFO prints the
  number of `pack_pattern` names reaching `cin` as a fact, not a rule.
- **C-4 Threshold:** `min_threshold_adder` is 1 (3C A-1); the option `--min-add N`, default 1.
- **C-5 What is not done:** comparator and `$neg` chains (3C S-1), the use of `cin` as a global
  carry (`adder_cin_global`, Parmys default false).

## 6. 4.6: FF feature matching (F-1 … F-8)

This is the least determined item (section 0 item 3). The proposal is a declared table, not a
guess, and everything is off unless the table is given.

- **F-1 The plain FF.** The `.latch` leaf (rising-edge D, Q, clk) is in every sweep arch. It has no
  enable and no reset, so today's path stands: `lower` turns every FF family cell into
  `$_DFF_P_` plus enable and reset glue (3B §6, decision 19: asynchronous controls become
  synchronous, warned once). On the two sweep archs 4.6 changes nothing. The 4.6 test on a
  "plain" arch is therefore the existing `lower` path run through `partial_map`.
- **F-2 FF models are declared.** A model such as `dffe` is a generic block unless the user says
  what it is. `read_arch --ff-file FILE` reads declarations, one per line:
  `ff dffer D=D Q=Q CLK=clk EN=E+ SRST=R+0` (`NAME ROLE=PORT ...`). Roles: `D Q CLK`; optional
  `EN`, `SRST`, `ARST`, each with a polarity (`+` active high, `-` active low) and, for resets, the
  value they force (`0` or `1`); `SET`/`CLR` as a reset of value 1/0. The names must be ports of
  the model with the right direction (else a located error at the declaration's line). A declared
  FF model is generated as a `hard` cell with a `seq` statement carrying that function (4.1
  templates are the precedent), so the simulator and `equiv-check` understand it. A model listed
  but absent from the arch is a located error. A shipped example `lib/ffmap/z1000.ffmap` covers the
  one real arch with `dff dffr dffe dffer` (question 13).
- **F-3 Match.** For each word FF cell of `$dff $dffe $sdff $sdffe $sdffce $adff $adffe` (not
  `$aldff*`, `$dffsr*` or latches; they go to `lower`), choose the declared model, among those with
  the cell's clock polarity, that needs the least glue. Features of the cell: enable (`EN`), sync
  reset (`SRST`, per-bit reset value), async reset (`ARST`, per-bit value). A model **supports** a
  feature when it declares it with the same value. The cost is the number of features the model
  lacks. The plain `.latch` (cost = all features) is the fall-back and means "leave the cell to
  `lower`". A tie takes the model declared first.
- **F-4 Glue for what the model lacks** is the equation `lower` uses (3B §6.1): enable as
  `EN ? D : Q`, sync reset as `SRST ? v : D`, reset over enable for the combined cells (3B's
  question 1 ruling). An unsupported **async** reset becomes synchronous with the decision 19
  warning. The glue is word cells (`$mux`) in front of the model's `D`, left for `lower`. A
  polarity mismatch on a control inserts a `$not`. A reset value that the model cannot force on
  some bits (a `1` reset on a model that only forces `0`) is glue on those bits only; bits are
  grouped by value.
- **F-5 Result.** One hard cell of the model per bit, named `<cell>.ff<i>`, `Q` driving the
  cell's Q bit. Initial values: a hard FF has none in BLIF (`.subckt`), so a defined `init` on a
  mapped bit is dropped with a WARNING naming the register (as 3C R-12 does for memory INIT).
  Bits with no defined `init` are exact.
- **F-6 Position.** After the memory phase, so a read-port register is merged into a `$mem`
  first (G-1); before `lower`, which leaves hard cells alone.
- **F-7 Default.** No `--ff-file` means no FF model exists and nothing is mapped. Parmys never maps
  to FF models (D-22), so the default is Parmys.
- **F-8 Reference.** Yosys `dfflegalize` is the model for the legalisation ladder (what to do for
  each missing feature); only the subset above is ported.

## 7. 4.7: memory port merge (G-1 … G-5)

Base: the code of 3C R-8 and R-9 (`mem_merge.c`), which maps only micros today (3C finding 4).

- **G-1 A separate pass `memory_merge`** (RTLIL view, no processes) runs the existing R-8 function
  and nothing else: an asynchronous read port whose data bits all feed one `$dff` (or `$dffe`
  with a constant-1 enable, a `RD_EN` otherwise) of one clock becomes a synchronous port;
  otherwise the address-register merge when no write port is on that clock (D12). The result is
  one `$mem` with `RD_CLK_ENABLE` set, observable with `write_rtlil`. `partial_map` calls the
  same function itself when a `$mem` still has an asynchronous port, so a script need not run
  `memory_merge`; the pass exists so the merge can be tested and used by itself. The merge code
  moves unchanged from `mem_merge.c` into a shared file, with no behavioural edit. This is what
  keeps the k6 identity (T-2).
- **G-2 What "registered writes" means.** Item 4.7's text says registered reads **and writes**.
  2D already emits `$mem` write ports as clocked ports (EL-27); a register in front of a write
  port cannot be merged, because that would write one cycle early. Yosys's `memory_dff` merges
  only read-side FFs. So nothing is added on the write side (question 15).
- **G-3 No `ram_style`.** The attributes `ram_style`, `rom_style`, `ramstyle`, `logic_block`,
  `block_ram` and `no_rw_check` on a memory are ignored, one WARNING per design:
  `partial_map: memory 'm': attribute 'ram_style' is ignored; mapping follows the architecture`.
  Parmys ignores them silently. The mapped netlist equals the one without the attribute.
- **G-4 Unchanged soft cases:** asynchronous port left, several clock domains, falling edge,
  `OFFSET != 0`, non-constant `RD_EN` (D9; the arch's RAMs have no read-enable pin), split write
  enables.
- **G-5 Diagnostics:** `memory_merge: N read ports merged (M data, K address), L left
  asynchronous`.

## 10. Tests (T-1 … T-9)

Every test that writes files creates its own temporary directory (`mkdtemp` in C, `mktemp -d`
under `${TMPDIR:-/tmp}` in scripts, `tempfile` in Python) and removes it. None names a fixed path.

- **T-1 Rule tests** (Unity, hand-built IR plus arch records from XML strings through
  `odin3_arch_read_text`): one test per rule ID above, asserting exact pins, parameters and a FULL
  `check`, and the before and after simulation (1E) where there is no RAM. Small fixture archs
  in `tests/unit/data/arch/`: a 27-wide square multiplier, a 25x18 multiplier, RAM D = 11 with
  three modes, no models at all, generic blocks, an FF-model arch with a declaration.
- **T-2 The k6 identity check (the exit criterion for the shell PR and for every later PR).**
  Three tiers.
  1. *Always (CI, no `VTR_ROOT`).* `partial_map` with no arch record against `hardmap` (the alias,
     same code) on the 26 hardmap micros of `tests/hardmap/micros.txt` and the in-repo fixtures
     `tests/hardmap/*.v`: `cmp` of `write_blif --vtr` and of plain `write_blif`. It guards the
     refactor and the alias. The first 5 designs of `tests/hardmap/vtr_designs.txt` join it when
     `VTR_ROOT` is set (tier 2).
  2. *Local (needs `VTR_ROOT`).* The same inputs with `read_arch` of
     `k6_frac_N10_frac_chain_mem32K_40nm.xml` in place of `read_techlib lib/vtr.o3lib`: `cmp`
     equal to tier 1. It proves that the record yields `W = 36`, `D = 15`, `w = 1`, `T = 3`.
  3. *At PR time (controller heavy run, release build, smallest design first).* A baseline binary
     built from main `f761d530` (a throwaway worktree and build under a `mktemp -d` directory)
     runs `hardmap` and the new binary runs `partial_map` on the 19 designs and the micros; the
     BLIFs are `cmp`ed. It is expected to be byte-identical on every input where 3C does not log
     "left soft" for a multiplier wider than 36 (no design in the 19 has one) and where `.prov`
     files differ only in the pass name. A difference is a failure, not a list entry.
  The tool is `tools/partial-map-check/identity` (a script around `odin3`, `cmp` and the
  `phase3_pre_abc.script` plus the `lower`-and-after tail); plan Task 3.
- **T-3 Micros on each sweep arch.** `hardmap-diff --arch X --golden-root G` generalised
  (`partial-map-diff`, a copy of the same Python driver with the arch passed through to a
  `read_arch` line in the script): the 26 micros per sweep arch against that arch's Parmys golden,
  `netlist-compare` identical or `equiv-check` equivalent, hard-block counts equal. Expect files
  per arch (`tests/partial_map/diff_expect_<arch>.txt`) list, each with a D-n ID, the differences
  of section 8 only.
- **T-4 Golden diffs.** The Parmys goldens for the COFFE and k4 archs are a **controller
  heavy-run step** (`tools/run-oracle.sh` per arch; hours; lanes idle; smallest first; not run by
  this lane). Until they exist, T-3 skips (exit 77) and the rule tests (T-1), the identity (T-2)
  and `fcheck` (T-6) carry the evidence. For k4_N4, Parmys may not finish designs with `$mul` or
  memories (no hard block; unverified); those micros are listed `no-golden` and checked by T-6.
- **T-5 Probes first** (plan Task 1): Parmys on oversize multipliers (X-4) and on a COFFE
  memory (R-2: D = 11 and the slice counts), recorded in a probe README as in 3C.
- **T-6 Functional check.** `tools/vtr-qor` `fcheck` (Verilator random check of RTL against the
  mapped BLIF with the hard-block models) on the micros for each sweep arch. This is the
  arch-independent evidence that does not need a Parmys golden.
- **T-7 4.7 test:** a registered-read RAM micro through `memory_merge` yields one `$mem` with the
  read register merged (a Unity test on `write_rtlil` output and an `equiv-check` against the
  input), and a `ram_style` micro gives the same netlist plus the warning.
- **T-8 4.6 test:** FF micros (`$dffe`, `$sdff`, `$adff`, enable plus reset) on the fixture FF
  arch with a declaration: simulated equivalent (1E) before and after; counts of mapped models
  and glue; the same micros on a sweep arch (no declaration) unchanged from the `lower` path.
- **T-9 Gates.** `tools/lint.sh` clean, `check` FULL before and after, the OOM sweep on each
  transaction (3C H-9), `docs/PASSES.md` rows (`partial_map`, `memory_merge`, the `hardmap`
  alias).
