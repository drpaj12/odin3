Purpose (hub purpose hierarchy): Leman Russ III fab-side Trojan detection needs a forward flow whose cells
keep a provenance chain to HDL, and a layout-to-HDL join that works without names. RQ (Leman Russ): does an
Odin III -> OpenROAD -> GDS flow keep provenance to every placed cell, and what does physical design add or
change? Measures: share of layout cell instances with an HDL chain; census of inserted / resized / removed /
renamed cells per step; LVS clean; join rate of the extracted layout back to HDL. The v1.4 feature makes
those measures a product of the tool (one flow, one file format), not of a spike.

## 1. Scope

In: (1) the silicon flow (Odin III to GDS and back to recovered cells) as an Odin III flow; (2) project-file
meta: named flows, ordered steps, provenance relationship per step; (3) provenance step files written at
every stage, by the silicon flow and by the existing FPGA flows (LUT / VTR); (4) schema docs, JSON Schema,
the Loki contract; (5) docs (README, manual chapter, release notes).

Out: any change to the C passes or the IR; a Liberty importer in core (gatemap G-1 stands); Yosys or ABC
outside Odin III's own `abc`; the Trojan-in-layout check (Leman Russ, next lane); camouflage / split
manufacturing implementation; analogue or timing signoff (STA, RC extraction); gf180 / IHP PDKs.

## 3. The silicon flow

### 3.1 Stages and steps

Stage = what kind of object a step produces. Step = one tool run. The silicon flow `silicon-sky130`:

| Step id | Stage | Tool | Reads | Writes |
|---|---|---|---|---|
| `read` | `hdl` | odin3 | HDL | the HDL spans the design is made of (added in implementation) |
| `elab` | `ir` | odin3 | HDL | `proc; flatten; opt; lower` word and gate cells with spans (`elab_locs.txt`) |
| `map` | `gates` | odin3 | IR, `lib/sky130hd.o3lib` | `gates.v`, `rtl.blif`, `gates.blif`, `locs.txt`, `prov.csv` |
| `equiv` | `gates` | `tools/equiv-check` | `rtl.blif`, `gates.blif` | `equiv.txt` (check, no new objects) |
| `netlist` | `gates` | `tools/silicon/clean_netlist.py` | `gates.v` | `clean.v` (attributes stripped, names legalised; the name map is `prov.csv`) |
| `place` | `placed` | OpenROAD | `clean.v`, LEF, Liberty | one instance dump per OpenROAD sub-step, `place.def` |
| `route` | `routed` | OpenROAD | placed design | `route.def`, `final.v`, `final.odb` |
| `gds` | `gds` | KLayout python module | `route.def`, LEF, PDK GDS | `top.gds` (no names), `top.named.gds` (names as GDS properties, kept as a measured variant) |
| `extract` | `extracted` | Magic | `top.gds` | `ext_hier.spice`, `ext_flat.spice`, per-cell `.ext` |
| `lvs` | `extracted` | Netgen | extracted SPICE, `final.v`, PDK SPICE | `lvs.log` (check) |
| `recover` | `recovered` | `tools/silicon/join.py` | `.ext` hierarchy, `route.def`, `prov.csv` | `join.csv`, `join.json` |

Proven in the spike: all steps, two designs (comparator, 17 cells; 4-bit shift register with clock, 12 cells),
equivalence yes, LVS "Circuits match uniquely", DRC report empty, join 17/17 and 15/15, wall time about 4 s
per design. Not proven: bigger designs, designs with constants (`conb_1` is a two-output cell and is not in
the library; constants stay `1'b0` in the netlist and OpenROAD must accept them or a TIE step is needed:
open question O-1), `restructure`, setup timing repair, a full PDN with met5 straps.

### 3.2 What the driver is

Tcl and Python under `tools/silicon/`, called from the project flow, not from C:
`liberty_to_o3lib.py`, `clean_netlist.py`, `openroad_flow.tcl` (+ `openroad_flow.py` runner), `klayout_gds.py`,
`magic_extract.tcl` (+ runner, own cwd per run because Magic writes `.ext` files into its cwd), `netgen_lvs.py`,
`join.py`, `census.py`. No Yosys, no LibreLane, no ORFS synthesis; if a package drags Yosys in, it stays unused
and the install notes say so. Driver parameters come from the project (`flow-var`, section 4): clock port,
utilisation, density, routing layers, PDK path.

### 3.3 Tool discovery

Order: `--tools DIR` (or `ODIN3_SILICON_TOOLS`) with `bin/`, then `PATH`. PDK: `--pdk DIR` or `PDK_ROOT`+`PDK`
(`sky130A`). The runner probes each tool once (`openroad -version`, `magic --version`, `netgen -batch quit`,
`python -c "import klayout.db"`), writes versions into the index, and stops with exit 2 and a list naming what is
missing and how to install it (the manual chapter has the commands). `--steps a,b` runs a subset (e.g.
`elab,map,equiv` needs only Odin III: the library and the mapped netlist with its step files work without any
external tool).

### 3.4 Install (to be documented with the commands verified in the spike)

User-space only: micromamba, `micromamba create -n eda -c litex-hub -c conda-forge --override-channels magic
netgen`, `... -n orcond ... openroad`, a venv with `pip install klayout ciel`, `ciel enable --pdk sky130 -l
sky130_fd_sc_hd <version>`. Disk about 2.4 GB for tools and PDK, a few MB per small design. `micromamba clean
-a -y` after install.

## 4. Project-file meta

Added to the `.o3proj` key table (precedent: `testbench`, project-testbench design). Words follow the existing
rules; a quoted word keeps blanks. Paths are relative to the project file.

```
schema 2
tool openroad required openroad    version-arg -version
tool klayout  required python      module klayout.db
tool magic    required magic       version-arg --version
tool netgen   required netgen
tool pdk      required sky130A     env PDK_ROOT
flowdef silicon-sky130 description "Odin III to GDS, SKY130 hd"
step silicon-sky130 map     stage gates    tool odin3    needs elab    out netlist=gates.v
step silicon-sky130 place   stage placed   tool openroad needs netlist in netlist=clean.v out def=place.def
provlink silicon-sky130 place from map  kind name  key instance
provlink silicon-sky130 place from place kind physical_origin  scope inserted
flow-var silicon-sky130 clock_port Clock
```

| Key | Form | Meaning |
|---|---|---|
| `schema` | `schema <n>` (first statement only; 1 or 2) | project schema; absent = 1; `n` > 2 is `unsupported_schema` |
| `tool` | `tool <id> (required\|optional) <exe-or-module> [version-arg <a>] [module <m>] [env <VAR>]` | an external tool a flow may need; recorded, never run by the core |
| `flowdef` | `flowdef <name> [description <text>]` | opens a flow; name is an identifier, unique |
| `step` | `step <flow> <id> stage <stage> tool <tool-id\|odin3> [needs <id>[,<id>...]] [in <role>=<path>]... [out <role>=<path>]... [args <text>]` | one ordered step; `needs` names earlier steps of the flow; `stage` one of `hdl ir gates luts packed placed routed gds extracted recovered` |
| `provlink` | `provlink <flow> <step> from <prev-step> kind <k> [key <field>] [scope <s>] [confidence <c>]` | how the objects of `<step>` relate to those of `<prev-step>`; `<k>` is a link kind (section 5.3); several per step allowed (one per scope) |
| `flow-var` | `flow-var <flow> <name> <value>` | a parameter for the driver (clock port, utilisation, ...) |

Reader checks (located errors, same class as today): `schema` not first (`syntax`), duplicate flow or step id,
`step` before its `flowdef` (`syntax`), `needs` naming an unknown or later step, unknown `stage` or link kind
(`unknown_option`), `tool` id unknown in a `step`, `provlink` naming a step not in the flow, or whose `from` step comes after the linked step (a step may link to itself, kind `physical_origin` only), a repeated id in one `needs`, a repeated `flow-var <flow> <name>`. Cycles are
impossible because `needs` must be earlier. All checks run at parse time; nothing is looked up on disk except
(`in`/`out` paths are recorded as written, relative to the project file; they are not checked on disk by the reader).

`dump_project` JSON gains, only for a schema 2 file with at least one flow or tool statement (a bare `schema 2` file dumps as schema 1): `"schema": 2`, `"tools": [...]`,
`"flows": [{"name", "description", "vars", "steps": [{"id","stage","tool","needs","in","out","args",
"provlinks": [{"from","kind","key","scope","confidence"}]}]}]`. A schema 1 file dumps exactly as today.

Compatibility matrix (tested): schema 1 file, v1.4 reader: unchanged output; schema 2 file, v1.3 reader:
`unknown_key` at line 1 (SI-5); `schema 3`, v1.4: `unsupported_schema`.

The FPGA flows get the same description in a shipped project include: `flows/vtr.o3proj.inc` is not a new file
type: `odin3_flow.py` generates the equivalent `flowdef` for its own run (stages `hdl ir gates luts packed placed
routed`) into the run record, so Loki reads one description whichever flow ran. A user project may write its own.

## 5. Provenance step files

### 5.1 Layout of a run directory

```
<out>/prov/index.json
<out>/prov/<NN>-<step>.json          header of one step
<out>/prov/<NN>-<step>.objects.jsonl objects of the step, one JSON object per line
```

`NN` is the step order. Every flow step that creates or changes objects writes a pair; check-only steps (`equiv`,
`lvs`) write a header with `objects_file: null` and a `check` field (`{"name","result","detail"}`). The index is
written last; its sha256 list lets a reader detect a partial run.

### 5.2 Contents

`index.json`:
`{"schema": 1, "kind": "odin3-prov-index", "flow": "silicon-sky130", "design": "<name>", "top": "<module>",
"odin3_version" (first line of `odin3 --version`, empty if no binary can be run), "project": "<relative path or null>", "tools": [{"id","version","path_alias"}],
"steps": [{"id","stage","file","objects","sha256","objects_sha256","count","needs","tool":{"id","version"}}]}`.
Paths are relative to `<out>/prov`; no absolute path, home path or user name is written (the same privacy rule
as the run record). Design files are listed with sha256.

Header `<NN>-<step>.json`: `{"schema":1,"step","stage","tool":{...},"inputs":[{"role","path","sha256"}],
"outputs":[...], "links":[{"from_step","kind","key","confidence","scope"}], "counts":{"objects":N,
"by_kind":{...},"by_origin":{...},"by_link_kind":{...}}, "census": {...}|null, "check": {...}|null,
"map": {"file","sha256"}|null}`. `census` (steps `place`, `route`, `gds`): the per-step table
{kept, moved, resized, inserted(by kind), removed, renamed} against the previous step.

Object line: `{"id":"gates:o3__c10","stage":"gates","kind":"cell","name":"o3__c10","type":"sky130_fd_sc_hd__nor2_1",
"origin":"hdl","links":[{"to":"ir:$c10","kind":"name","confidence":"exact"}],"attrs":{...},"src":[{"file","span"}],"recs":["r12","r40"]}`.

- `id` = `<stage>:<local id>`, unique in the run. Local ids: IR and gates stages use the Odin III object name; placed and
  routed use the instance name; `gds` uses `<master>@<x>,<y>` (name-free); `extracted` uses Magic's use id plus the
  same `@x,y`; `recovered` uses the DEF component it joined to or `unjoined:<master>@x,y`.
- `kind`: `module block stmt net port cell`. FPGA stages also `lut`, `ble`, `clb`, `site` (levels of the existing table).
- `origin`: `hdl` (has a chain to source), `physical:<step>` (inserted by that step: `tap`, `cts_buffer`, `repair_buffer`,
  `hold_buffer`, `fill`, `decap`, `antenna`, `tie`), or `unknown`. A cell never has `origin: hdl` without a `links` entry
  reaching an `hdl` or `ir` object.
- `links`: to objects of the **previous stage** (the `recovered` stage also links by `location_match` to the `routed` instance it joined; a join may reach back) (not necessarily the previous step); empty only for `origin` physical or
  for the first stage. A `resized` cell has `attrs.resized_from` (previous master).
- `src`: HDL spans as `dump_locs` prints them, present on the first stage that has them (`ir`, `gates`), for the reader that has
  no name map; `recs`: record ids `r<n>` into the v2 name map named by the header `map`, when one exists.
- `attrs` by stage: `placed`/`routed`: `master, x, y, orient, status`; `gds`: `master, x, y, orient`;
  `extracted`: `master, x, y, orient, ext_id`; `recovered`: `def_comp`, `join` (`matched|unmatched|ambiguous`).

### 5.3 Link kinds (the relationship vocabulary used in `provlink` and in `links[].kind`)

| Kind | Meaning | Confidence |
|---|---|---|
| `id` | same object id across a step that only copies (writers, `equiv`) | exact |
| `name` | same instance name in the previous stage (OpenROAD keeps names) | exact |
| `cone` | coarse link of a mapped gate to the cone of RTL objects it replaces (gatemap G-2, the existing `coarse_records`) | medium |
| `fine` | per-object record (name map `R`/`C` chains) | exact |
| `join` | an optimisation join (the existing `Q`/`K` lines) | stated by the record |
| `resize` | same name, other master | exact |
| `physical_origin` | no HDL parent; the object was inserted by the named step | exact (it is a label, not a link) |
| `location_match` | name-free: same master and same location as an object of the previous stage | high when unique, `ambiguous` otherwise |
| `structural_match` | recogniser: matched by cell structure (later; transistor recovery without library cells) | stated by the matcher |

Confidence is one of `exact high medium low ambiguous` plus an optional number `score`.

### 5.4 Existing FPGA flows

`odin3-flow` with `--prov` writes the same files. v1.4 writes exactly: step `read` (stage `hdl`, constructs from `C` lines),
step `map` (stage `luts`, BLIF cells from the `O`/`N` lines, link `fine` with `recs`), and, when `odin3-prov-post` added `A`
lines, step `place` (stage `placed`, one `site` object per atom, link `name` to the LUT object, `recs` from the atom).
Not written in v1.4 (the map has no per-BLE or per-CLB data and the `ir` cells are not in the BLIF map): stages `ir` and
`packed`, `join` links from `Q`/`K`, and design `inputs` in the index (the map and the BLIF are `outputs` of the steps, with
sha256). Source file names are relative to the design directory (base name when outside it). `tools/flow/prov_steps.py` reads the v2 map and the flow
directory; it never reparses HDL. It runs as the last step of `odin3-flow` when `--prov` is set (and as
`odin3-prov-steps FLOW_DIR` standalone), so a past run can be converted. Without `--prov` no step files are written (the flow
output is unchanged).

## 6. Schema docs and the Loki contract

- `docs/user/provenance-files.md`: the layout, every field, each link kind, one worked example per flow (silicon comparator,
  VTR), how to resolve an object back to HDL ("walk links until stage `hdl`/`ir`, then `src` or `recs` into the map").
- `docs/schemas/prov-index.schema.json`, `prov-step.schema.json`, `prov-object.schema.json` (JSON Schema draft 2020-12), checked by
  a test that validates the shipped fixtures; no third-party validator in the tool (a small stdlib checker `tools/silicon/
  schema_check.py` implements the subset used).
- `docs/user/project-flows.md` (or a chapter in `inputs.md`): the new keys, with the compatibility rules.
- Loki contract (also in the Loki docs, which are the reader's side): Loki reads `index.json` (`schema`, `flow`, `design`, `top`,
  `steps[].id/stage/file/objects/sha256/count`, `tools[].id/version`), each header (`stage`, `links`, `census`, `check`,
  `map`), each object (`id`, `stage`, `kind`, `name`, `type`, `origin`, `links[].to/kind/confidence`, `attrs.master/x/y`, `src`,
  `recs`). Unknown fields are ignored; unknown `schema` > 1 is refused. Loki's `resolve(object)` walks `links` back to `hdl`/`ir`
  and returns the chain and the weakest confidence on the way. Loki PR (part D) adds `loki/prov_steps.py` and tests on a fixture
  made by this flow.
