## 0. What the repo already gives, and what it does not

**Already there.**
1. The writer (`odin3_json_write`). Its output is the Yosys schema: `creator`, `modules`; per module
   `attributes`, `ports`, `cells`, `netnames`; per cell `hide_name`, `type`, `parameters`,
   `attributes`, `port_directions`, `connections`. Bits are `"0" "1" "x" "z"` or the integer net ID + 1
   (ordinary nets only). INT parameters are 32 binary digits (64 beyond the `int32` range), BITS
   parameters their digits MSB first, STRING parameters the text with one trailing blank when the text
   is only `01xz ` (Yosys's rule), COVER parameters rows joined by `\n`. `$sop` of at most 6 inputs is
   written as `$lut`, a wider one as Yosys `$sop` (`DEPTH`, `TABLE`) with a helper `$not` for an
   OFF-set cover. Latch `INIT` is an `init` attribute of the Q net. Declared black boxes and hard
   models are modules with attribute `blackbox`. `src` is `"file:line.col"` of the first leaf location.
2. The registry: `$lut` is a first-class cell (`ir/lut.h`), `$and` ... `$tribuf`, `$mem`, `$memrd`,
   `$memwr` and the word flip-flops are registered with Yosys parameter and port names, so most Yosys
   word and gate cells need no translation, only a lookup by name.
3. The BLIF reader's construction path for modules, port nodes, port wires and nets, and the
   implicit-black-box mechanism, which this reader reuses. The 5.2 option and validation style.
4. `tools/equiv-check` (BLIF), `opt_equiv.Checker` (RTLIL), `tools/icells-check` (the shape of a
   round-trip tool with level scripts and an expect file).

**Not there.**
1. A JSON parser. Yosys's own is recursive and has no limits; a hostile or merely deep file would
   overflow the stack or allocate without bound. CLAUDE.md forbids recursion over data of unbounded
   depth.
2. Anything that maps a bit number to a net, a netname to a wire, a `$` type name to the registry, or
   a parameter string back to a typed value (INT, BITS, STRING, COVER).
3. A way to choose the top module (Odin III's writer writes no `top` attribute; Yosys writes
   `"top": "00..01"` in the module attributes).
4. Yosys fixtures in the repo that CI can read: CI has no Yosys 0.55, so the Yosys-written inputs of T-3
   are committed, with the script that makes them.

## 1. The pass (J-1, J-2)

**J-1** `read_json [--top NAME] [--auto-blackbox] <file>` reads the file into an
empty design (as `read_blif`: INVALID_ARG for a design that has modules). One pass run `read_json` (the
pass manager's run, as `odin3_blif_read_in`). The global `--top` applies after reading, as for
`read_blif`; the pass option `--top` is the same value and wins when both are given. `-` is not
accepted (the reader needs two passes over the bytes, M-0).

**J-2** C API: `odin3_json_read(design, path)` and `odin3_json_read_in(ctx, path)`, declared in
`src/frontends/json/reader.h` and documented there (purpose, ownership, failure modes). The public ABI
(`include/odin3/odin3.h`) is not changed: readers are internal entry points as `odin3_blif_read` is
(question 8).

## 2. Parsing (E-1 to E-5)

**E-1 Iterative parser.** A hand-written parser with an explicit stack of open containers; no
recursion, whatever the nesting. The depth is capped at 32 (the schema needs 8: file, `modules`,
module, `cells`, cell, `connections`, port, bits); a deeper file is the located error
`JSON nested deeper than 32`. The parser builds a compact value tree in an arena (`util/arena`): each
value is a 32-byte node (kind, first child, next sibling, key, string or number payload, and the
line and column of its first byte). Objects keep key order; the schema walk (section 4) needs the file
order of `ports`, `cells` and `netnames` (M-1, M-9).

**E-2 Grammar.** RFC 8259 JSON: objects, arrays, strings, integers, `true`, `false`, `null`; blanks are
space, tab, CR, LF. Beyond what Yosys accepts: `\uXXXX` is decoded to UTF-8 (Yosys fails above 127;
Odin III's writer writes non-ASCII as is, and Yosys writes control bytes as `\u00XX`), a surrogate
pair is combined, a lone surrogate and `\u0000` are errors (names are C strings in the strtab). Numbers
are integers in the range of `int64`; a fraction or exponent is an error (Yosys turns a real into a
string, which no schema field has). A byte-order mark is skipped. Invalid UTF-8 in a string is kept as
is (names are byte strings, PHASE1 #2); a NUL byte in a string is an error. Trailing commas are an
error (Yosys skips commas anywhere; Odin III is strict because the writer never needs them). Anything
after the root value but blanks is an error. A duplicate key in one object is an error (Yosys keeps the
last; no writer produces one, so it is a corrupt file).

**E-3 Limits.** Each is a named constant in `src/frontends/json/limits.h`, a located error when
exceeded, and changeable only by a test hook (`odin3_json_test_set_limits`):

| limit | value | why |
|---|---|---|
| file size | 1 GiB | the value tree is about 3 times the text; 1 GiB of JSON is about 150 M cells of 1 line each, far beyond any design here |
| string length | 1 MiB | a `$mem` INIT parameter is the longest legitimate string |
| nesting depth | 32 | E-1 |
| bits in one port, netname or connection | `ODIN3_READER_MAX_WIDTH` (2^20) | the BLIF reader's cap, one short file never allocates more |
| bits over all connections of one cell | `ODIN3_READER_MAX_TOTAL_WIDTH` (2^22) | as the BLIF reader |
| cells, netnames, modules | 2^24 each (the IR's ID space is `uint32_t`) | clean error instead of an ID overflow |

A bit number is a label, never an index: it is looked up in a `u64map`, so `4294967295` costs the same
as `2` (E-5).

**E-4 Located errors.** Every error is logged as `path:line:col: message` with the JSON path of the
value in the message, as `modules.top.cells.$c5.connections.A[3]`, and returns ODIN3_ERR_PARSE
(malformed JSON, schema violation, unknown type, width mismatch), ODIN3_ERR_IO (file cannot be read or
changed between the passes), ODIN3_ERR_NO_MEMORY (out of memory), ODIN3_ERR_INVALID_ARG (NULL argument,
non-empty design). Reading stops at the first error; the design may hold part of the file, so the
caller destroys it (as `read_blif`). The error table is in section 7.

**E-5 No unbounded structures on the IR side.** The bit-to-net map is a `u64map`; the schema walk and
the round-trip tools traverse the value tree and the IR with explicit worklists (CLAUDE.md). A test
builds a chain of 1,000,000 cells and one 200,000-deep `[[[...` file, and checks the depth error in
bounded stack (T-6).

## 3. The schema accepted (J-3 to J-9)

Yosys 0.55 `write_json` writes (and `jsonparse.cc` reads) the structure below. `read_json` accepts
every member listed; members not listed are ignored (J-8).

**J-3 Root.** An object. `creator` (string) is recorded in the run information (`creator=...`). `modules`
(object, required unless the file is empty of modules, which is an error: "no modules"). `models` (the
`-aig` AIG tables) is ignored with an info line.

**J-4 Module.** An object with: `attributes` (object, optional; M-11), `parameter_default_values`
(object, optional; kept as module attributes `parameter_default:<NAME>` so Yosys parameterised
modules are not silently reshaped; no Yosys 0.55 netlist the micros produce has it), `ports` (object),
`cells` (object), `memories` (object, M-13), `netnames` (object). Every member is optional (jsonparse
accepts each as absent).

**J-5 Port.** `direction` (`input`, `output`, `inout`; required), `bits` (array; required), and
optional `offset`, `upto`, `signed` (numbers; non-numbers ignored, as Yosys).

**J-6 Netname.** `hide_name` (number; read, not used: a name starts with `$` iff it is hidden, which
the writer derives from the name), `bits` (required), `offset`, `upto`, `signed`, `attributes`.

**J-7 Cell.** `hide_name` (as J-6), `type` (string, required), `parameters`, `attributes`,
`port_directions` (object name to direction; used to type connections of a type the registry does not
have, M-8, and to cross-check those it has, E-6), `connections` (object name to array of bits,
required), `model` (the `-aig` tag, ignored).

**J-8 Unknown members** of any object (a key not named above) are skipped with the value still parsed
and its limits applied; one info line per file counts them by first key. This is how graph-export
keys and Yosys additions pass.

**J-9 Odin III keys (Phase 6.3).** Keys beginning `odin3_` at the root, in a module, a cell or a
netname are reserved for Phase 6.3's export. 5.3 skips them (J-8) and counts them in the info line;
the dispatch is one table `odin3_json_ext_keys[]` in `reader_ext.c` that 6.3 fills with handlers, so
6.3 adds no change to the walk. A value of `odin3_version` at the root that is a number above 1 is a
located error ("written by a newer Odin III": a reader of version 1 must not silently drop
semantics); absent or 1 is accepted.

**Values (shared by attributes and parameters), J-10.** A value is a string or an integer. Yosys's
rule (`json_parse_attr_param_value`) is applied unchanged for a value of an attribute or of a
parameter the registry does not type: a string of only `0 1 x z` is a bit vector (MSB first); a
string of `0 1 x z` followed by blanks only is the string with one trailing blank removed (so it is not
read as bits); any other string is a string; an integer is a 32-bit vector (signed when negative). A
typed parameter (M-6) takes the registry's kind instead. An array or an object as a value is an error.

## 4. Mapping to the IR (M-0 to M-14)

**M-0 Two passes.** Pass 1 declares every module, its ports and its attributes, and every module that
has attribute `blackbox`; pass 2 reads netnames, cells and memories. A cell can therefore name a module
defined later in the file (Yosys sorts modules by name, so a parent often precedes its child). The
file is read into the tree once; "two passes" are two walks of the tree, not two reads of the file.

**M-1 Modules.** One IR module per JSON module, in file order. Names are kept as written. A module
with attribute `blackbox` (any non-zero value) and no cells becomes a black-box cell type, as
`read_blif` makes one from `.blackbox` (`odin3_celltype_declare_blackbox`), with its ports in port
order and widths from `bits` (a registered library type of the same name must match by port name,
direction and width, as the BLIF reader requires: it is then that cell, `--lib` style). A module with
attribute `top` non-zero is the top (a Yosys-written file); else `--top`; else the modules no
other module instantiates, black boxes excluded: exactly one is the top (Odin III's own files), none or
several is the located error `cannot choose a top module: ... (use --top)` listing the candidates.

**M-2 Ports.** Each `ports` entry in file order is a port node of the type `$port_in`, `$port_out` or
`$port_inout` by `direction`, with a port wire named by the key, width `len(bits)`, `offset`/`upto`
giving msb and lsb (`upto`: msb = offset, lsb = offset + W - 1; else lsb = offset, msb = offset + W - 1;
the exact inverse of the writer), `signed` from J-5. A port may also appear in `netnames` with the same
name (Yosys and Odin III both write it); that entry then adds its attributes and a second `bits` check
(E-7) to the same wire and creates no second wire.

**M-3 Bits and nets.** A bit is `"0" "1" "x" "z"` (a constant net of the module, created at first use)
or an integer (one ordinary net per distinct integer in the module). Nets are created **in ascending
bit-number order**, then the constants in the order 0, 1, x, z as they are first used. This makes
net IDs a function of the file's bit numbers alone, which R-3 needs, and it does not depend on a
hash order. A bit of `"x"` in an **input** connection is the constant x; in an **output** connection a
constant is an error unless it is `"x"` or `"z"`, which is the open pin (Yosys writes a driven
constant as an alias, not on an output port).

**M-4 Netnames.** Each entry in file order is a wire named by the key, width `len(bits)`, shape as M-2,
its bits bound to the nets of M-3. Two netnames over the same integer are aliases of one net: the first
is the net's primary wire, the others alias wires (IR-14 alias names; as the BLIF reader's port nets).
A netname of one bit is a wire of one bit, not a net name: a net the Odin III writer wrote with a
bare net name (`write_net_netname`) reads back as a one-bit wire, and writes back to the same text
(R-4). A netname over a constant bit binds the wire's bit to the constant net.

**M-5 Cell types.** Resolution order for `type`:
1. a module of the file (an instance; parameters are the module's `parameter_default_values` overridden
   by the cell's `parameters`, as `read_blif` takes a model's parameters);
2. a registered cell type of that name, including tech-library cells loaded before the read
   (`read_techlib`) and `$` internal cells (`$and`, `$add`, `$lut`, `$dff`, ...: the writer writes them
   by these names, Yosys too);
3. a black-box module of the file (M-1);
4. otherwise the located error `cell 'x' has type 'T', which is neither a module of the file nor a
   registered cell type (use --auto-blackbox to treat it as a black box)`. With `--auto-blackbox` it is
   an implicit black box (as `read_blif` makes one, all its ports 1 bit INOUT unless `port_directions`
   gives the direction, and the widths its connections give) and a **WARNING** names the type once. A
   `$`-prefixed name is not exempt: an unregistered internal cell is wrong silently if it is treated
   as a black box, so under `--auto-blackbox` it is still a warning per type and the netlist is not
   equivalent to its source (stated in the warning).

The Yosys 0.55 internal cells the registry does not have, and so the error of rule 4, are: word level
`$alu $lcu $fa $macc $macc_v2 $shift $sshl $pos $eqx $nex $bmux $demux $bwmux $bweqx $divfloor
$modfloor $slice $concat $buf $ff $anyconst $anyseq $allconst $allseq $anyinit $initstate $mem_v2
$memrd_v2 $memwr_v2 $meminit $meminit_v2 $fsm $assert $assume $cover $live $fair $check $print
$equiv $specify2 $specify3 $specrule $get_tag $set_tag $original_tag $overwrite_tag $future_ff`; gate
level `$_ANDNOT_ $_ORNOT_ $_NMUX_ $_AOI3_ $_OAI3_ $_AOI4_ $_OAI4_ $_MUX4_ $_MUX8_ $_MUX16_ $_TBUF_` and
the flip-flop and latch families of `$_DFF*_`, `$_SDFF*_`, `$_DFFE_*`, `$_DFFSR_*`, `$_ALDFF_*`,
`$_DLATCH*_` other than `$_DFF_P_`, `$_DFF_N_`, `$_DLATCH_P_`, `$_DLATCH_N_` and `$_FF_`. This list was
made by comparing `kernel/celltypes.h` with the registry (`src/ir/cells`); Task 3 regenerates it by
script from the registry at implement time so it cannot go stale, and the table is in the spec's v1.1.
`$scopeinfo` is dropped with one info line per file (it is debug scoping Yosys 0.55 writes unless
`-noscopeinfo`, and carries no function). The micros through the T-3 fixtures use only registered types
(question 5: the flows are chosen so).

**M-6 Parameters.** For a registered type, each parameter in `parameters` must be a parameter of the
type (unknown name: error, the 5.2 V-1 wording) and is typed by the registry:
- INT: a string of `0 1` of width 32 or 64 is the two's-complement integer (width 32 sign-extended); an
  integer is itself; a shorter binary string is zero-extended; any other string is a located
  `cannot read '...' as an integer`;
- BITS: a string of `0 1 x z` (J-10) or an integer (as 32 bits) is the bit vector; the writer's `""`
  for the empty vector (5.2 V-5) reads as zero length;
- STRING: the string; the Yosys trailing blank (J-10) is removed only when the text, blank included,
  is of `01xz ` characters only;
- COVER: rows joined by `\n`, each `<inputs> <output>` (or only `<output>` for a cover with no inputs).
A parameter the type declares and the cell omits takes the registry default (as the Verilog reader does
for an instance), and the type's `verify` hook failing is a located error on the cell (5.2 V-6). A
parameter whose value changes a port width is applied before the connections are checked (E-7). For an
instance of a module of the file or an implicit black box there is no registry to type the values:
they are node attributes named `parameter:<NAME>` (J-10 typing), as the Verilog reader's `param_attr`
sets them, and the writer must write them back as parameters (R-5).

**M-7 Connections.** For each connection `P` of a cell of a registered type or module: `P` must be a
port of the type (unknown port: error, the 5.2 V-2 wording); the number of bits must equal the port's
width at the cell's parameters (error, **no resize**: read-back must not reshape a netlist, 5.2 V-3);
unconnected ports (absent from `connections`) stay open, as the Verilog reader leaves them. The
`port_directions` of a registered type are checked against the registry (E-6). A bit used on an input
pin that no cell, port or netname drives is allowed (an undriven net; `check` rule 11 warns, as it does
for open LPM pins today).

**M-8 Cells.** One node per cell in file order (node ID order = file order, as the BLIF reader's IR-16),
named by the key (the writer's generated `$c<ID>` keys are names on read-back: a node that was
unnamed is named `$c<ID>` afterwards, which the writer writes back as the same key; this is a gen1 to
gen2 difference, R-2). A cell with a name that is also a netname is two objects with the same name in
different kinds, which IR-14 allows. `$sop` (Yosys's, with `DEPTH`, `TABLE`, `WIDTH`) is read as the
Odin III `$sop` cover: rows are decoded from `TABLE` (2 bits per input per row, `01` = 0, `10` = 1,
`00` or `11` = don't care, as Yosys `cellaigs`/`$sop` and as `lut.c` `write_table` writes them), and a
Yosys `$sop` whose output feeds only a `$not` the writer added (the helper of an OFF-set cover) is NOT
merged back: it reads as `$sop` + `$not`, equivalent, and R-3 holds because it writes the same way. A
`$lut` is the registered `$lut` (`WIDTH`, `LUT`). A `$dff` and the bit cells keep their `INIT`
from the Q net's `init` attribute (M-11).

**M-9 Order.** Ports, wires, nets and nodes are created in file order (nets: M-3). This is why Odin
III's writer, which writes in ID order, reads back into the same relative order.

**M-10 Provenance.** Every object gets an IMPORTED record `{file = path, line, col}` of its defining
JSON value (a port, netname, cell, module: the key's position) in the `read_json` run, as `read_blif`
does. Nothing else is recorded in 5.3: `src` is M-12.

**M-11 Attributes.** Module, netname and cell `attributes` become IR attributes (`odin3_attr_set`) on
the module, the wire (of the netname) or the node, by J-10's typing: a bit vector is BITS, a string
STRING, an integer INT. Exceptions: `init` of a netname whose bits are driven by a registered latch or
bit flip-flop Q pin sets that cell's `INIT` parameter (the writer's inverse: one char per bit, MSB
first; the writer writes INIT 2 and 3 both as `x`, so `x` reads as 3 (unknown), the registry default,
stated in R-2) and the attribute is not kept; `init` on a netname
no Q drives stays an attribute. A repeated key cannot occur (E-2).

**M-12 `src`.** Kept as the STRING attribute `src` on the object and written back as written: the
writer's rule "a user `src` replaces the provenance `src`" makes R-3 hold. 5.4 converts it to a
provenance record (decision in the 5.4 spec, L-8); the reader has one switch for it,
`odin3_json_opts.keep_src_attr`, false in 5.3's PR and true after 5.4's.

**M-13 `memories`.** Entries (`width`, `size`, `start_offset`, `attributes`, `hide_name`) are checked
(numbers, non-negative) and kept as module attributes `memory:<name>:<field>`; they are not an IR
object (a registered `$mem` carries its storage). A Yosys `$memrd` or `$memwr` (v1) that names a
memory is read as the registered `$memrd`/`$memwr` when the registry has the port and parameter set,
else the error of M-5 rule 4. Yosys 0.55 `write_json` after `memory_collect` writes `$mem_v2`, which is
not registered (M-5): memory designs from Yosys are out of the T-3 set until a Phase 4 item registers
`$mem_v2` (question 6).

**M-14 Hierarchy.** A cell whose type is a module of the file is an instance node; the reader sorts
nothing and flattens nothing. Cycles in the module instantiation graph (a module that contains itself,
directly or not) are the located error `module 'A' instantiates itself through 'B'`, found by an
explicit worklist.

## 5. Provenance

M-10 only: IMPORTED records at JSON positions. 5.4 restores HDL locations from `src` beside it.

## 6. The round trip (R-1 to R-6)

Generations: gen1 is the netlist Odin III wrote from; `write_json(gen1)` is file 1; `read_json(file 1)`
is gen2; `write_json(gen2)` is file 2; gen3 and file 3 likewise.

**R-1 Fixpoint.** file 2 equals file 3 byte for byte, for every micro at every level (T-2). This is the
"write, read, write identical" requirement. It is **not** claimed between file 1 and file 2 in general,
for the reasons of R-2, because the first read renames and reshapes what the IR kept implicitly. (The
same ruling as 5.1's decision 7: the fixpoint is generation 2 to 3.)

**R-2 What gen1 to gen2 changes, and only this:** (a) unnamed nodes, wires and nets get the names the
writer generated (`$c12`, `$n34`); (b) a named net with no wire reads as a one-bit wire (M-4); (c) net
IDs are renumbered (M-3), so integer bits differ; (d) a `$sop` is a `$lut` (the writer's own
conversion; at most 6 inputs) or a `$sop` plus helper `$not` (wider); (e) latch `INIT` 2 reads as 3
(the writer writes both as `x`); (f) a node of a hard or black-box type keeps its parameters but a
declared-model parameter set is re-derived from the widths. `file 1` and `file 2` differ in the integers
of (c) and in these names only; the test normalises exactly (a) to (c) when it shows a diff (T-2).

**R-3 Equivalence.** gen1 and gen2 are equivalent (T-2, T-3): word and LPM levels by the RTLIL
`Checker`, gate and LUT levels by `equiv-check` on `write_blif`, the same split and for the same
reasons as 5.2 (the RTLIL writer has no bit storage cells, `write_blif` no word cells). A LUT-level
netlist round trip is **identical** under `netlist-compare` (a `$lut` is written as `.names` through
`odin3_blif_isop` in both generations); a gate-level one is identical when its covers are canonical
and is otherwise equivalent (R-2 d). PHASE5's "identical under `netlist-compare` on the micros and the BLIF
goldens" holds exactly for covers that survive the `$sop` to `$lut` to `.names` conversion unchanged
(`.names` rows from ABC and from `lower` do, being isop covers); the test reports each design as
identical, equivalent-only (with the reason `cover form`) or failing, and only the last fails the test
(question 3).

**R-4 Text identity of one-bit netnames.** The writer writes a one-bit wire and a bare net name with the
same member set apart from `offset`/`upto`/`signed`, which one-bit scalar wires never have, so R-1 holds
through M-4.

**R-5 Parameters of module instances** read as attributes `parameter:<NAME>` and are written as
parameters (jw `ODIN3_WATTR_PARAMETER` is the `.param` role; the writer maps `parameter:` keys likewise,
Task 3 step 4 checks the writer and fixes the mapping if it writes them as attributes: that would
break R-1 for hierarchical designs, and is a writer fix, reported).

**R-6 Yosys-written JSON** reads (T-3) and its netlist is equivalent to the RTL it came from; its text
is not reproduced by Odin III (Yosys names, hide_name flags, sort order, `creator`).

## 7. Errors (E-6 to E-8) and their text

The table (each is `path:line:col: modules.<m>.<...>: <text>`, tested by name in T-5):

| code | condition |
|---|---|
| E-6 | `port_directions` of a registered type disagree with the registry for a port |
| E-7 | `bits` length of a connection does not equal the port's width; a port and its netname disagree in width or in bits |
| E-8 | duplicate port, cell or netname key in one module is E-2; the same name for a port and a cell is allowed; a net driven by two ordinary drivers is refused as `read_blif` refuses it (PHASE3 #36, check rule 4's test) |

A net with a second driver is checked after each cell as in the BLIF reader, because it makes the IR
invalid (`check` rule 4); an `$tribuf` output and inout pins are exempt as there.

## 10. Risks

- **Bit-number order (M-3) and R-1.** The fixpoint depends on creating nets by ascending bit number and
  constants last. If `odin3_node_create_connected` or the wire binding creates nets itself in a
  different order, R-1 fails by renumbering; Task 3's first test is R-1 on a 3-cell file, so this shows
  at the start, and the fix is in the reader's order.
- **`$sop` to `$lut` (R-2 d)** makes gen2 different from gen1 for BLIF-sourced designs; the tool says
  so explicitly (R-3). If Peter wants `$lut` read back as `$sop`, that is a reader option, not a
  default (question 3).
- **Yosys fixtures drift.** The fixtures are committed text; a Yosys rebuild (docs/ORACLES.md, Peter's
  call) changes them, and `gen.sh` records the version it used in a `VERSION` file the test checks.
- **Registry gaps (M-5).** A real Yosys netlist with `$alu`, `$macc`, `$mem_v2` or the wider gate
  families is refused. That is correct for 5.3 (every type read is one Odin III has a rule for) and a
  visible limit for Phase 6.1/6.3 users; the plan lists it as follow-up work, not a hidden skip.
- **Memory.** The value tree is about 3 times the text (E-3 table); a 200 MB JSON needs about 600 MB. A
  streaming walk is possible later and does not change the format; not needed for the micros and the 14
  small VTR designs.

## 11. Out of scope

HDL locations (5.4); Phase 6.3's keys other than skipping them (J-9); a JSON writer change beyond what
5.4 lists (the R-5 check is the only possible one); `-aig` models; Yosys cells not in M-5's registered
set; `$mem_v2`; reading JSON from stdin; SystemVerilog; any pass.

## 12. Open questions (agent defaults taken; Peter may override)

1. **Reader shape.** (a) a DOM of the whole file, two walks (this spec); (b) a streaming reader that
   handles one module at a time. **Recommend (a)**: the schema is order independent in Yosys's own
   writer (modules sorted by name, a parent before its child), the 14 small VTR designs are a few MB,
   and (a) reuses the located-error path of the tree; (b) is a later optimisation behind the same API.
2. **Fixpoint generation.** (a) gen2 to gen3 byte identical, gen1 to gen2 equivalent and normalised
   (R-1, R-2); (b) gen1 to gen2 byte identical (would need the writer to write what the IR does not keep:
   unnamed objects, net IDs). **Recommend (a)**, the same ruling as 5.1's decision 7: the IR does not
   keep generated names or sparse net IDs, and making it keep them is an IR change.
3. **"Identical under `netlist-compare`".** PHASE5 5.3 says the round trip is identical on the micros and
   BLIF goldens. (a) report identical, equivalent-only (cover form) or failing; only failing fails
   (R-3); (b) require identical, and read `$lut` back as `$sop`; (c) add a `netlist-compare --lut-canon`
   mode. **Recommend (a)**: `.names` covers from ABC and `lower` are isop covers and survive; a
   hand-written non-minimal cover would not, and (b) changes what a Yosys `$lut` is read as for the sake
   of a comparison tool.
4. **Top selection.** (a) `top` attribute, else `--top`, else the unique uninstantiated non-black-box
   module, else error (M-1); (b) always require `--top`. **Recommend (a)**; and no writer change to
   emit a `top` attribute in 5.3 (the unique root rule recovers Odin III's own files). If Peter wants the
   writer to emit it, it is one line and a JSON golden change, listed as a 5.4 option (5.4 question 7).
5. **Unregistered Yosys cell types.** (a) located error, `--auto-blackbox` makes an implicit black box
   with a warning (M-5); (b) always an implicit black box with a warning, as `read_blif` does for `$pow`;
   (c) a translation table of Yosys cells to Odin III cell sets (`$alu` to `$add`/`$sub`, ...).
   **Recommend (a)**: (b) hides a wrong netlist behind a warning, and (c) is real work that belongs
   with the Phase 4 and 6.1 items that need it, not the reader.
6. **Memories from Yosys.** (a) `$mem_v2`, `$memrd_v2`, `$memwr_v2` stay unregistered (M-5, M-13), the T-3
   set excludes memory designs; (b) register them now. **Recommend (a)**: a registry change is an IR
   change, Peter's review (rule 10), and the 5.3 exit test names the micros, not memories.
7. **LPM level in the round trip.** (a) included when `--lib lib/lpm.o3lib` is given, else listed as
   skipped by name; (b) not tested. **Recommend (a)**, cheap, and shows the declared black-box module
   reads back as the library cell.
8. **Public ABI.** (a) internal entry points only (`odin3_json_read` in `src/frontends/json/reader.h`,
   as `odin3_blif_read`); (b) add `odin3_read_json` to `include/odin3/odin3.h`. **Recommend (a)**: no
   Phase 5 item needs the C ABI to read, and an ABI addition is Peter's call (D6/D8).
9. **Strictness (E-2).** (a) strict RFC 8259 plus the `\u` extension (this spec); (b) Yosys's lenient
   grammar (commas anywhere, any whitespace). **Recommend (a)**: nothing in the schema needs (b), and a
   corrupt file should be an error with a line and column.
10. **Limits.** The values of E-3 (1 GiB, 1 MiB, 2^24 objects). **Recommend** as written; they are
    constants in one header and a test hook, easy to change if a real design needs more.

## 14. v1.2: the gate-level flip-flop families and `$N` parameters (follow-up, Peter approved)

- **M-5, registry.** The 68 gate-level flip-flops `$_DFFE_<c><e>_`, `$_DFF_<c><r><v>_`,
  `$_DFFE_<c><r><v><e>_`, `$_SDFF_<c><r><v>_`, `$_SDFFE_<c><r><v><e>_`, `$_SDFFCE_<c><r><v><e>_`
  (Yosys 0.55 `simcells.v`) are registered, appended after `$lut` (`src/ir/cells/dffx.c`, list in `dffx.h`;
  `docs/IR.md` IR-8). `$_DFFSR_*`, `$_ALDFF_*`, `$_SR_*` and the latch families with a reset stay
  unregistered (the error of rule 4). The M-5 list of v1.1 shrinks accordingly.
- **Consumers.** The simulator has a hook for each. `lower` rewrites them as it does the word flip-flops of
  the same shape (an asynchronous reset becomes synchronous, PHASE3 decision 19, with the same warning,
  report and `--async error`), so a gate-level netlist read from a file reaches `write_blif --vtr`; the VTR
  writer still refuses an un-lowered one (E1b, E5). `write_rtlil` has no form for them (as for
  `$_DFF_P_`, their INIT). `opt`'s order walk treats them as storage. `opt` otherwise treats them as plain cells (`odin3_ff_is_ff` is false: no
  opt_dff, no INIT handling) until `lower`; this is safe, only unoptimised. `fsm` counts `$_SDFF*` as sequential.
  The plain BLIF writer refuses them with a located error (no `.subckt` of an undefined model); the Verilog
  writer writes them as an instance of the simcells module of the same name; `flatten` copies them as any cell. The ABC adapter treats them as cut cells.
- **M-6, positional parameters.** A parameter `$1`, `$2`, ... (Yosys's spelling for the `#(...)` of a cell it
  could not resolve) of a hard cell, black box or module that has no parameter of that name is kept as the
  attribute `parameter:$N` (J-10 typing) and written back as the parameter (R-5). It is not bound to the
  type's declared parameters. The fixtures `adder_hard_block`, `hard_adder_cin_propagation` and
  `multiply_hard_block` still do not read: Yosys's unresolved cell has the width of its connections
  where the registered library cell has fixed ports (no resize, M-7), and `multiply` is connected by position.
- **T-3.** `tools/json-check` writes the read-back of a BLIF level after `lower`, and compares the
  fixture with Yosys's own reading after `dfflegalize` (Yosys's BLIF holds the cell as a `.subckt` that
  equiv-check cannot read). `lower` runs before the BLIF read-back only when the source holds one of the 68 types
  (a read-back without them is written exactly as before, so `lower` cannot hide a reader difference).
  Yosys cannot legalise an asynchronous reset to a plain flip-flop, so those rows
  are `unproven` in `tests/json/expect.txt`.
