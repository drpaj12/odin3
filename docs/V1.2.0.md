## 1. Current state (file:line, v1.1.1 main `0b90fff9`)

### 1.1 What a record holds

- A record has `kind` (SOURCE, IMPORTED, DERIVED), `run`, `op`, `locs`, `ast`, `hier`, `parents`
  (`src/ir/prov.h:120`). Records are immutable and hash-consed; SOURCE and IMPORTED identity is
  every field except `op`, DERIVED identity includes `run` and `op` (`src/ir/prov.h:80-86`,
  `docs/IR.md` IR-12, IR-13). Record IDs grow in creation order, so every parent is older than its
  child (`src/ir/prov.h:23-26`). A repeated parent in a DERIVED record is kept once
  (`src/ir/prov.h:99-100`).
- The elaborator makes SOURCE records per AST node: wire to its declarator, cell to the expression
  that made it, `$proc` to its `ALWAYS`, each action, case and switch to its statement
  (`docs/specs/2026-10-11-2D-elaboration-design.md` section 10, EL-45; code
  `src/frontends/elab/elab2_wires.c:94` `prov_for`, `src/frontends/elab/pg.c:474` `pg_stmt_prov`,
  `src/frontends/elab/pg_always.c:648`). The record stores the node's own span, the node's ID in
  the elaborated store (`ast`) and `hier`. **When the node sits in an inlined function or task, the
  record also stores the call site as a second location** (`elab2_wires.c:94-101`, the `req->call`
  branch): a SOURCE record with `ast` set and two locations is a call-site record.
- **SOURCE records are flat.** The record of `q <= d` inside `if (en)` inside `always` carries the
  span and `ast` of the assignment only; no parent edge reaches the record of the `if` or of the
  `always` (`src/frontends/elab/pg.c:479-480` makes each record from one node and one scope; SOURCE
  has no parents, `src/ir/prov.h:120-129`). The nesting lives only in the AST, reachable through
  `ast` and `odin3_ast_parent_index_build`, which picks the parent by span containment
  (`src/ast/ast.h:421-428`).
- `hier` holds the specialization name and **named** generate and block scopes only: an unnamed
  scope is skipped (`src/frontends/elab/elab2_wires.c:81`, `rec->name != 0`). So an unnamed `if` or
  `case` is not a level in `hier`; and `hier` is module-relative until `flatten` adds the instance
  path (`docs/IR.md` IR-12, `src/passes/flatten/prov.c:33-62`, `odin3_flatten_derive` at `:65`).
- Restored locations (`read_verilog -netlist`, `read_json`) make a SOURCE record with `ast` 0 and
  up to `ODIN3_HDL_LOC_MAX` (8) locations (`src/frontends/hdl_restore.c:42-43`), plus a DERIVED
  record with the SOURCE and the base record as parents (`:46-48`); BLIF readers make IMPORTED
  records (structural only).

### 1.5 The exact gaps

1. **An unnamed `if` or `case` is not a level.** No SOURCE record points at its parent
   (1.1); `hier` skips unnamed scopes (`elab2_wires.c:81`); a `proc` mux points at the switch and
   case records but not at the `always` (`docs/specs/2026-10-11-2E-proc-design.md:898-906`).
2. **Only the first SOURCE leaf is printed.** Names, the map entry and the timing join use
   `locs[0]` of one leaf (`prov_name.c:9-27`); the others exist only via `--src-attr` (BLIF PLAIN),
   JSON `hdl`, Verilog `src`, capped at 8.
3. **Joins are not labelled.** Merge, CSE and ABC regions make multi-parent DERIVED records
   (1.2) but nothing says that distinct HDL constructs were blended, which pass blended them, or
   which constructs.
4. **No operation class.** Refine, rewrite and coarsen are not recorded and cannot be guessed (1.2).
5. **ABC bulk fallback.** Over budget, one record covers the whole run and every new LUT carries
   it (`src/passes/abc/prov.h:66-75`): a LUT then has every cell of the run as an ancestor. Norns
   sees this as "its budget makes whole runs share one record" (`scripts/build_words.py:18`).
6. **No records after Odin III.** BLE, CLB and site are not in the IR or the BLIF; V1.1.1's
   attribution works at atom level only.
7. **Records and the AST layer are not exported.** Neither the chain, nor `hier` of a record, nor
   the run and op, nor the AST, reaches a file or the Python API; the AST is gone by write time.
8. **Netlist-derived records have no AST** (`hdl_restore.c:42-43`, IMPORTED).
9. **Map read-back is partial.** Only the seven-field lines are read back (1.3).

## 2. Level vocabulary

One ordered list, coarse to fine, for constructs and objects. A level is the granularity of an
object or a construct. The names are exact and appear in the schema. There is no `design` level
(no record or AST node sits above a `module`) and no `bit` level (a bit is a position inside a word
cell, and `lower` makes one record per word cell, shared by its gates, `connect.c:20-35`).

| Level | Kind of thing | Source of the node |
|---|---|---|
| `module` | a module specialization | AST `MODULE` |
| `block` | a process, continuous assign, generate construct or subprogram | AST `ALWAYS`, `INITIAL`, `CONT_ASSIGN`, `NET_ASSIGN`, `GENERATE`, `GEN_FOR`, `GEN_IF`, `GEN_CASE`, `GEN_BLOCK`, `FUNCTION_DECL`, `TASK_DECL`, `SPECIFY_BLOCK` |
| `branch` | an if or case arm | AST `CASE_ITEM`; for `IF`, two synthesized arm rows `IF_THEN` and `IF_ELSE` (2.2) |
| `stmt` | a statement, declaration or switch | AST `IF`, `CASE`, assignments, loops, timing statements, blocks, declarations (2.1) |
| `expr` | an expression that made a cell | AST `BINARY`, `UNARY`, `TERNARY`, `SELECT`, `CONCAT`, `CALL`, ... (2.1) |
| `word` | a word-level cell | IR node, granularity `word` (IR-9) |
| `gate` | a bit-level cell (`$_AND_`, ...) | IR node, granularity `bit` (IR-9) |
| `lut` | a `$lut` cell | IR node of type `$lut` |
| `ble` | a basic logic element | VPR `.net` (Task 8) |
| `clb` | a cluster | VPR `.net` (Task 8) |
| `site` | a placed grid location and subtile | VPR `.place` (Task 8) |

Hard and black-box cells keep their IR-9 tag `hard` or `blackbox` at the rank of `word`, with the
cell type in the object's `flags` (`cell=<type>`). `gate`, `lut` and `word` objects are told apart
by the object (granularity tag and cell type), not by the record: a record is shared by the gates
of a word cell, so the **object** carries the level, in the `O` and `N` lines (3.2). A net takes the
level of its driver; a wire and a port bit have level `word`.

**Instance is a separate axis.** An `INSTANCE` node is a sibling of the `ALWAYS` blocks in the parent
module, not their ancestor. The instance is not a rung of the ladder above. It enters the DAG as
flatten's context parent (3.1), and an object's instance path is the sequence of context parents
its walk passes (3.3). In an unflattened hierarchy there is no instance chain: the object lives in
its own module, and its chain stops at that `module`; the instance level appears only once `flatten`
has run. The construct table still holds `INSTANCE` rows (parent: the enclosing module) so that a
context parent resolves to a construct.

(its children attach to it); an unnamed `SEQ_BLOCK` that holds one statement still gets a row, so
the walk never has to decide transparency from names.

### 2.2 The synthesized `IF_THEN` and `IF_ELSE` rows

The arm of an `if` is not an AST node: `IF` has the slots condition, then-statement and optional
else-statement (`src/ast/kinds.h:69`, `SL3(E, S, S_OPT)`). A SOURCE record for a statement in an
arm points at that statement node, not at the arm. The construct table therefore gets a **synthetic
row per arm**, keyed `(run, ast_of_IF, part)` with `part` 1 for the then-arm and 2 for the else-arm
(`part` 0 is the node itself, so the key of every ordinary row is `(run, ast, 0)` and no key
collides with the `IF` row). The arm row's parent is the `IF` row; its span is the arm
statement's span. A statement resolves to its arm by the root-down walk of 4.3: when the walk
descends from an `IF` through child slot 1 or 2 it first emits the arm row, then the child with the
arm row as its parent. A statement that is not a direct child of an `IF` or a `CASE_ITEM` has no arm
row. Rule 12 (4.3) requires every key to be unique.

## 3. Records, joins and the export schema

### 3.1 What a step records: the operation class

> Correction 2026-10-25 (Task 2 review): `odin3_kit_prov` has 9 call sites, not 11 (the list below is
> the 9). `merge.c:889` and `ffbits.c:456` call `odin3_prov_derive` directly, not `odin3_kit_prov`;
> they override to coarsen through the new `odin3_kit_derive_coarsen`. Storage is 16-byte rows per
> class run plus 8-byte overrides, not "12 bytes per operation". "Fail in `Debug`" for an undeclared
> derive is `check` rule 13. A `proc` run is refine plus rewrite (proc calls the opt kit), not refine
> only. Lint: readers declare a class (rewrite), so the raw-begin rule has no exemption. Agent
> default (5): N nodes of 1 distinct construct (all parents the same record) is a rewrite, not a
> coarsen.

The class of an operation is **declared by the pass**, not inferred. A design-global op-class table
(IR addition, Task 2) holds a **default class** per `(run, op)` and an optional **override** per
DERIVED record. A class is:

- `dir`: `origin` (SOURCE or IMPORTED; implicit, never declared), `refine` (one parent, many
  pieces share the record: `proc`, `lower`), `rewrite` (1:1, or a regrouping that is not a blend:
  `opt` rewrites, `hardmap`, `lpmmap`, `dfflibmap`, `unmap`, `submod`, restored locations),
  `coarsen` (N to 1: merge, CSE, FF merge, `abc`, `raise`), `context` (flatten: the record adds the
  instance);
- `from` and `to` levels (section 2);
- `bulk`: a flag, set by `abc` for the over-budget record and the record of unanchored objects;
- `context_tail`: how many parents at the **end** of the parent list are context parents, not data.
  It is 0 for every class but `context`. Flatten declares it per derive: `odin3_flatten_derive`
  (`src/passes/flatten/prov.c:65-84`) builds `{orig, inst}` and drops either when it is 0
  (:69-76), so a record has `{orig, inst}` (tail 1), `{inst}` alone when `orig` is 0 (tail 1, no
  data parent), or `{orig}` alone when there is no instance record (tail 0). Position from the
  start is therefore not a test; the declared tail is.

Why per derive and not only per `(run, op)`. One op can derive records of two classes: the opt FF
visit begins one op (`dff_state.c:197`, via `odin3_kit_begin_rewrite`) and inside it
`dff_gates.c:35` derives 1:1 (`odin3_kit_prov` over the FF cell) while `dff_merge.c:318` derives
N:1 (over the merged FFs). And two begin sites are lazy and have no caller to declare anything:
`kit.c:904` (`rb_prov`) and `ff.c:789` (`new_prov`) begin an op when `op == 0`. So the class is a
property of the **derive call**. The side table is keyed by the derived record ID, which is unique
per `(run, op, parents, hier)`, so hash-consing and identity are untouched.
`odin3_kit_prov(oc, parents, n, &out)` (`src/passes/opt/kit.c:1060`; 11 call sites in `src/`:
`kit.c:906`, `wreduce.c:258`, `dff_gates.c:35`, `share.c:687`, `reduce.c:798,1034`,
`dff_merge.c:318`, `expr_util.c:246`, `fsm/map.c:560`) is the real derive point of the opt
overrides. Its signature gains the class: `odin3_kit_prov(oc, parents, n, const odin3_opclass
*cls, &out)` (5 parameters, within the code standard's limit; its 11 call sites and the header
`kit.h:258` change); `NULL` means the op's default. The call sites above that are N:1
set it to `coarsen`. Storage:

- the **default** for `(run, op)`: runs `{run, first_op, class}`, a new row only when the class
  changes from the previous operation of the run, at most 12 bytes per operation (usually a few
  rows per run; measured operation counts in section 5.2);
- the **override**: a row `{record, class}` (about 12 bytes) written only when a derive's class
  differs from its op's default, so only mixed ops (the opt FF visits) pay;
- a **lazy begin** has no default: its op's default is the class of its first derive. The same
  record ID derived twice with two classes is a `check` failure (rule 13), as is a missing class.

Interface (internal, `src/ir/prov.h`; the public ABI exposes only the result, 4.3):

```c
odin3_prov_begin_op_class(ctx, const odin3_opclass *cls);  /* next op; cls is its default */
odin3_prov_derive_class(ctx, parents, hier, const odin3_opclass *cls, &out);
                          /* derive; cls NULL = the op's default; non-NULL = this record's class */
```

`odin3_prov_derive` and `odin3_prov_derive_hier` keep their meaning and take the op's default;
on an op with no default (a lazy begin through the undeclared `odin3_prov_begin_op(ctx)`) they
fail in Debug. The undeclared `odin3_prov_begin_op(ctx)` stays for ops that make only SOURCE or
IMPORTED records and for lazy begins whose first derive is `odin3_prov_derive_class`. The
function `odin3_prov_begin_op_lazy(ctx)` is added for the two lazy begins (`kit.c:904`,
`ff.c:789`) so the lint rule below can reject `odin3_prov_begin_op` itself without exempting
files by name.
**`check` rule 13 fails in Debug when a DERIVED record has neither an override nor a default**, and
`tools/lint.sh` gets a rule (in `tools/check_rules.py`, which scans `src/` and `plugins/`) that rejects a
call to `odin3_prov_begin_op` outside `src/ir/` and the three readers and the restore sites of the table
below; tests and `tests/bench` (`tests/bench/bench_ir.c:107`) are not scanned, so they stay
exempt. The sites below are from a fresh `grep -rn "odin3_prov_begin_op\|odin3_kit_begin_" src`
(`odin3_kit_begin_rewrite` is the only `odin3_kit_begin_*` function). Count: 18 lines in `src/`
outside `src/ir/` call `odin3_prov_begin_op`, one of them the wrapper `kit.c:1057`; the wrapper
has 16 call sites; so there are 17 direct begin sites and 16 through the wrapper, **33 begin
sites** in all:

### 3.2 The schema, version 2

The map stays one TAB-separated UTF-8 file with LF lines, the escaping of version 1
(`%09 %0A %5C %25`, `%23` for a leading `#` of the first field,
`src/backends/common/name_map.h:1-12`) **plus `%2C` and `%7C`**, because list fields are
comma-separated and `|`-separated and `hier=<text>` (`flags`) can hold `,`, `|` and `"` (a
string-parameter specialization holds `/`, see `flatten/prov.c:30-31`); `%2C` and `%7C` are
escaped in every field of a version 2 line, and the parser unescapes them first. The map has the
same name (`<netlist>.names`, or `--name-map`). It is written only on request (3.5); without the
request the file is version 1 and byte-identical to today. Version 2 begins:

```
# odin3-names 2 hash=sha256 width=10 prov=1 ast=refs
```

`ast=` is `refs`, `constructs`, `full` or `none` (section 4): what the map holds, which is at most
what the read kept. Every later line starts with a one letter type, so a reader ignores a type it
does not know (a located WARNING, as version 1 does for a malformed line) and a version 1 reader
refuses the file at the header (unknown version).

| Type | Fields (after the type letter) | Meaning |
|---|---|---|
| `O` | `module kind short full hier file line recs level` | an object renamed by `hash`: version 1's seven fields unchanged, then `recs` (comma list of record IDs `r<n>`, the naming record first) and `level` (section 2) |
| `N` | `module kind name recs level` | an object that keeps its name (a port bit, a generator) and has records |
| `R` | `id kind level dir step parents origins cons flags` | one provenance record |
| `C` | `id kind level parent file span name` | one construct of the AST layer |
| `F` | `id path` | a file, once, referenced by `R` and `C` as `f<n>` |
| `T` | `id pass args info` | a pass run, referenced by `R.step` as `t<n>.<op>`; it has **no IR run number** (the numbering below) |
| `A` | `atom recs stale` | post-Odin: an atom (BLIF net name as VPR sees it) with its BLE, CLB and site records (Task 8) |
| `Q` | `id why objective gain pcrit rho slack near npaths members basis stale` | a join record's why-classes, objective and criticality (3.6) |
| `K` | `id member pcrit rho slack basis stale` | one member of a joined record with its own criticality (3.6) |

`stale` (last field of `A`, `Q`, `K`) is `-` or `t<n>`, the pass run that mutated the netlist after
the line was written (4.5, "later passes"). Odin III and `prov_post.py` write `-`.

**The collection rule for `recs`** (one definition; the writer, the restore check of 4.5 and the
Task 9 test use it). An `O` or `N` line is written for each live object of a module (node, net,
wire, port bit) whose `prov` field (`src/ir/ir_internal.h`: `odin3_node_rec`, `odin3_net_rec`,
`odin3_wire_rec`, `odin3_module`) is not 0; an object with `prov` 0 gets no `recs` and, if it is
renamed by `hash`, an `O` line with an empty `recs`. Odin III's `recs` holds **exactly one record,
the object's own `prov`** (the naming record); it never lists a parent, a tombstone or another
object's record, because the parents are reached through the `R` lines. `prov_post.py` does not
change `O`/`N` lines (it adds `A`, `Q`, `K`). The order is therefore trivial: one id per object,
and the roots order of the numbering below is the sort order of the objects. A restored object
keeps the single id it was bound to; a v2 file whose `recs` holds more than one id is read with a
located WARNING, the first id is bound, and the rest are dropped, so write 2 emits one id and
write 1 = write 2 holds for every file Odin III wrote.

Fields of `R`:

- `id`: `r<n>`, numbered from 1 by the **numbering algorithm** below.
- Numbering algorithm (one definition for `r`, `c`, `f` and `t`; the writer, `prov_post.py` and
  the Task 9 test implement exactly this; in C it uses an explicit worklist, not recursion, and
  gives the order stated here):
  1. **Sort keys.** `O` lines sort by `(module, kind, short)` and `N` lines by `(module, kind,
     name)`, each field compared as unescaped bytes, `kind` by its letter; `short` is the hash
     name, unique within a module. All `O` lines come before all `N` lines.
  2. **Roots, in order**: for each `O` line then each `N` line in sort order, its `recs` in the
     object's stored order (the collection rule above: one record, the object's own `prov`); then the records named by the `extra` lines
     (`A`, `Q`, `K`) in their stored line order, each line's ids in written order (4.5).
  3. **Post-order DFS**: `visit(r)` returns when `r` is numbered; otherwise it visits the parents of
     `r` in stored order, then gives `r` the next number. A record therefore comes after all of its
     parents, and an `extra` root that a later pass appended (`ble`, `clb`, `site`) is numbered
     after every record the Odin III traversal reaches, which is where it sits in the file.
  4. **`c<n>`**: after `r` is fixed, scan the `R` lines in number order; for each, its construct
     set (`S`: its one construct; `D`: the members of `J`, in the key order of 3.3) in that order;
     a construct is numbered when first reached, **after its parent chain** (parent first,
     recursively up to the `module`). Sibling constructs are visited in the key order of 3.3, so
     the numbers do not depend on row order.
  5. **`f<n>`**: files in order of first reference, scanning the `R` lines (origins, in `r` order),
     then the `C` lines (in `c` order).
  6. **`t<n>` and `<op>`**: pass runs in order of first reference, scanning the `R` lines in `r`
     order (for each line, its `step`, then the run of a `stale=t` flag in its `flags`), then the
     `stale` fields of the `extra` lines in their stored order. A `stale` run has no special
     place: it is numbered where it is first reached in this scan (the `step` of a record that
     the mutating run made, else the `stale=` flag of the first stale post-Odin `R` record, else
     an `extra` line), so it falls after every run an earlier record names. **Only referenced runs are
     written** (the reader's own pass run is written only if a written record names it). `<op>`
     is renumbered per `T` row: the distinct operations referenced, from 1, in ascending order of
     the original operation number. The `T` row has no IR run number: a restore appends fresh
     runs after the reader's own (4.5), so the IR number differs per generation and is not in the
     file.
  The numbers depend on the file's content only, so equal designs give equal bytes and the
  numbers do not depend on IR IDs.
- `kind`: `S` (SOURCE), `I` (IMPORTED), `D` (DERIVED).
- `level`: for `D`, the `to` level of its operation's class; for `S`, the level of its construct.
- `dir`: `<dir>:<from>`, the class direction of 3.1 and its `from` level (`coarsen:gate`; `level` is the
  `to` level), so a reader restores the whole class (Task 9).
- `step`: `t<n>.<op>`.
- `parents`: comma list of `r<n>`.
- `origins`: for `S` and `I`, the locations `f<n>:L.C-EL.EC`, `|` separated, at most 8 (the cap of
  `ODIN3_HDL_LOC_MAX`, with `capped` in `flags`), full spans, columns included.
- `cons`: for `S`, the construct `c<n>` (empty when `ast` is 0, or the leaf is restored or
  imported). For a `D` with a join, the reduced set `J` of 3.3.
- `flags`: comma list from `join`, `join=instance`, `lossy=bulk`, `lossy=cap`, `n=<total>`,
  `chain=span`, `capped`, `hier=<text>` (the record's `hier` string, escaped; a record with `hier`
  0 has none), `call=c<n>` (a call-site record, 4.3), `cell=<type>` on hard objects, `ctx=<n>` (the
  `context_tail` of 3.1; absent when 0), `bulk` (the class flag of 3.1; `lossy=bulk` stays the
  per-record statement).

> Correction 2026-10-27 (Peter, decision 3; Task 10 build). Two more flags are written and read, both by
> `odin3-prov-post` and the restore (Task 9 default 7 and 8 already carry them): `stale=t<n>` (last flag of a

> `sub=<n>` and, when the `.place` has the column, `layer=<n>` (Task 8, default 8). They join the flag list above;

Fields of `C`: `id` is `c<n>`; `kind` the AST kind (or `IF_THEN`, `IF_ELSE`, `CALL_SITE`); `level`
as section 2 (`instance` rows have level `instance` and parent: the enclosing module); `parent`
the parent construct or empty for a `module`; `file` `f<n>`; `span` `L.C-EL.EC`; `name` the
construct's name where it has one (module, instance, block label, declarator).

### 3.3 Joins

**Leaves and constructs.** The backward walk from a record `s` follows parents depth-first, each
record once. One kind of parent edge is not data and is skipped by the join computation: the last
`context_tail` parents of a record (3.1), which is flatten's instance record. Which parents they are
is declared by the derive, not found by position from the start: a flatten record may be `{orig,
inst}`, `{inst}` alone (`orig` is 0, `flatten/prov.c:69-76`) or `{orig}` alone. The walk enters a
context parent only to build the context chain (below); its leaves never reach `J`. The SOURCE
leaves reached are classified:

- a leaf with a construct (`ast` != 0 and a row in the table) is a **construct leaf**;
- a leaf without one (restored locations, IMPORTED, `ast` 0) is a **span-only leaf**. Span-only
  leaves are never members of `J` and never make a join (a netlist-restored record carries up to 8
  locations, `hdl_restore.c:42-43`; counting each as a construct would fake joins). The walk records
  their number as `chain=span` on `s`.

**Anchor.** A construct leaf is mapped to its **anchor**: the construct itself if its level is
`stmt` or coarser (`stmt`, `branch`, `block`, `module`), otherwise its nearest ancestor of level
`stmt` or coarser. Distinctness is decided between anchors, never between expressions, so the
`$mul` and `$add` cells of `x = a*b + c` (two `expr` leaves of one statement, neither an ancestor
of the other) have the same anchor and are not a join. For a leaf in an inlined function or task,
the construct is the call-instance row (4.3), so the anchor of the same function body called from
two `always` blocks differs by call site.

**Reduced set.** `J(s)` is the set of anchors of `s`'s construct leaves with every member that is
an ancestor of another member removed. Two anchors `a` and `b` are *distinct* when neither equals
nor is an ancestor of the other. Let `J(p)` be the same set for a parent record `p`.

**Rules.**
- `s` is a **join of distinct constructs** (`flags` has `join`) when its class is `coarsen`,
  `|J(s)| >= 2`, and `J(s)` is not equal to `J(p)` of any single parent `p`: the step itself
  blended constructs; a blend inherited from one parent is not a new join. `cons` lists `J(s)`.
- `s` is a **join of instances** (`join=instance`) when its class is `coarsen` and two construct
  leaves with the **same anchor** are reached through different **context chains**. The context
  chain of a leaf visit is the sequence of context records passed on the walk from `s`
  (flatten's instance record of each nesting level, found through the declared tail); two instances of one module differ in that
  sequence. This is computed from the record graph, not from `hier` strings (so the named
  generate scopes of one instance do not look like instances), and the instance members never enter
  `J(s)`.
- Two bits of one statement, a statement and its own condition (same anchor), or an `if` and its
  arms, are not a join. `refine`, `rewrite` and `context` records are never joins.
- **Proc mux arms.** A `proc` mux has the switch record and one record per case as parents, so it
  merges several arm statements. Decision (V112-12, question 5): `proc` operations are declared
  `refine`, so the mux is not a join. The arms of one `if` or `case` belong to one `stmt`
  (the switch); a mux is the hardware form of that one statement, and Peter's "joining of ideas" is
  about blending separate constructs. The alternative is `coarsen` with the rule above, which would
  label every mux of a two-arm `if` a join of its two arm statements.
- **One cap rule.** `cons` lists at most 16 members of `J(s)`. The members are **sorted by a stable
  key before the cap is applied**: `(file path bytes, start line, start column, end line, end
  column, kind code, name bytes, part)` compared along the chain from the `module` down (a call
  instance's chain includes its call-site row, so one body under two call sites differs), ascending,
  the same on the first write and after a restore (row indexes, which a restore changes, are not
  in the key). Two rows with an identical chain are one construct. When
  `|J(s)| > 16` the record has `lossy=cap` and `n=<|J(s)|>`. When the operation was declared `bulk`
  (3.1; the pass says so, not the construct count) the record has `lossy=bulk` and `n=<|J(s)|>`,
  whatever `|J|` is: a legitimately wide cone of a normal operation is not mislabelled bulk, and a
  small bulk run is not missed. Both flags can be set.

The pack and place records of Task 8 use the same rule: a `clb` record whose BLE records have
distinct anchors is a join labelled by the `pack` step.

### 3.6 Why things were joined and how critical they were

Peter (2026-10-25, Loki's view): timing-driven optimisation and clustering are among the steps that
hide structure, so a join must say **why** its members were put together and **how critical**
they were. Both are data on the join record, not prose. They are written as the `Q` and `K` lines
of 3.2, only for `coarsen` records that are joins and for **logic** `clb` records (3.3; the I/O, memory and
multiplier blocks of the architecture get none); a consumer that does not know the types
ignores them.

**Limit, stated.** Odin III's own joins (the `abc` LUT regions, the opt merges, the FF merges)
carry an `objective` and **no pair class**: a pair class needs a packed CLB, so `why` is empty for
them. No class set for LUT joins is defined in this version; defining one (for example by the
shared-input structure of the cells inside a LUT region) is a later question, not part of Peter's
2026-10-25 decisions.

**Pair classes (the N17 definitions).** Norns round 4 (`norns/docs/plan/round4.md`, "RQ-N17", merged
in `norns` main `4a100fc`; the census code is `scripts/r4census.py`, read only) classes every
unordered pair (a, b) of members of one logic CLB by the **first** rule that applies. Members are the
LUT (`.names`), FF (`.latch`) and adder atoms of the CLB. A net is a BLIF net that does not drive a
`.latch` clock pin; it is *local* when its fanout (sink pin count) is at most 32 and a *broadcast*
net above 32. The pack-time criticality of an atom is the maximum, over its non-clock input pins,
of VPR's `setup_pin_criticality` from the pre-cluster timing analysis; the critical threshold is
theta_c = 0.5.

| Class | Rule |
|---|---|
| `SC` series-critical | a local net is driven by one of the two atoms and the other is among its sinks, and the pack-time criticality of that sink pin is >= 0.5 |
| `SN` series-noncritical | the same direct local net, criticality < 0.5 |
| `SI` shared-input | not SC or SN; both atoms are sinks of one common local net (fan-in sharing) |
| `OR` orthogonal | not SC, SN or SI; the two atoms have the same word label (round 2) or are sinks of one common broadcast net (enable, reset, select) |
| `FL` filler | none of the above |

**The word label (OR)** is read from the construct chain: the atom's nearest ancestor of level
`word` (a declarator) among the constructs of the records of its first leaf, so it needs a map
with the chain. It is not taken from the Norns round-2 `members.json`. An atom without a chain
(IMPORTED, a BLIF with no map) has no word label, and the word-label test is false for it. The
Task 10 comparison with `r4census.py` reports any pair where the two labellings differ.

The classes are exhaustive and disjoint by precedence. Peter's three-way illustration maps to
SC (series-critical), SI + OR (shared-input and orthogonal) and SN + FL (filler and non-critical).

**A join can be a hybrid.** The `why` field of `Q` is a **multi-label set with shares**: for a CLB
of m members, the m(m-1)/2 pairs are classed, and `why` lists `class:share` for every class with a
non-zero count, share = pairs of the class over all pairs, rounded to three decimals by **largest-remainder**
(floor each share to 0.001, then add 0.001 to the classes with the largest remainders, ties in the
order SC SN SI OR FL, until the sum is 1.000), listed descending, ties in the same order. A class
with a non-zero pair count is always listed, even when it rounds to `0.000` (1 pair in 2000). A CLB of one
member has no pair and an empty `why`. The weighted shares of N17 (w1: pair weight = the smaller
pack-time atom criticality; w2: the smaller post-route criticality rho) are not stored; they are
computed from the `K` lines, and for that the `K` lines of a logic `clb` list **every member**
(the count is bounded by the CLB capacity of the architecture, so no cap applies). Clustering classes other than these five (a future packer's own) are
written as `X-<name>`; `why` is never a single forced label.

**Gain terms (the mechanism, where the packer records it).** `gain` is a `source:share` list of
how the CLB's molecules came to be added, with the sources the Norns census records (seed,
connectivity and timing, affinity group, transitive, high fanout, attraction group, RAM,
unrelated; share = molecules added by the source over all molecules). Pair classes say what the
members share; `gain` says which packer term pulled them in. Together they are the hybrid:
structure and mechanism. Empty unless a census file exists.

*Joining the census to a `clb` record.* The census keys the `M` and `A` lines by `cseq` (cluster
sequence), not by CLB. `prov_post.py` maps `cseq` to a `clb` record through the atoms: a `cseq`
whose closed cluster (it has a `K` line) holds the atoms that sit in one block of the VPR `.net`
(`final.flat_place` or the `.net` block tree gives the CLB of each atom) is that CLB's cluster.
A cluster destroyed or never closed (no census `K` line), a CLB whose atoms span several `cseq`,
and a `cseq` with atoms in no CLB give `gain` absent (`-`). **The packing-differs rule:** the
census names the `.net` it ran with (its SHA-256, which N17 requires to match the final run's);
`prov_post.py` compares it with the SHA-256 of the `.net` it reads and, on a mismatch, writes
`gain`, `pcrit` (census-derived) and the census-based `why` as absent, never `r` or `i`, with a
located WARNING.

**Objective (Odin III passes).** `objective` is the stated purpose of the step that made the
join, read from the pass run (`T` row: pass, `args`, `info`): for `abc`, a depth-or-area
statement that a rule of `prov_post.py` or the exporter derives from the script (a script that
states none gets an empty field, never a guess); for the opt passes, the pass kind (`opt:merge`,
`opt:ffmerge`, `opt:wreduce`, ...), which is the name of the mechanism and not a purpose, and is
always known; for `pack`, the packer and its options (`vpr-pack`, `norns-pack:beta=4`).
**Marking:** a value read verbatim from the pass run (the pass kind, a packer option) is `r`; a
script-derived objective is `i`, because the mapping from an ABC script to depth or area is a
rule applied afterwards (the rule is fixed in Task 10 against `src/passes/abc/` and shown in the
test), unless the script states the goal literally, which is `r`.

**Criticality data.** For a join with members M (the atoms of a `clb`, the cells of a `lut`):

- `pcrit`: pack-time criticality, the maximum over M of the atom value above, 0 to 1, three
  decimals. Empty if the packer did not provide it.
- `rho`: post-route criticality, the maximum over M of rho(atom), where rho is the maximum over the
  attributed paths through the atom of arrival_ns over arrival_ns of path 1 (0 for an atom on no
  reported path), the N17 definition.
- `slack`: the smallest post-route slack in ns over M, from the attribution (`timing_attr`, V1.1.1).
- `near`: near-critical flags with the margin stated: a comma list `5:<0|1>,10:<0|1>`. A path is
  near-critical at margin m (percent) when arrival_ns >= (1 - m/100) * arrival_ns of path 1; the
  join is near-critical at m when a path through any member is. The margins 5 and 10 are the N17
  pair; the list may name others.
- `npaths`: the number of near-critical paths through the join at each margin, `5:<n>,10:<n>`.
  It counts the paths the setup report holds (`--timing_report_npaths 1000`); when the report holds
  1000 and the last still lies within the margin, the count is written `>=<n>` (capped).
- `members`: the member count; the `K` lines list every member of a logic `clb`; for any other
  join they list at most 16 members, the highest `rho` first (ties by name), with `members` the
  total. Each `K` line has its own `pcrit`, `rho`, `slack` and `basis`.

**Recorded or inferred.** `basis` is a comma list `field=r|i` over `why`, `objective`, `gain`,
`pcrit`, `rho`, `slack`, `near`, `npaths`, with `-` for an absent field. `r` means every input of
the value was read as written by a tool: a pass-run field, a VPR report, a census file. `i` means
at least one input was inferred by `prov_post.py` from netlist structure or from a proxy. Where each
value comes from:

post-Odin tool (`prov_post.py`, question 7) rewrites that line with the other fields and adds the

## 4. The AST layer: how the chain is obtained

Peter: the AST and the netlist are both provenance. So the AST layer is not a lookup at write time
that may fail; it is held by the design and exported. Three forms, one schema (`C` lines):

- **refs (recommended).** A design-held *construct table*: the AST nodes that any SOURCE record of
  the run references, plus all their ancestors up to the `module`, with kind, level, span, name and
  parent. Built once, when elaboration ends (`odin3_elab_stage2` success), from the elaborated
  store while it is still alive, whatever `--keep-ast` says.
- **constructs (minimal alternative).** The same table restricted to nodes whose kind is a
  construct kind (levels `module` to `stmt`, section 2): no `expr` level; a record that references
  an expression resolves to its nearest construct ancestor.
- **full (dearer alternative).** Every node of the elaborated store (all 68 kinds), parent, span,
  name. For a consumer that wants expression trees; not needed for the chain.

### 4.1 Evidence for choosing a held table over "the AST at write time" (option A)

Option A reads the held AST store when a writer runs. It fails the requirement in four checked
ways: (1) the store is dropped at the end of the read unless `--keep-ast` (1.4), and neither the
Python API, nor `odin3-flow`, nor the CLI default keeps it; (2) the ABI does not expose the
`ast` field, so a Python consumer could not resolve it even if the store were held (1.3); (3) a
design read back from BLIF or JSON never had the store; (4) the construct chain must survive the
file (the map). Making every flow keep the AST costs about 41 bytes per node
(`docs/specs/2026-10-11-2D-elaboration-design.md` section 11, `ODIN3_ELAB_MAX_ELAB_NODES`) plus the
parent index, held for the whole run, to export a subset at the end. Option A stays valid as a
fallback: a writer that finds the elaborated store held may export from it (`ast=full`).

The table is the compact, persisted form of exactly what option A reads, built early. Option B as
originally framed (a construct index field in `odin3_prov_record`) would put the construct in the
hash-consing identity of every SOURCE record and change a struct that IR-12 and check rule 7 test;
rejected: the record already has `ast`, the table resolves it.

### 4.2 Modes are read-time

The mode is a **read-time option**: `read_verilog --prov-ast refs|constructs|full|off` (default
`refs` as designed; **the cost gate of 5.3 failed, so the CLI default is `off`**, see the Task 4 gate
correction; the slang reader takes the same option through the shared hook, `src/api/elab_abi.c:79`).
`off` skips the snapshot completely (the read-time off switch: no table, no cost; the map then has
`ast=none`, the `R` lines have empty `cons`, and `check` rule 12 is vacuous). The export option
`--prov-map [refs|constructs|full]` only **selects a subset** of what the read kept (`full` kept
allows all three; `refs` kept allows `refs` or `constructs`; `none` allows none). Equal inputs and
equal options give equal bytes on every machine.

**Budget exhaustion is an error.** If the table does not fit the design byte budget
(`src/passes/budget.h`), `read_verilog` fails with `ODIN3_ERR_NO_MEMORY` and a message naming
`--prov-ast constructs` and `--prov-ast off`. There is no silent downgrade at run time (it would
make `ast=` and the bytes depend on the machine).

   Rules for all of them:
   - **Strings** (`file`, `name`, `hier`) are owned by the design, NUL-terminated, and valid until the
     next IR mutation of the design or its destruction, as the header's "Strings" rule says
     (`odin3.h:134-137`); a copied struct holds nothing else. Record IDs and construct rows are
     stable until the design is destroyed (records are never deleted, `prov.h:19-23`; the table is
     append-only and compaction does not touch it).
   - **Ownership**: the caller owns the `out` structs; nothing is allocated for the caller; a
     visitor runs after the walk (as `odin3_prov_visit_sources` does) and may call reader functions;
     it must not change the design.
   - **Dead objects**: a node, net or wire that is dead but not yet compacted answers like a live
     one (as `odin3_prov_visit_sources`, `odin3.h:812`); an ID `compact` has freed names no object and

     construct is reported once**, at its first reach, with the record of the leaf that reached it.
     A leaf without a construct is skipped. **`odin3_prov_visit_joined`** visits the rows of `J`

### 4.4 What the chain cannot give

Records with no `ast` (restored locations, IMPORTED) have no construct; their `cons` is empty and
`flags` carries `chain=span`. Objects of a design read from BLIF have `I` records and no chain at
all; that is stated in the map and not guessed. An unrolled loop's iterations share their body's
records (EL-45), so the construct of an iteration is the loop body, with the loop index only in
`hier` when the scope is named. A design read back from a version 2 map has the chain of the map
(4.5; decision 7 of D14 as amended); a design read back from a version 1 map has none.

### 4.5 Restoring a version 2 map (read-back; Peter 2026-10-25)

Peter took question 4 the other way: read-back is in. `read_blif`, `read_json` and `read_verilog
-netlist`, when given a `--name-map` of version 2 (the `--name-map` of today, `read_verilog.c:446`),
rebuild the records and the construct table of the file in the design. A design read back from a
version 2 map then has the chain, the classes and the joins of the design that wrote it.

**What is read.** `F`, `T`, `R`, `C`, `O`, `N`, `A`, `Q` and `K` lines. `T` rows become pass-run rows (pass,
`args`, `info`) in file order, appended after the reader's own run, so `t<n>` maps to a run and
`t<n>.<op>` to `(run, op)` (the IR run numbers are new and are not the writer's; the file has none,
3.2). `R` rows become records in file order (parents before children, 3.2), each `D` record with
its class (`dir:from`, `level`, the `ctx=` and `bulk` flags, 3.1) as an override or, when every
record of an op agrees, as the op's default. `C` rows become the restored construct table. `O`
and `N` rows bind the object (by its short name, as the version 1 reader does) to the record of
`recs` that names it; a `recs` with more than one id breaks the collection rule of 3.2 and is a
located WARNING (the extra ids are dropped). `A`, `Q` and `K` lines (post-Odin data) are held
verbatim in a design-held text list, their `r<n>` ids rewritten to the new record IDs (this is the
third design-global table, `extra`, filled only by a restore; it adds no field to any IR object).
The records that only these lines reach (the post-Odin `ble`, `clb` and `site` records) are
restored like any other and are **roots of the traversal** (3.2, numbering step 2), so a second
write exports them and the lines do not dangle. A file that fails `names --check` (3.5) is
refused before anything is bound.

**A v2 restore creates no restored-location records.** With a version 1 map the readers make a
restored-location SOURCE and a derived record for each object (`blif/reader.c:789`,
`json/reader_locs.c:68`, `elab/netlist_locs.c:118`; derive `hdl_restore.c:46-48`, and
`blif/reader_locs.c:341`). With a version 2 map those steps are **skipped**: an object binds to the
record its `O` or `N` line names, and an object the map does not list has record 0. Every object
that had records when the map was written is listed (it has an `O` or `N` line), so this loses
nothing and the second write gains no row. The reader's own pass run is written only if a written
record or a `stale` field names it (3.2, step 6).

**Later passes: restored post-Odin data goes stale, it is never re-emitted as current.** `A`, `Q`,
`K` lines and the post-Odin records are keyed by the atoms and cells of a netlist. After a restore,
the first pass run that is not a reader, a writer or a pass that only looks (`check`, `stats`,
`hierarchy`, `names`, `dump_locs`, `dump_project`, `sim`, `preprocess`; fix round 1) is the
**mutating run** `t`; a run of such a kind that came before the restore counts too. Where it is held: not an IR field of any object but a
slot (a pass-run row number, 0 = none) in the design-held `extra` table (the third design-global
table, filled by a restore; a design with no restore has no table and no slot). The restore sets
it to 0. `odin3_pass_run_begin` sets it to the new run's row when the `extra` table exists, the
slot is 0 and the pass is not a reader, a writer or one that only looks (above); it never changes it
afterwards (so the first mutating run is kept) and `odin3_design_copy` copies it with the table.
The writer reads it to put `stale=t<n>`; the numbering of 3.2 (step 6) gives it its `t<n>`. From then on, at write time, every restored `A`, `Q`, `K`
line gets `stale=t<n>` in its last field, and every post-Odin record (those reachable only from
`extra` roots) gets the flag `stale=t<n>` in `R.flags`. History is kept: they are still written, still
roots and still hash-consed, and the run `t` is a `T` row (step 6 counts the `stale` field as a
reference); `basis` keeps its value but a consumer must treat a stale line as not current.
Odin III writes no `A` or `K` line for the changed netlist and no `Q` line for a join record
that was restored; for a **new** join record (made after the restore, for example by `opt`) it
writes the fresh objective-only `Q` of 3.6 with `stale=-`, and the restored stale lines stay as
history. `prov_post.py` writes fresh `A`, `Q` and `K` lines with `stale=-`. A line already stale keeps its first mutating run. Test: restore, then `opt`, then
write; the restored lines carry `stale=t<n>`, each new join of `opt` has a `Q` with `stale=-` and
only `objective`, a second restore and write keeps all of them (Task 9).

**How a restored SOURCE record refers to a restored construct row.** There is no AST store, so the
`ast` field cannot be a node ID. Decision: **the `ast` of a restored SOURCE record is remapped to the
construct row**: the restore assigns each `C` row `c<n>` the number `n` as its `ast` key, in the
pass run it belongs to (the run of the SOURCE records that reference it, the original read run
`t<k>`), and the restored SOURCE record carries `ast = n`. The construct table key `(run, ast)` of
4.3 is therefore unchanged in form: `construct_find(design, run, n, part, call)` finds the row;
`part` and `call` are stored in the row as before. A synthesized `IF_THEN`/`IF_ELSE` or call-site
row gets its own `n` (it is a row of its own), so the remap is injective on `(ast, part, call)`.
The alternative, a separate `construct_ref` field in the record, adds a field to a record and is
rejected (D14 decision 3). The `restored` flag is **per pass run** (on each restored pass-run row, 4.3), not per table: a
design restored from a map can still run `read_verilog`, whose live rows (keyed by store node
ID) are consumed normally, while the guard stops code that expects `ast` to be a store node ID
(the elaborator, `dump_locs`) from reaching a restored run's rows. With `ast=none` in
the header no `C` rows exist, every restored SOURCE has `ast` 0, and the design reports `ast=none`
again on the second write.

**Hash-consing identity.** A record's identity is unchanged in form: SOURCE `(origin locations,
ast, run, hier)`, DERIVED `(run, op, parents, hier)` (IR-13). The restore interns the records in
file order, so each lands on a fresh ID. The `ast` remap is injective on `(ast, part, call)` per
run, but **the map is not injective on the original `ast`** in two cases, so the claim is scoped:

- **`--prov-ast constructs`**: SOURCE records for equal-span `expr` nodes (counted in 5.2)
  resolve to the same construct row, get the same `ast = n`, and restore into one record. Parent
  lists and the `R` count then change on the first rewrite.
- **A call-site miss** (`chain=span`, a SOURCE record with `ast` != 0 and no row, rule 12): it
  restores with `ast` 0, and two such records that differ only in `ast` collapse.

For these, the guarantee is weaker and stated: the second write is the canonical form, and every
later generation is byte-identical to it (write 2 = write 3), and the chain, join flags and
`Node.provenance()` answers of every object are unchanged by the collapse (anchors do not change).
For `refs`, `full` and `ast=none` with no call-site miss, write 1 = write 2. What is lost and
stated: records no object or `extra` line reaches (the writer exports only reachable records),
the original `ast` node IDs, the original IR run numbers, and `hier` strings identical to the
file's text only.

**`check` on a restored design.** Rule 12 holds unchanged: every SOURCE with `ast` != 0 resolves to
a row, which the restore guarantees by building the rows first; it is skipped when the header says
`ast=none`. Rule 13 holds unchanged: every restored DERIVED record has a class from its `dir`
field, a `context_tail` no larger than its parent count, and no record carries two classes. A
version 2 file written by a version-1-era tool, or one with a `D` record without a `dir`, fails the
restore with a located error and leaves the design as the reader made it (no partial restore).
The restore is run under `check` in Debug like any reader.

**Round trip (what is claimed).** Two claims, scoped:

1. **The map.** write, read with the written map, write again: for `refs`, `full` and `ast=none`
   with no call-site miss, the two maps are byte-identical (numbering by the algorithm of 3.2,
   classes through `dir`, `ctx` and `bulk`, `extra` lines and their records as roots, stale marks
   kept). A file extended by `prov_post.py` appends lines at its end; it is not in canonical
   line order, so the test normalizes with one rewrite: write 2 = write 3, and the set of lines
   of the `prov_post` file equals the set of lines of write 2. `constructs` mode and call-site
   misses: write 2 = write 3 only (above).
2. **The netlists.** The netlist half is claimed **only for the reader and writer pairs whose
   idempotence is proved first**: Task 9 begins with a check, on every micro, that
   `read_X(write_X(d))` written again equals the first output byte for byte (node order, `.latch`
   initial values, parameters, ports), for `write_blif --vtr` with `read_blif`, `write_json` with
   `read_json`, and `write_verilog` with `read_verilog -netlist`. `test_hash_readers.c`
   round-trips names only and is not that proof. A pair that fails the check is listed in the
   test; it keeps neither claim (no netlist claim and no map claim), because a reader that does
   not reproduce its own writer's netlist cannot be relied on to bind the same objects. The map
   claim is scoped to passing pairs.

Task 9 holds the tests.

## 5. Size (measured)

### 5.1 Bounds

- Records are hash-consed, so a record is written once however many objects carry it; `O` and `N`
  lines carry only the record IDs. Records written are the records reachable from the objects
  written (not the whole store); the sizes below count the whole store, so they are upper bounds.
- Construct rows are written once, only for constructs a written record references (`refs`), their
  ancestors included.
- Joins list at most 16 constructs; the ABC budget bounds DERIVED edges by
  `16 x (old cells + new objects) + 65,536` per run (`docs/IR.md` "Provenance across ABC").
- In memory: the construct table is 48 bytes a row (44 plus alignment); the op-class table is at
  most 12 bytes per operation.

## 6. Steps after Odin III

A tool, `tools/flow/prov_post.py` (standard library only, next to `timing_attr.py`, installed by
the same `CMakeLists.txt`, `pyproject.toml` and `plugins/python/entry.py` rows as V1.1.1), command
`odin3-prov-post FLOW_DIR`. It reads:

- the BLIF VPR read (hash names) and its map (`<blif>.names`, version 2);
- VPR's packed netlist `.net` (XML; block tree with the primitive, BLE, CLB nesting and the atom
  name of each primitive) and `.place` (block, x, y, subtile).

It appends to the map, in the same file and schema: `R` lines of level `ble` and `clb`
(`dir=coarsen`, `step` `t<n>.0` a new `T` row `pack`, parents = the records of the atoms inside),
`R` lines of level `site` (`dir=rewrite`, parent the CLB, the `.place` coordinates in `flags`),
and `A` lines keyed by atom name. Joins use section 3.3 unchanged: a CLB whose atoms blend
distinct anchors is labelled a join by `pack`. The map is rewritten atomically (temporary file
then `os.replace`). It parses version 2 with its own stdlib parser (`tools/flow/name_map_v2.py`,
Task 7): `tools/flow` is stdlib-only and `odin3.read_name_map` needs the cffi package.

**Atom name join.** VPR names a block after the net its first output drives and an I/O pad after
its port (`docs/V1.1.1.md` Join). With `--name-style hash` those names are the hash names written
in the BLIF; the `O` lines of the map are keyed by the same short names, so the join is exact and
needs no second BLIF. A BLIF written with short names has no map keyed by them, so the tool
refuses it (the V1.1.1 route with two BLIFs stays for that case). A provenance-named BLIF joins by
the `full` field (3.5).

## 7. Consumers (read-only study; no consumer code in this lane)

### 7.1 Loki (how it labels cells from provenance today)

Loki (`loki/` repo, Python, imports `odin3`) labels final cells by a **span join**:

- A word-level snapshot is taken after `proc; opt; flatten; ...` but before `lower`
  (`loki/snapshot.py:39-62`), one `WordCell` per live word node with `spans=node_spans(node)`, where
  `node_spans` is `node.sources()` (`loki/snapshot.py:20-21`), i.e. `odin3_prov_visit_sources`
  (`plugins/python/odin3.py:650`): file, line, column, end line, end column.
- Final cells (LUTs, flip-flops, gates) get the same `spans` from the final design
  (`loki/extract.py:51`).
- `match_words` (`loki/labels.py:41`) says a word cell W matches a final cell c when `set(W.spans)`
  is a non-empty subset of `set(c.spans)`, sorted by span count then ID. `_cell_label`
  (`loki/labels.py:161`) groups matches with equal (spans, type) (`_groups`, `:75`), sets
  `construct_types` (distinct types joined by `|`), `construct_type` (`_primary`, `:147`),
  `n_construct_cells`, `ambiguous` (identical spans cannot be told apart), and the role.
- The module path cannot come from the record. Flatten keeps the instance path in the record's
  `hier` (`src/passes/flatten/prov.c:33-62`), but the ABI does not return `hier`, and a cell lists
  only the innermost instantiation span. `module_path` (`loki/labels.py:83`) therefore climbs
  from the innermost site to the top through the module hierarchy it recorded before `flatten`
  (`take_instances`, `loki/snapshot.py:65`) and writes `top/*` when a module has several parents
  (the open question in `docs/specs/2026-10-21-l0-dataset-design.md:124-129`).
- The spec (`docs/specs/2026-10-21-l0-dataset-design.md:102-151`) states what the labels rest on:
  `sources()` "is the only provenance the ABI exposes" (`:108-111`); a LUT lists all spans of its
  cone (`:150-151`, section 5.3); a LUT that merges several constructs lists all of them and "a LUT
  is not split".

What D14 changes for Loki, concretely:

1. **The join becomes a walk.** With records and the chain exposed (Tasks 3 and 6), the construct
   of a final cell is read from its record ancestry, not by span-subset matching. The
   identical-span ambiguity (`ambiguous`) goes away **for expression cells and instances**: two
   instances of one module have different context chains, and two statements on one line have
   different constructs. It does not go away for cells made by one `proc` switch: the muxes and
   selects of a switch share one record (`docs/specs/2026-10-11-2E-proc-design.md:898-906`), so
   Loki word cells made by one switch still tie, and `ambiguous` stays for them.
2. **`module_path` is exact** from the flatten records' context chain, including nested instances.
3. **New label columns** become possible from the chain: `block` (always, assign, generate),
   `branch` (the if or case arm), `stmt`, `expr` kind and span, `join_of` (the constructs a LUT
   blends, from section 3.3) and `n_constructs`. `LABEL_COLUMNS` (`loki/schemas.py:21`) is a Loki
   schema change in its own lane; the existing columns keep their meaning.
4. **L15 loss audit** (`work/controller-scripts/ROUND4-PLAN.md`, Loki r5: "construct at file:line
   lost at pass P because merged with Q") needs the join label of 3.3: the first `coarsen` record
   in a construct's descendants that has `join` and names the construct in `cons` is "lost at step
   P" (pass, run, op), "joined with Q" is the other members of `cons`. Today this has to be
   reconstructed from pass-by-pass snapshots of spans; with the map it is a lookup per construct,
   and the snapshots become a check.
   **Why and how critical (3.6).** The L15 line carries the `Q` line of that first join record:
   "construct X (`file:line`, `stmt`) lost at step P (pass, run, op), joined with Q because
   <classes> (<basis>), criticality <c>". Example: "`assign y = a & b` (`top.v:30`) lost at `pack`
   (run 7, op 12, `norns-pack:beta=4`), joined with `always @(posedge clk)` (`top.v:12`) because
   series-critical 0.40 + shared-input 0.35 + filler 0.25 (recorded), pack criticality 0.82, post-route
   rho 0.97, slack 0.21 ns, near-critical at 5% on 12 paths". For an Odin III step the "because" is
   the objective: "joined with Q by `abc` (run 3, op 41, depth objective); post-route slack 0.4 ns,
   near-critical at 10%". A construct that is lost in a non-critical filler cluster is then
   separable from one lost on a near-critical series chain, which is the optimisation question
   Peter raised (what hides structure, and does it matter for timing).
5. **From-BLIF designs** (`docs/specs/2026-10-21-from-blif-design.md`): a design read back from a
   BLIF carries no chain unless it is read with the version 2 map of the flow that produced it: then
   the records and the construct table are restored into the IR (4.5), and `Node.provenance()` and
   `Node.chain()` answer as for a freshly elaborated design. Loki can also read the file directly
   (`odin3.read_name_map`). A BLIF without a map has no chain.

Loki's stated facts (`docs/specs/2026-10-21-l0-dataset-design.md` section 5.1, re-checked by
its tests) stay true: `Node.sources()` and `odin3_prov_visit_sources` do not change (Task 3).
Loki keeps its span join as the fallback for designs without a map (BLIF only, no Odin III
provenance) and for the `chain=span` records of 4.4.

## 8. Compatibility

- `--name-style short|provenance|hash` unchanged. Without `--prov-map`, `hash` writes the map
  version 1 byte-identical to today; the netlist files are byte-identical in every mode (the hash
  name depends only on the first-leaf full name, H-2).
- `--prov-map` without `--name-style hash` is an error (3.5). `write_blif` PLAIN, `write_json` and
  Verilog with short or provenance names carry no chain.
- `read_blif --name-map`, `read_json --name-map` and `read_verilog -netlist -name-map`
  (`src/frontends/verilog/read_verilog.c:446`) read version 1 as now; they accept version 2 and use
  only the `O` lines (ignoring other types with one WARNING per type). **They also restore the
  records, parents, classes and the construct table** of a version 2 map (4.5, Task 9; Peter
  2026-10-25): the design answers `Node.provenance()` and `chain()` as the writing design did,
  and write, read, write gives byte-identical maps, as scoped in 4.5 (netlists only for the
  reader and writer pairs whose idempotence Task 9 proves first). A version 1 map restores no
  records (restored locations only, as today). A version 1-only build refuses a version 2 file at
  the header; this is why version 2 is opt-in.
- `names --lookup/--reverse/--check` accept both versions; version 1 output is unchanged.
- **Behaviour changes (only with `--prov-map`; version 1 and every netlist are as before).** (a) A
  derived record whose operation has no operation class is refused: `ODIN3_ERR_INVALID_ARG`, the
  record, run and operation logged, no map and no netlist written (a Debug build stops earlier, at
  the `check` before the pass, with `ODIN3_ERR_CHECK` and rule 13; nothing is written either).
  Earlier Task 5 code wrote a map for it that failed its own check. (b) `--prov-map` given twice is
  an error. (c) A word right after `--prov-map` that is `refs`, `constructs` or `full` is the mode,
  so a file of that name is written `./refs`. (d) A line over `ODIN3_NAME_MAP_MAX_LINE` (1 MiB)
  is refused. (e) An overlapping use of the label cache of one design fails (logged) instead of
  racing.
- Goldens: none changes. The goldens are BLIF, logs and `.prov` produced without the new option
  (`CLAUDE.md` rule 9); the new code runs only on request, the construct table is not written to
  any existing output, and `dump_locs` is untouched. Task 4 adds a test that runs the whole micro
  set before and after and compares every writer output byte for byte.
- **ABI version 6 to 7.** A v6 plugin does **not** load against v7: `src/api/plugin.c:30` passes
  `ODIN3_ABI_VERSION` to the plugin's init, `plugins/example_c/example_plugin.c:108` rejects any
  other value (`ODIN3_ERR_ABI_MISMATCH`), and `plugins/python/odin3.py:115` requires an exact match
  with the library. The consequence is that every compiled plugin is rebuilt against the v7 header
  (in this tree: `plugins/example_c` and the `tests/unit` plugins, which are built with the tree);
  third-party plugins must be rebuilt. The `odin3.h:57` comment ("incremented on every incompatible
  change") is the stated policy, but v5 (S1 simulation API) and v6 (the reader seam of D13) were
  bumped for additive changes (`docs/V1.1.0.md:44-45`), so the practice is a bump for every API
  addition and there is no stability promise (`docs/V1.1.0.md:92`). The alternative is an additive
  route without a bump (the functions are added and the version stays 6, so old plugins keep
  loading, but a v6 host with a new header would fail only at call time); this is question 2.
- `schema_version`: the map's header version is the schema version (2); each later additive
  field gets a new trailing field, and readers must tolerate unknown trailing fields on `R` and `C`
  lines.
- Memory: the construct table adds 48 bytes per row to every `read_verilog` run whose mode is not
  `off` (the CLI default is `off`; Task 4 gate), counted in the
  design byte budget (`src/passes/budget.h`; section 5.3 gives the shift of the opt and budget
  gates, `src/passes/opt/register.c:238`, `src/passes/budget.c:154`). If the table does not fit,
  the read fails with `ODIN3_ERR_NO_MEMORY` and names `--prov-ast constructs|off` (4.2).
